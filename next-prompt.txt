## THE TWO DEFECTS ALREADY CAUGHT (do not re-introduce them)

**(1) A decode-based check CANNOT distinguish an omitted proto field from an explicit `null`.** The PLAN's first draft proved the `request.body`/`response.body`-ABSENT assertion with an `EmitUnpopulated: true` deliberate break, expecting the decoded `Body` to become non-nil. **It does not.** `protojson.Unmarshal` maps `"body": null` back to a **nil** `Body`, and `EmitUnpopulated` is a *superset* of `EmitDefaultValues` (so `raw_value: ""` and `trailers: []` still render). Under that break the whole `0099` fixture stayed **GREEN — no assertion fired at all.** Measured:
```
BAD file contains "body": null:                       true
after decoding it: req.Body==nil? true  resp.Body==nil? true
would assertion(5) `GetBody()!=nil` fire?             false
```
⇒ The property is now split: assertion **(5)** is a decoded `GetBody()==nil` check, and assertion **(5b)** greps the **RAW file bytes** for any `"body"` key. Break **(c)** (`EmitUnpopulated`) proves (5b) **only**; a new break **(c′)** (fabricate `Body{AsString:"x"}`) proves (5). **If break (c) fires assertion (5), or fires nothing, STOP — the body-absence proof is compromised.**

**(2) The ONE-SHARED-VALUE proof was self-defeating.** `TestChainDestroy_EmitsExactlyOnce` originally did `f := hf.Decoder.(*tapFilter)` and fed BOTH header sets into `f`. Under the two-value split it exists to forbid, `hf.Decoder` **is** the fresh value — it received both header sets, matched, emitted, and the break **PASSED**. The test now drives the **interface values** (`hf.Decoder.DecodeHeaders`, `hf.Encoder.EncodeHeaders`). **Preserve that shape if you refactor.** Also: do NOT add a break that drops `Decoder` entirely — any test dereferencing `hf.Decoder` panics on a nil interface conversion (a crash, not a proof). That framework fact is pinned by `chain_test.go`'s `TestDestroy_EncoderOnlyFilterWithNoDecoderFires`.

## The FOUR LOAD-BEARING seams (pinned at the SPEC, re-derived and CONFIRMED at the PLAN — do NOT re-derive, do NOT weaken)

- **THE EMIT SITE: ONE SHARED `*tapFilter` VALUE IN BOTH `HTTPFilter` FIELDS.** `FilterChain.Destroy()` (`chain.go:665`) is `destroyOnce`-guarded and its loop is `if f.Decoder != nil { f.Decoder.OnDestroy() } else if f.Encoder != nil { f.Encoder.OnDestroy() }` (`chain.go:668-672`). The branches are **mutually exclusive**. So (a) a both-sided filter's `OnDestroy` fires **EXACTLY ONCE** — no once-guard is needed for correctness, and the PLAN pins **NO defensive `sync.Once`** (it would be dead code no test could drive); and (b) **an Encoder-only `OnDestroy` is UNREACHABLE whenever a Decoder is present.** A natural two-value decomposition would silently NEVER emit. Tap installs ONE shared `*tapFilter` in both fields — the landed `compressor` precedent (`compressor.go:300-307`, `Decoder: f, Encoder: f`).
- **THE `:status` WIRE-LEAK TRAP.** `:status` is NOT in the encode header map (`connection.go:736` says so verbatim); take it from `EncoderFilterCallbacks.ResponseStatus()` (`callbacks.go:488`, ADR-0196). **NEVER mutate the map handed to `EncodeHeaders`:** `connection.go:738` passes `merged` (built `:733`) to `RunEncodeHeaders`, then `ReconcileOrderedHeaders(resp.Headers, merged)` at `:741`, and `writeH1Reply` emits every field after `textproto.CanonicalMIMEHeaderKey` — which is a **no-op for `":status"`** (empirically confirmed). A synthetic `:status` WOULD be emitted as a literal header ON THE WIRE (H1) or a duplicate pseudo-header (H2). Build a COPY. Likewise `:scheme` is NEVER injected into the filter-visible request map (only `:method`/`:authority`/`:path` are) — UNassert it cross-side.
- **THE TRACE IS AN END-OF-STREAM ARTIFACT AND THE REFERENCE NEVER EARLY-EMITS.** Even when an `or_match` request arm is already TRUE at decode, the reference still emits the WHOLE stream (request + response) at stream end (the `orshort` probe). The tri-state (match/no-match/undetermined) exists to RESOLVE the tree, NOT to decide when to emit. Emission is unconditional at stream end, gated only on the resolved match.
- **THE FIXTURE MUST DRIVE A BODYLESS `GET` → `204`.** The reference ALWAYS captures bodies with NO suppression knob, but a **zero-length body message OMITS the `body` field entirely**. Only a bodyless request + a 204 response yields structurally headers-only traces on BOTH sides. **No new BackendKind is needed:** the landed `HTTPStatusHeader` (kind 3) backend driven with `x-backend-status: 204` emits a bodyless `204 No Content` + `Content-Type: text/plain`, **no `Content-Length`, zero body bytes** (verified by raw-socket probe). `BackendCount()` returns 1 and the backend is genuinely used. Do not "simplify" the fixture to a 200-with-body.

- **D-TAP-DIRMOUNT (NEW at the PLAN)** — `file_per_tap` writes one file per stream with an unpredictable `<trace_id>` name, so the reference (in Docker) needs a **DIRECTORY** bind-mount. `fixture.HostMount` is `{HostPath, ContainerPath}` and the runner pre-creates `HostPath` as a **FILE** (`O_WRONLY` on a dir ⇒ `EISDIR`).
