## Architecture as PLAN'd (43.2a — ADR-0253; SUPERSEDES ADR-0056)

**The two admission dimensions:** (1) the 43.1 conn-creation permit (`connPool`, `max_connections`) gates opening a NEW conn; (2) the NEW H2 stream slot (`http2_protocol_options.max_concurrent_streams`, cap C) gates multiplexing onto an EXISTING conn. A request opens a new conn only when every existing conn is stream-saturated; it PENDS only when BOTH are exhausted. **THE load-bearing SPEC finding (AMEND-H2-1, the §11 live probe, USER-CONFIRMED, REVERSED the BRAINSTORM):** the reference's multi-conn growth keys off the cluster's OWN `max_concurrent_streams` (the LOCAL cap), opening EXACTLY `ceil(K/C)` conns — deterministic, cross-side EXACT (NOT the 43.1 soft-breaker robust prong; `reference_h2_pool_local_cap_driven`). **Design:** a NEW `internal/cluster/h2pool.go` — `c.h2Pool map[string][]*pooledH2Conn` (keyed by `ep.Addr()`, guarded by `h2PoolMu`) + a SEPARATE per-endpoint stream-aware pending queue (woken on stream-free OR conn-close; the 43.1 wake PATTERN — `sync.Mutex` + FIFO + buffered-cap-1 — but a DISTINCT structure from `connPool.waiters`; bounded by `max_pending_requests`). The crux: H2 requests use the NEW `tryAcquireConnSlot` (non-blocking) + the H2 queue, NEVER `connPool.waiters`; all H2 wakeups route through `h2PromoteLocked` (called after every capacity-freeing event). Conn-Close is always pool-driven (the codec's readLoop cancels `cc.ctx` but never closes the underlying conn — `client.go:222-224`). **Stats (AMEND-H2-2):** add `upstream_cx_http2_total` + `http2.streams_active` (useH2-gated; **1183 → 1185**), NO `_http2_active`.
