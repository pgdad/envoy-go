# Phase 52 Brainstorm — `locality-weighted` LB (SIXTH Load-balancing-family row; the family STAYS OPEN; the FIRST LB construct to consume per-host HEALTH state)

**Status:** brainstorm complete (lifecycle-state 0 → 1). This document captures the design decisions reached during the brainstorm session for phase 52 (`load-balancer-locality-weighted`), the **SIXTH Load-balancing-family row**. Phase 52 lands `Cluster.common_lb_config.locality_weighted_lb_config` (`envoy.config.cluster.v3`) — weighting traffic across Envoy localities (region/zone/sub_zone) by each locality's configured `load_balancing_weight`, degraded by that locality's live health state. Unlike phase 38's `subsetLB` (a wrapper triggered by per-ROUTE `metadata_match`, extending the `loadBalancer.Pick` seam with a new pick-input), locality-weighted LB is a wrapper triggered ENTIRELY by CLUSTER-static config (`common_lb_config` presence + `LocalityLbEndpoints.locality`/`load_balancing_weight`) — it needs **zero** new `Pick` parameters, delegating the EXISTING `(hashKey, hasHash, match, hasMatch)` straight through to a locality's child unchanged. It is, however, the family's **FIRST construct to consume the phase-39/40 per-host health state inside the LB pick itself** (not just the existing panic/available filter each leaf policy already does) — a locality's effective weight must degrade as its hosts go unhealthy, which is the load-bearing novel mechanism this phase adds (the four prior post-round-robin policies — least_request/random/ring_hash/maglev — and subset all treat health only as a binary include/exclude filter over a flat set; none of them WEIGHTS by a health-derived scalar).

The load-bearing facts that shape this brainstorm:

- **`Endpoint` gains its SECOND dimension beyond metadata.** Today `internal/cluster/cluster.go`'s `Endpoint` is `{Host, Port, Metadata}` (`Metadata` landed at phase 38/ADR-0240); `extractEndpoints` (`manager.go:771-795`) flattens every `*endpointv3.LocalityLbEndpoints` group into the flat `[]Endpoint`, and the flatten function's own error message ("zero endpoints across all locality groups") proves the locality-GROUP boundary is visible only at error-reporting time — `group.GetLocality()` and `group.GetLoadBalancingWeight()` are never called. Locality-weighted LB requires both, captured per-endpoint (mirroring the phase-38 `Metadata` precedent exactly): a `Locality` identity (region/zone/sub_zone) plus the group's configured `LocalityWeight`.
- **NO new `Pick` parameter — this is the FAMILY'S FIRST zero-seam-change wrapper.** subsetLB (phase 38) needed the seam to grow a new `(match, hasMatch)` pick-input because the subset match is a per-ROUTE, per-REQUEST value that must reach the cluster's `Pick` call. Locality selection needs no such per-request input — the wrapper resolves a locality PURELY from its own per-cluster state (each locality's configured weight + its CURRENT live health fraction, both cluster-scoped) at every `Pick` call, then delegates `child.Pick(hashKey, hasHash, match, hasMatch)` UNCHANGED to the chosen locality's child (passing the existing hash-key/subset-match straight through, exactly as `subsetLB.Pick` already passes them to ITS child — proving the interface already generalizes to wrapper-of-wrapper delegation with zero further widening). The exported `Cluster` surface and the `loadBalancer` interface stay byte-stable with NO signature change at all — a STRICTER form of "reuse" than phase-35's random (which reused the interface but was itself a leaf) or phase-37's maglev (reused the ADR-0235 hash-key seam but is still a leaf): phase 52 reuses the FULL wrapper-delegation shape phase 38 established, with a wrapper of its own.
- **The FIRST LB construct that consumes per-host health as a continuous WEIGHT, not a binary filter.** Every existing policy (`roundRobin`/`randomLB`/`leastRequest`/`maglevLB`/`ringHashLB`, and `subsetLB`'s children) treats a host as either `available()` (counted) or not (skipped) — health is a pure include/exclude gate (`internal/cluster/health.go:138`). Reference Envoy's locality-weighted algorithm instead SCALES each locality's configured weight by that locality's healthy-host fraction (further adjusted by an "overprovisioning factor", default 140%, that lets a locality stay at full weight until a meaningful fraction of its hosts are down) before drawing a weighted-random locality. This is a materially different consumption of the SAME `clusterHealth` state (`internal/cluster/health.go:71-93`) built by phase 39/40 — no new health-tracking machinery, just a new READ pattern over it (per-locality aggregation instead of per-host).
- **`healthy_panic_threshold` composes at the CLUSTER level, above locality weighting.** `parsePanicThreshold`/`inPanic` (`health.go:429-437`, `:165-171`) already computes a CLUSTER-wide (not per-locality) healthy fraction and, when it drops below the configured threshold (default 50%), every existing leaf policy ignores health entirely and picks over the FULL endpoint set. Reference Envoy's locality-weighted LB does the identical thing: on cluster-wide panic, locality weighting is bypassed and the pick degrades to a flat, health-ignoring draw over ALL endpoints (mirroring exactly what `roundRobin.Pick`'s existing panic branch already does at `loadbalancer.go:44-66`, generalized: a `localityWeightedLB` in panic mode delegates to a plain-flat child built once over the full endpoint set at construction, bypassing per-locality selection). No new panic concept — the EXISTING cluster-wide `inPanic` gate is reused verbatim, just consulted one layer higher (by the locality wrapper, before it ever weighs a locality) rather than inside each leaf.
- **A oneof sibling must be explicitly handled, not silently swept in.** `Cluster.CommonLbConfig`'s `LocalityConfigSpecifier` is a `oneof` of `zone_aware_lb_config` (field 2) and `locality_weighted_lb_config` (field 3) — TODAY, `manager.go` reads ONLY `common_lb_config.healthy_panic_threshold` (`health.go:432`); neither oneof arm is consumed, so `zone_aware_lb_config` is currently silently ignored (parse-accepted, inert). The moment this phase lifts `locality_weighted_lb_config` out of that silent-ignore set, `zone_aware_lb_config` — a DIFFERENT algorithm this phase explicitly does NOT build (§2.1) — must not be allowed to silently fall through to "no locality behavior" as if it had been consciously declined; per this project's established discipline for exactly this shape (a sibling oneof arm left in silent-ignore after one arm is lifted out — the phase-44.1 `TcpGrpcAccessLogConfig` finding), phase 52 adds an EXPLICIT reject arm for a configured `zone_aware_lb_config` rather than leaving it swept into the same silent-ignore bucket it shared with `locality_weighted_lb_config` before this phase.

### 1.1 What phase 52 delivers as a self-contained whole (envelope: a single flat row, no pre-authorized split)

Phase 52 lands locality weighting as one self-contained whole:

1. **The `localityWeightedLB` wrapper** (ADR-0269) — built ONCE at cluster construction when `common_lb_config.locality_weighted_lb_config` is present (immutable topology thereafter — locality membership and each locality's configured weight never change post-boot, matching the project's static-bootstrap-only model; no dynamic EDS churn exists project-wide). For each distinct `Locality` identity among the cluster's endpoints, build one **child `loadBalancer`** via the EXISTING policy factory (`buildLeafLB`) over that locality's endpoint sub-slice (the `subsetLB` shape exactly — §2.3). At `Pick`, IF the cluster is in cluster-wide panic (the EXISTING `clusterHealth.inPanic` gate, computed over ALL endpoints — §2.5), delegate to a pre-built flat child spanning every endpoint (bypassing locality weighting entirely, mirroring what every leaf policy's OWN panic branch already does); OTHERWISE compute each locality's EFFECTIVE weight (configured weight scaled by that locality's live healthy-fraction, exact formula pinned at SPEC — §2.4/D-LW3), weighted-random-draw a locality, and delegate `child.Pick(hashKey, hasHash, match, hasMatch)` UNCHANGED. REUSES the ADR-0232 release half + the ADR-0235/0239 hash-key/subset-match pass-through (both flow straight through to the chosen locality's child, exactly as they already flow through `subsetLB`'s children).
2. **The `Endpoint` locality dimension + capture** — `Endpoint` grows a `Locality` field (a small `{Region, Zone, SubZone string}` identity — zero value = the unset/default locality, itself a valid single group) and a `LocalityWeight uint32` field (the group's `load_balancing_weight`; the reference requires ALL localities in a `ClusterLoadAssignment` to either ALL set it or ALL leave it unset — mixed presence is a reject, pinned at SPEC D-LW2). `extractEndpoints` (`manager.go:771-795`) captures `group.GetLocality()` (region/zone/sub_zone) and `group.GetLoadBalancingWeight().GetValue()` per locality GROUP (not per individual `LbEndpoint`), stamping every endpoint in that group with the same `Locality`/`LocalityWeight` pair. `group.GetPriority()` stays discarded (couples to the separate "priority load balancing" candidate, exactly as subset left it — phase-38 §8/§9).
3. **Manager acceptance + config parse** — `internal/cluster/manager.go` parses `Cluster.CommonLbConfig.LocalityConfigSpecifier`: a `locality_weighted_lb_config` arm (the empty marker message — its mere PRESENCE toggles the mode; no data fields of its own, §2.1) WRAPS whatever child the existing `lb_policy` switch produced (a SECOND wrap-after-switch site, alongside the phase-38 `lb_subset_config` wrap at `manager.go:461-465`) in a `localityWeightedLB`; a `zone_aware_lb_config` arm is EXPLICITLY REJECTED (§2.6/D-LW1, the sibling-reject discipline); BOTH `lb_subset_config` AND `locality_weighted_lb_config` configured on the same cluster is EXPLICITLY REJECTED (§2.2/D-LW1, the deferred-composition boundary). PGV/build rejects pinned at SPEC (D-LW1/D-LW2).
4. **The panic-mode interaction** (§2.5) — a pre-built flat child (spanning ALL endpoints, built once via the factory alongside the per-locality children) that `Pick` delegates to WHEN `clusterHealth.inPanic` fires over the whole cluster — the EXISTING cluster-wide panic gate consulted one layer higher than today (by the wrapper, before per-locality weighing), not a new panic concept.
5. **The differential fixture `0095-lb-locality-weighted`** — TWO localities of backends with distinct configured `load_balancing_weight` (e.g. 2:1) on BOTH sides. Arm (a): all-healthy — assert per-locality request share matches the weight ratio within a banded statistical margin (~4-5σ, `reference_differential_band_sigma_margin`). Arm (b): health-degradation — fail active health checks on a subset of one locality's hosts (reusing the phase-39 poll-to-convergence pattern, `reference_health_check_propagation_warmup`), then assert request share shifts away from that locality proportionally to its degraded effective weight. Cross-side byte-equivalence + a cross-side `StatsAsserter` — §6.
6. **The BEHAVIOR_CONTRACT bundle** + the STATE/ROADMAP advance + the row-52 `in-progress → done` flip at the IMPL six-gate (a flat family row — NO parent rollup per ADR-0106, and NO pre-authorized split — §1.4).

**Anticipated ADRs:** ADR-0269 ONLY (the locality-weighted policy + the `Endpoint.Locality`/`LocalityWeight` dimension + the panic interaction + the `zone_aware_lb_config` sibling-reject) — a SINGLE-ADR phase (§7), the phase-35/37 "reuse" shape, since §1.7 establishes there is no seam BUILD here. DECISIONS tail STAYS **ADR-0268** at this brainstorm; next-free **ADR-0269**.

### 2.2 Subset-LB composition: kept independent; BOTH-configured is an explicit reject *(Q2 → self-contained scope boundary)*

**Decision:** phase 52 does NOT wire `LbSubsetConfig.locality_weight_aware`/`scale_locality_weight` (subset's own locality-interaction flags, deferred at phase 38 — "couples to locality-weighted LB (no locality weights yet)"). If a cluster configures BOTH `lb_subset_config` AND `common_lb_config.locality_weighted_lb_config`, phase 52 REJECTS the combination at cluster build (a recorded envoy-go-strict departure — the reference WOULD compose them via `locality_weight_aware`; exact reject wording pinned at SPEC, D-LW1) rather than picking an undocumented precedence between the two wrap-after-switch sites (`manager.go:461-465` for subset, the new site for locality-weighting).

**Rationale:** composing them faithfully means each subset's children ALSO honor locality weight within the subset (a THIRD layer of wrapper nesting, subset → locality → leaf) — a real algorithm and architecture question (does a subset's per-subset endpoint sub-slice retain enough per-locality granularity to weight meaningfully? does the subset fallback child ALSO need locality-awareness?) that deserves its own brainstorm dialogue rather than an assumption baked in here. Rejecting the combination is honest about the gap (an explicit, tested reject) rather than silently picking one wrapper and ignoring the other's config.

### 2.3 Child-policy scope: mirror subsetLB — ALL five children via factory reuse *(Q3 → ADR-0269)*

**Decision:** `localityWeightedLB` is a `loadBalancer` wrapper that, at build time, groups the cluster's endpoints by `Locality` identity and builds a **child `loadBalancer` per locality via the existing policy factory** (`buildLeafLB`) over that locality's endpoint sub-slice — ALL five policies (round_robin/least_request/random/ring_hash/maglev) supported uniformly, exactly the `subsetLB` shape (`subset.go:158-205`). At `Pick` (outside panic — §2.5), weighted-random-select a locality by effective weight, then delegate `child.Pick(hashKey, hasHash, match, hasMatch)` unchanged — the hashKey/match pass straight through (a ring_hash/maglev child inside a locality routes by key WITHIN that locality; a subset match — recall §2.2, mutually exclusive with this wrapper — never reaches here in practice, but the parameter still passes through harmlessly, matching subsetLB's own unconditional forwarding).

**Rationale:** identical to phase 38's §2.2 rationale — factory reuse makes "all children" barely harder than one (the per-locality child build is the existing build over a sub-slice), it is the most faithful shape (the reference balances WITHIN a locality by the cluster's configured `lb_policy`), and it keeps the exported `Cluster` surface byte-stable. No Approach-B/C alternatives were seriously considered given the direct, already-validated subsetLB precedent.

### 2.4 Effective-weight computation: configured weight × live per-locality health fraction *(self-answered envelope; exact formula SPEC-BLOCKING, D-LW3)*

**Decision:** each locality's EFFECTIVE weight for the weighted-random draw is its configured `LocalityWeight` (§2.1 — a per-locality-group `uint32`, defaulting to `1` when the reference's own default-weight rule applies, D-LW2 pins the exact default/mixed-presence rule) SCALED by that locality's live healthy-host fraction, reusing the EXISTING `clusterHealth.available(ep)` per-host gate (`health.go:138`) aggregated over just that locality's endpoints — NOT the reference's exact internal formula assumed here; **D-LW3 is SPEC-BLOCKING** and executes a live probe against the reference (varying a locality's healthy-host count under a fixed configured weight, reading the resulting request-share ratio) to pin the precise degradation curve, INCLUDING whether the reference's default 140% overprovisioning factor (`HostSet::EffectiveLocalityWeight` in upstream C++ — kept at full weight until healthy fraction drops below ~1/1.4 ≈ 71%, then scaling linearly to zero) applies, and whether `Cluster.CommonLbConfig` exposes any way to configure it (the reference's `LocalityLbEndpoints` proto has no top-level override for this — checked in the same module-cache pass; if a knob exists it was missed and D-LW3 will surface it). envoy-go REPRODUCES whatever the live probe finds bit-for-bit — no simplified/approximated formula is acceptable per the project's byte-stability discipline for LB weighting phases (the phase-40.1 percent-cap cross-multiply lesson: exact-formula fidelity, not an approximation that happens to look similar).

**Rationale:** this is the phase's single most load-bearing empirical unknown — every prior LB phase's weighting-adjacent nuance (ring_hash's ring-size PGV cap, maglev's primality requirement, subset's fallback-policy trichotomy) was pinned via a live probe, never assumed; the same discipline applies here, amplified because this phase introduces the family's first CONTINUOUS (not discrete/enum) weighting input.

### 2.5 Panic-mode interaction: reuse the EXISTING cluster-wide `inPanic` gate, one layer higher *(self-answered; confirmed at SPEC, D-LW4)*

**Decision:** `localityWeightedLB` builds, alongside its per-locality children, ONE additional flat child (via the SAME factory, over the FULL unweighted endpoint set) at construction. At `Pick`, it FIRST checks `clusterHealth.inPanic(allEndpoints)` (the EXISTING cluster-wide gate every leaf policy already consults internally, `health.go:165-171`) — if the cluster is in panic, delegate directly to the flat child (bypassing per-locality weighting AND the per-locality health degradation of §2.4 entirely, since panic mode already means "ignore health, use everyone"); otherwise proceed to the §2.3/§2.4 weighted-locality draw. D-LW4 confirms this against the reference's actual panic-interaction behavior (an untested assumption otherwise) — specifically whether the reference's `PanicModeThreshold`, when tripped, discards locality weighting ENTIRELY (this brainstorm's assumption) or degrades to some intermediate behavior.

**Rationale:** `inPanic` is ALREADY a cluster-wide (not per-locality) computation (`health.go:165-171` operates over the caller-supplied endpoint slice, and every existing leaf policy calls it with its OWN full slice); reusing it verbatim at the wrapper layer, rather than inventing a NEW panic concept, is the minimal-surface-area choice and matches the "reuse over rebuild" thread running through §1.7.

### 2.6 The `zone_aware_lb_config` sibling: EXPLICIT reject, not silent fall-through *(self-answered; the phase-44.1 lesson applied; D-LW1)*

**Decision:** a cluster configuring `common_lb_config.zone_aware_lb_config` (the sibling `LocalityConfigSpecifier` oneof arm this phase does NOT build) is REJECTED at cluster build with a clear error (exact wording pinned at SPEC, D-LW1), rather than silently falling through to today's "no locality behavior" no-op (which `zone_aware_lb_config` currently, accidentally, already gets — since NEITHER oneof arm is read today).

**Rationale:** this project has already been bitten by exactly this shape — lifting ONE type-URL/oneof-arm out of a shared silent-ignore set without an explicit reject for its sibling(s) lets the to-be-rejected sibling slip through unnoticed (the phase-44.1 `TcpGrpcAccessLogConfig` finding, caught at final review). Before phase 52, both `zone_aware_lb_config` and `locality_weighted_lb_config` shared the SAME silent-ignore fate (nobody read either); after phase 52 lifts `locality_weighted_lb_config` into real behavior, leaving `zone_aware_lb_config` in silent-ignore would be indistinguishable from "we decided zone-aware traffic shaping doesn't apply here" when in fact it is simply unimplemented — an explicit reject makes the gap visible and testable (a unit-level reject-arm test, the phase-38 `lb_subset_config`-reject-arm precedent).

### 2.7 Differential strategy: static weight-ratio arm + health-degradation shift arm *(Q4 → fixture envelope §6)*

**Decision:** the fixture `0095-lb-locality-weighted` configures TWO localities of HTTP backends with distinct `load_balancing_weight` (e.g. a 2:1 ratio) on BOTH sides. **Arm (a) — static ratio:** with all hosts healthy, assert per-locality request share matches the configured weight ratio within a banded statistical margin (`reference_differential_band_sigma_margin`, ~4-5σ over ≥20 runs — the phase-35 `0060` re-tuning lesson). **Arm (b) — health-degradation shift:** configure active health checks on the cluster (reusing the phase-39 substrate), fail health checks on a controlled subset of one locality's hosts (a responder that starts returning non-2xx to the health-check path, the phase-39/40 precedent), poll `/stats` to convergence (`reference_health_check_propagation_warmup` — poll-the-gauge + a transient-503-tolerant warmup, NOT a sleep), THEN re-measure request share and assert it shifted away from the degraded locality proportionally to its now-reduced effective weight. Cross-side byte-equivalence + a cross-side `StatsAsserter` (any `lb_locality_*`-style stats the reference exposes, or the existing `membership_healthy`/`upstream_rq_total` cross-equal if D-LW5 finds no dedicated locality stat namespace). Every live assertion proven via a deliberate-break with `-count=1` (`reference_differential_break_protocol_count1`) — e.g. "drop the locality identity from one group so both merge into the default locality" defeats arm (a); "skip the health-degradation step" defeats arm (b).

**Rationale:** subset LB's proof was a pure SET-membership property (deterministic, static); locality-weighted LB's defining property is STATISTICAL (a weight RATIO, not a hard partition) AND involves LIVE STATE CHANGE (health degrading mid-test) — the two arms together are the minimum needed to distinguish "weights are honored" from "weights degrade correctly under partial locality failure," the actual novel mechanism this phase adds (§ intro). D-LW6 pins the exact route/endpoint topology, the flake-free protocol, and the `-run 'TestDifferential/0095'` selector (`reference_differential_run_selector`).

### 2.8 Stat surface: anticipated SMALL delta, exact set a SPEC live-probe pin *(self-answered envelope; D-LW5)*

**Decision:** anticipated stat surface delta is SMALL (0 to +2) — unlike subset's `lb_subsets_*` group (ring_hash/maglev/subset each landed policy-describing gauges/counters), locality-weighted LB's algorithm is largely an internal WEIGHTING computation with no obviously-named dedicated stat group recalled from the reference's `ClusterStats`; **D-LW5 is SPEC-BLOCKING** and live-scrapes the reference's `/stats` under a configured `locality_weighted_lb_config` cluster to confirm whether any `cluster.<name>.locality.*` or similar namespace exists (envoy-go mirrors it if so) or whether the EXISTING `membership_total`/`membership_healthy` gauges (`reference_membership_total_vs_healthy_gauge`) are the only cross-side-visible signal (in which case the `0095` `StatsAsserter` relies on `upstream_rq_total` request-share counting instead of a locality-specific stat).

**Rationale:** every prior LB phase's stat-surface claim was verified (not assumed) against the live reference (subset's anticipated ~+4 `lb_subsets_*` WAS confirmed at its SPEC); this phase makes no confident a-priori claim beyond "small," deferring the exact number to the same live-probe discipline.
