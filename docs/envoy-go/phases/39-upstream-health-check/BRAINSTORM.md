# Phase 39 Brainstorm — active health checks (the FIRST Upstream-robustness-family row; the family's keystone — the host health-state dimension that unblocks the 3 health-gated LB candidates)

**Status:** brainstorm complete (lifecycle-state 0 → 1). This document captures the design decisions reached during the brainstorm session for phase 39 (`upstream-health-check`), the **FIRST Upstream-robustness-family row** and the project's first NEW feature family since the §9 Network-filters family closed at phase 33. Phase 39 lands `Cluster.health_checks` (`[]core.config.core.v3.HealthCheck`, proto field 8) — **active** upstream health checking (periodic probes that mark hosts healthy/unhealthy) over HTTP + TCP + gRPC checkers, the per-host **health-state dimension** the project has never had, and the health-aware LB pick that makes all six LB constructs route only to healthy hosts (with a panic-threshold fallback).

Phase 39 is therefore the family **keystone**: it introduces the host health-state primitive that (i) the 3 health-gated Load-balancing-family candidates {locality-weighted LB, priority load balancing, panic thresholds} require to be non-vacuous, and (ii) the sibling Upstream-robustness rows {outlier detection, circuit breakers, retries + hedging, connection pooling} compose with. Until phase 39, every LB construct picks over the full static endpoint set unconditionally — `Endpoint` (`internal/cluster/cluster.go:33`) carries `{Host, Port, Metadata}` and NO health field; `extractEndpoints` (`manager.go:557`) discards the EDS `health_status`; there is no background runtime at all (no goroutines, no timers in `internal/cluster`).

The load-bearing facts that shape this brainstorm:

- **`Cluster.health_checks` is a list of `core.v3.HealthCheck` (proto field 8), each a oneof over three checkers.** Verified in the EXISTING core `/envoy v1.32.4` dep (`~/go/pkg/mod/github.com/envoyproxy/go-control-plane/envoy@v1.32.4/config/core/v3/health_check.pb.go`): `HealthCheck` carries the timing/threshold envelope (`timeout`, `interval`, `initial_jitter`/`interval_jitter`/`interval_jitter_percent`, `unhealthy_threshold`, `healthy_threshold`, `no_traffic_interval`/`unhealthy_interval`/`healthy_edge_interval`/…, `alt_port`, `reuse_connection`, `event_log*`, `tls_options`) + a oneof `HealthChecker` ∈ {`HealthCheck_HttpHealthCheck`, `HealthCheck_TcpHealthCheck`, `HealthCheck_GrpcHealthCheck`}. `HttpHealthCheck`: `host`, `path`, `send`/`receive` payloads, `expected_statuses`/`retriable_statuses` (`[]Int64Range`), `codec_client_type`, `method`, request-header mutation. `TcpHealthCheck`: `send`/`receive` payloads, `proxy_protocol_config`. `GrpcHealthCheck`: `service_name`, `authority`, `initial_metadata`. ZERO new go.mod MODULE for HTTP/TCP (the core dep carries `HealthCheck` + the H1/H2 upstream client already exists); the gRPC `grpc.health.v1` message is available transitively via `google.golang.org/grpc/health/grpc_health_v1` (already in the module graph) — whether to take it as a DIRECT dep or hand-roll the trivial `HealthCheckRequest{service}`/`HealthCheckResponse{status}` message is a 39.2 pin (D-HC8).
- **The host health-state dimension is the NEW primitive — and it is CLUSTER state, not per-request, not per-`Endpoint`-value.** `Endpoint` is an immutable value type passed by copy through the dial/pick funnels; health mutates over time. So health lives on the `Cluster` as a per-host registry (`map[string]*hostHealth` keyed by `Endpoint.Addr()`), each entry holding atomic `healthy` + `consecutiveFailures`/`consecutiveSuccesses`. This is distinct in kind from the two existing pick-inputs (the ADR-0235 request-derived hash key, the ADR-0239 route-static subset match) — both per-request ctx carries; health is shared cluster state injected at LB build.
- **A NEW cluster-level background runtime — the project's FIRST.** Active health checking is timer-driven: per cluster × per configured `health_check`, a background goroutine probes every host every `interval` with a per-probe `timeout`, applies the consecutive-success/failure thresholds, flips host state, and increments stats. `internal/cluster` has no goroutines/timers today; phase 39 adds a runtime with a lifecycle — started post-`Freeze` at boot (a new `Manager.StartHealthChecks(ctx)` from `cmd/envoy-go/main.go`), cancelled + drained at shutdown (wired into the existing `Manager.Drain()`, `manager.go:214`). This is the project's first long-lived per-cluster subsystem (the network-filter upstream-pool seam, ADR-0230, is request-driven, not timer-driven).
- **The six LB constructs become health-aware at the pick seam (Approach A — pick-time filter + panic).** LB internals stay built once over the full host set; each `Pick` consults the cluster's health view, skips unhealthy hosts (round_robin: advance index; least_request: choose among healthy; ring_hash/maglev: walk the ring/table to the next healthy host — **preserving key→host stability**, exactly upstream's behavior), and falls back to picking from ALL hosts when the healthy fraction drops below the panic threshold (`Cluster.common_lb_config.healthy_panic_threshold`, a `Percent`, default 50% — verified at `cluster.pb.go:2655`; D-HC5). This is a shared mechanism consulted by all six LBs — a behavior-neutral extension when no host is unhealthy (every existing fixture stays byte-identical). It is NOT a per-request `Pick` parameter (health is cluster state) — the health view is injected at LB build.
- **Determinism is the novel differential risk — solved by poll-to-convergence, not fixed sleeps.** Active HC is asynchronous: a dead host is marked unhealthy only after `unhealthy_threshold` consecutive failed probes (≥ `interval × threshold` wall-clock). The `0066` driver POLLS the admin `/stats` endpoint (`internal/admin/admin.go` — `/stats` + `/stats/prometheus` exist) for the health/membership counters until BOTH sides converge, THEN runs the load phase and asserts 100% of traffic on the live host(s). No `time.Sleep` race.

### 2.2 Checker-roster scope: HTTP (39.1) + TCP + gRPC (39.2) *(Q1 → the by-codec split)*

**Decision:** the full HTTP + TCP + gRPC checker roster, split by codec: 39.1 = the HTTP checker (with the full keystone substrate); 39.2 = the TCP + gRPC checkers (reusing the substrate). §1.4.

**Rationale:** the user chose the comprehensive roster (Q1=C) over an HTTP-only keystone. The three codecs are independent probe mechanisms over the same health-state + runtime + LB substrate, so the substrate lands once with HTTP (the project's native protocol — the H1/H2 client + the HTTP differential backends already exist), and TCP (connect / payload-match) + gRPC (`grpc.health.v1` over H2) follow as substrate-reusing legs. HTTP-first minimizes the codec surface in flight while the keystone (the new runtime + the six-LB surgery + the new state dimension — the load-bearing, highest-risk work) is proven.

### 2.3 Health-aware LB architecture: pick-time filter + panic fallback, build-time-injected health view *(Q2 → ADR-0243)*

**Decision (Approach A):** each of the six LB constructs becomes health-aware by consulting a build-time-injected health view at `Pick`: pick a candidate by the policy's normal rule; if unhealthy, advance (round_robin: next index; least_request: choose the least-loaded HEALTHY host; random: re-draw; ring_hash/maglev: walk the ring/table to the next healthy host); if the healthy fraction < `healthy_panic_threshold`, enter panic mode and pick from ALL hosts (ignore health). The LB internals stay built once over the full host set (no rebuild on health flips).

**Rationale:** Approach A matches Envoy's actual semantics (the LB operates over the host set partitioned into healthy/unhealthy with a panic threshold) and PRESERVES ring_hash/maglev key→host stability (a key maps to the same host; walk-to-next-healthy is exactly upstream's degradation, and it returns to the original host when it recovers — no ring rebuild, no key remap). Rejected: Approach B (rebuild each LB's structure on every health flip — O(N) or O(ring) rebuilds, races with concurrent picks under the ADR-0024 per-cluster state scope, and breaks ring_hash/maglev key stability because a rebuilt ring/table over a different host subset remaps every key) and Approach C (a subsetLB-shaped health-filter wrapper — since health is dynamic nothing precomputes, so the wrapper degenerates to A's re-picking, and a wrapper over ring_hash can't preserve key determinism without reaching into the child). The health view is injected at BUILD (not threaded through `Pick`) because health is cluster state, not a per-request value (§1.7) — keeping the `Pick` signature byte-stable.

**The load-bearing design point (behavior-neutrality):** when every host is healthy (the state of EVERY existing fixture and conformance config), the health-aware pick returns the SAME host the unsubsetted policy would — the skip loop never fires and panic mode never triggers. So the full 67-dir differential + h2spec 53/53 + proxy-wasm 10/10 stay byte-identical (the real guard); only the new `0066` fixture (with a configured dead host) exercises the filter. D-HC6 confirms the per-construct skip + panic semantics against the reference.

### 2.4 The checker-runtime lifecycle: started post-Freeze, drained at shutdown *(self-answered; pinned at SPEC, D-HC4)*

**Decision:** the checker goroutines start AFTER the manager `Freeze` (so the host set + stats are immutable/allocated) via a new `Manager.StartHealthChecks(ctx context.Context)` called from `cmd/envoy-go/main.go` at boot (after the listeners are up, before/around the drain-manager wiring); each goroutine selects on `ctx.Done()` and a per-`interval` ticker; `Manager.Drain()` (`manager.go:214`) cancels the root context and waits (a `sync.WaitGroup`) for the goroutines to exit. Test code that builds a `Manager` without calling `StartHealthChecks` gets NO checkers (every existing unit/differential test is unaffected unless it opts in).

**Rationale:** the post-Freeze start keeps the build path (which every existing test drives) free of background goroutines — the runtime is opt-in at the boot path only. Draining the goroutines at `Drain()` reuses the existing graceful-shutdown hook (phase 08) rather than adding a parallel lifecycle. D-HC4 confirms the reference's checker scheduling (immediate first check vs first-check-after-interval; the `no_traffic_interval` interaction; whether the first check blocks readiness) so the `0066` poll-to-converge timing is correct.

### 2.5 Differential strategy: poll-to-convergence then steady-state routing *(Q-differential → fixture envelope §6)*

**Decision:** the fixture `0066-health-check-http` configures, on BOTH sides, a cluster with `health_checks: [{http_health_check{path}, interval: <short>, timeout: <short>, unhealthy_threshold: <low>}]` over endpoints = {a LIVE HTTP backend that 200s the probe path, a DEAD endpoint (an unbound `127.0.0.x:port` → connect-refused)}; the HTTP listener routes to that cluster. The driver: (1) **poll phase** — scrape `/stats` on BOTH sides until the dead host is marked unhealthy (`membership_healthy` == liveCount AND `health_check.failure` ≥ threshold) on both, with a generous deadline; (2) **load phase** — send N requests; assert 100% land on the LIVE backend (the dead host is filtered out) on BOTH sides — the health-filter signature (the unfiltered policy would send ~half to the dead host → connection failures / 503s); (3) cross-side `health_check.*` + `membership_*` stat parity + `upstream_rq_total` cross-equal. Every live assertion proven via a `-count=1` deliberate-break (`reference_differential_break_protocol_count1`): drop the health filter → traffic leaks to the dead host → the 100%-live assertion fails; invert the threshold convergence → the poll never completes.

**Rationale:** active HC's interesting property is that an unreachable host is detected and removed from rotation. The poll-to-convergence phase eliminates the timing race (no fixed `time.Sleep` — the load phase starts only after BOTH sides agree the host is unhealthy), making the steady-state routing assertion deterministic and cross-side. The DEAD-host-via-unbound-address design needs NO new BackendKind (the live host reuses the existing HTTP backend; the dead host is just an address with no listener). A flapping/recovery arm (a host that fails then recovers, exercising the `healthy_threshold` return path) is a candidate second arm (D-HC7) — it needs a controllable backend (a possible +1 BackendKind) and is deferred to a second `0066` arm or to 39.2 if it complicates the keystone. The maglev/ring_hash modular-invariant convention does NOT apply (this is a membership property, not a hash-stability property). D-HC7 pins the exact topology, the poll predicate, the deadline, and the ≥20-run flake-free protocol.

### 2.6 Deferred-policy posture: a NEW reject surface (`health_checks` validation) *(self-answered; pinned at SPEC, D-HC2)*

The deferred TCP/gRPC checkers' disposition in 39.1 (parse-accept-behavior-deferred vs boot-reject — the kafka-31 vs thrift-33 precedents) is a D-HC2 sub-pin.

**Rationale:** the byte-stable-reject discipline (ADR-0080) governs the new surface. Enumerating the reject set at SPEC keeps the blast radius known up front, never discovered at the six-gate. This is NOT a retarget of the lb_policy reject text (that lineage ended at phase 38) — it is a wholly new validation surface for the `health_checks` field.
