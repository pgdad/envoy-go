# Phase 42.2 Brainstorm — hedging (the SECOND leg of the FOURTH Upstream-robustness-family row; CONCURRENT attempts + the project's FIRST per-attempt timeout — layered over the 42.1 retry substrate)

**Status:** brainstorm complete (lifecycle-state 4 → 4; row 42 stays `in-progress`). This document captures the design decisions reached during the brainstorm session for phase **42.2** (`hedging`), the second leg of the FOURTH Upstream-robustness-family row (row 42). Phase 42.1 (`9e5c6a7d` PLAN → `4a255b25` IMPL squash, ADR-0249) landed the SEQUENTIAL retry loop — a `retryExecutorH1`/`retryExecutorH2` wrapping the single-attempt driver, classifying the buffered `ActionResponse.Status` against a parsed `retry_on` bitset, replaying the buffered body, sleeping an exponential backoff, and re-attempting under the activated phase-41 `retry_budget`. Phase 42.2 layers **CONCURRENCY** + the project's **FIRST per-attempt timeout** on top: `RetryPolicy.per_try_timeout` (field 3 — a per-attempt deadline) plus `RouteAction.hedge_policy` (`route.v3.HedgePolicy`, field 27; `VirtualHost.hedge_policy` field 17 the route-absent fallback) — racing a second attempt before the first completes and taking the first acceptable response.

Where phase 42.1 RE-ATTEMPTS a failed request sequentially (one attempt at a time, on a settled retriable outcome), phase 42.2 HEDGES — it bounds each attempt with `per_try_timeout` and, on `hedge_on_per_try_timeout`, leaves the slow attempt in flight while launching a concurrent hedge, returning whichever completes acceptably first. It is the first envoy-go feature with MORE THAN ONE upstream attempt in flight per request, and the first per-attempt deadline.

The load-bearing facts that shape this brainstorm:

- **THE #not-implemented-hide: finding — `HedgePolicy`'s fan-out fields are NOT wired in the reference; only `hedge_on_per_try_timeout` is.** `route.v3.HedgePolicy` (`config/route/v3/route_components.pb.go:2827`) has THREE fields: `initial_requests` (field 1, `*wrapperspb.UInt32Value`, default 1, PGV `gte:1` — proto-static in the rawDesc) and `additional_request_chance` (field 2, `*type.v3.FractionalPercent`, default 0% — nil ⇒ no additional request) are BOTH annotated **`[#not-implemented-hide:]`** in the upstream proto — they exist in the API but are NOT implemented by the reference Envoy binary. Only `hedge_on_per_try_timeout` (field 3, `bool`, default false) is wired: per its proto comment, when the per-try timeout is hit, "a retry will be issued without resetting the original request, leaving multiple upstream requests in flight. The first request to complete successfully will be the one returned to the caller." So the reference's ONLY hedging mechanism is per-try-timeout-driven (NOT a parallel fan-out), and it works **in concert with** `retry_policy` (it needs ≥1 retry-on condition + a `num_retries` cap) and `per_try_timeout`. This finding RESHAPES the parent-42 brainstorm's "racing concurrent attempts" framing (§2.1): the reference's concurrency is timeout-triggered, not fan-out-triggered.
- **The user's deliberate scope: implement the FULL `HedgePolicy` semantics — including the fan-out the reference no-ops (Q-scope → Fork: IMPLEMENT-FAN-OUT).** Phase 42.2 implements `per_try_timeout` + `hedge_on_per_try_timeout` (both reference-faithful) AND the `initial_requests`/`additional_request_chance` parallel fan-out (which the reference leaves `#not-implemented-hide:`). This is a DELIBERATE richer-than-reference scope — a recorded DEPARTURE for the two fan-out fields, with a split verification posture (next fact).
- **Split verification: cross-side for the reference-implemented fields, subject-side for the fan-out (Q-fanout-verify → Fork: SPLIT-BY-FIELD).** `per_try_timeout` + `hedge_on_per_try_timeout` are verified CROSS-SIDE against `contrib-v1.37.2` (the reference implements them). ### 1.1 What phase 42.2a delivers as a self-contained whole (envelope: per_try_timeout)

Phase 42.2a lands the per-attempt deadline over the live 42.1 sequential substrate, as a self-contained whole:

1. **The per-attempt deadline ctx** (ADR-0250) — `RetryPolicy.per_try_timeout` (field 3, a `*durationpb.Duration`) parsed in `buildRouterActionWithVH` (`hcm/config.go`) and carried on the `RetryPolicy` (`retry.go`). The retry executor derives a per-attempt child `context` (`context.WithTimeout(reqCtx, perTryTimeout)`) around each `doH{1,2}ClusterAction` call. On the per-attempt deadline expiring, the attempt fails as a LOCAL-ORIGIN retriable timeout (distinct from a client-initiated parent-ctx cancel — §2.3, a load-bearing distinction; the 42.1 H2 `Status:0` ctx-cancel-is-NOT-retried path must NOT swallow a per-try timeout).
2. **The `upstream_rq_per_try_timeout` counter** (ADR-0250) — a cluster-level counter incremented when an attempt hits its `per_try_timeout`, registered via the 42.1 `EnsureRetryStats` scoping (retry-policy clusters only; byte-stable elsewhere). The exact name + the counter→event mapping is a SPEC pin (D-H-STATS).
3. **The retry interaction** (ADR-0250) — without `hedge_on_per_try_timeout`, a per-try-timeout is just another retriable outcome: the attempt is abandoned, `upstream_rq_per_try_timeout`++ + the existing `upstream_rq_retry`++ on the re-attempt, and the EXISTING 42.1 sequential loop re-picks a host (under the same `num_retries` + `retry_budget` caps). NO concurrency at 42.2a.
4. **The `per_try_timeout` default + the global-route-timeout interaction** (ADR-0250) — the default when unset, and the interaction with `RouteAction.timeout` (field 8, the overall route deadline — whether envoy-go implements it AT ALL is a D-H-TIMEOUT obligation; if not, `per_try_timeout` is the FIRST request deadline of any kind), are SPEC pins.
5. **The differential `0076-per-try-timeout`** — a held backend (REUSE `BlockingHoldResponder` 36 / the `/__release` gate) that exceeds a small `per_try_timeout` deterministically + a fast healthy retry target ⇒ the per-try-timeout fires ⇒ the retry recovers to a downstream 200. Cross-side (the reference implements `per_try_timeout`). Count-based + the release-barrier (`reference_concurrency_differential_release_barrier`), poll-the-gauge, never a sleep-assertion. §6.
6. **The BEHAVIOR_CONTRACT 42.2a bundle** + the STATE advance; ROADMAP row 42 STAYS `in-progress` (42.2b remains).

### 1.2 What phase 42.2b delivers as a self-contained whole (envelope: hedging)

Phase 42.2b lands the concurrency + the fan-out over the 42.2a deadline, as a self-contained whole:

1. **The concurrent `hedgeExecutorH1`/`hedgeExecutorH2`** (ADR-0251) — a separate concurrent racer in `retry.go`, dispatched (via the `H{1,2}ClusterAction` closure switch, alongside the 42.1 `if rp != nil` branch) ONLY when the action carries a `hedgePolicy` that triggers concurrency. It reuses the 42.1 per-attempt unit (body replay + the per-attempt deadline ctx + `doH{1,2}ClusterAction` + the `matches(status, localOrigin)` classify + the per-attempt CB-admission + `RecordUpstreamResult` + the shared `retry_budget`) but launches attempts CONCURRENTLY and collects the first acceptable result.
2. **`hedge_on_per_try_timeout`** (ADR-0251) — when set, a per-try-timeout no longer ABANDONS the attempt: the slow attempt is LEFT in flight and a hedged attempt is launched concurrently; the first acceptable (non-retriable) response wins; a late error from the slow attempt is discarded; a late SUCCESS from a loser is discarded (the first acceptable already returned). A hedge counts as a retry (`upstream_rq_retry`++) drawing on the same `num_retries` + `retry_budget` caps (the proto: "a retry will be issued"). Cross-side (the reference implements it).
3. **The initial fan-out `initial_requests`/`additional_request_chance`** (ADR-0251) — `initial_requests` (N) fires N concurrent attempts up front; `additional_request_chance` (a `FractionalPercent`) probabilistically fires one more. First-acceptable-wins. SUBJECT-SIDE verified (the reference no-ops these — §2.5); the downstream-2xx outcome stays cross-checkable.
4. **The first-acceptable-wins collector + the goroutine lifecycle** (ADR-0251) — a result channel + a `select`-first-acceptable collector; losers are cancelled via `context` + drained (no goroutine leak, no double-`RecordUpstreamResult` race); each in-flight attempt independently runs CB-admission + the outcome seam (so circuit breaking + outlier detection see EVERY concurrent attempt). §2.6.
5. **The `hedge_policy` parse + the vhost fallback** (ADR-0251) — `RouteAction.hedge_policy` (field 27) with the `VirtualHost.hedge_policy` (field 17) route-absent fallback, parsed in `buildRouterActionWithVH` (mirroring the 42.1 `parseRetryPolicy` route-first/vhost-fallback), carried on `clusterRouteAction`. The `HedgePolicy.initial_requests >= 1` PGV is the only real reject arm (D-H-PROTO).
6. **The differential `0077-hedge-on-per-try-timeout`** (cross-side, `hedge_on_per_try_timeout`) + a **subject-side fan-out arm** (`initial_requests>1`). §6.
7. **The BEHAVIOR_CONTRACT 42.2b bundle** + the STATE/ROADMAP advance; ROADMAP row 42 flips `done` (all three legs landed).

## 2. Design decisions

### 2.1 Subject confirmation: hedging — the `HedgePolicy` + `per_try_timeout` proto surface; the #not-implemented-hide finding *(Q-subject → the pre-authorized 42.2 leg)*

`RouteAction.hedge_policy` (field 27; `VirtualHost.hedge_policy` field 17 fallback) is a single `route.v3.HedgePolicy` message in the EXISTING go-control-plane dep (ZERO new module). Its three fields: `initial_requests` (field 1, `*wrapperspb.UInt32Value`, default 1, PGV `gte:1`, **`#not-implemented-hide:`**), `additional_request_chance` (field 2, `*type.v3.FractionalPercent`, default 0%, **`#not-implemented-hide:`**), `hedge_on_per_try_timeout` (field 3, default false — the ONLY reference-wired field). `RetryPolicy.per_try_timeout` (field 3, a `*durationpb.Duration`) is the per-attempt deadline. The full field roster + the default/PGV pins + the `RouteAction.timeout` interaction are SPEC obligations (§10, D-H-PROTO/D-H-TIMEOUT). The #not-implemented-hide finding is load-bearing: the reference's hedging is per-try-timeout-triggered concurrency (`hedge_on_per_try_timeout`), NOT the fan-out the field names suggest — so the cross-side-faithful core is `per_try_timeout` + `hedge_on_per_try_timeout` (the user adds the fan-out as a subject-side-verified departure, §2.5).

### 2.2 The 42.2a/42.2b sub-split: per_try_timeout first, then hedging *(Q-split2 → Fork: SUB-SPLIT)*

`per_try_timeout` (42.2a) is the clean prerequisite: a per-attempt deadline that the EXISTING sequential 42.1 loop consumes (bound each attempt; on expiry, a retriable timeout → the existing re-attempt), cross-side-faithful, no concurrency, ~120–200 LoC. Hedging (42.2b) layers the concurrent `hedgeExecutor` + `hedge_on_per_try_timeout` (which CHANGES the per-try-timeout behavior from abandon-and-retry to leave-in-flight-and-hedge) + the fan-out on top, ~300–450 LoC. Splitting isolates the concurrency risk (goroutines, the first-acceptable-wins collector, the cancel/drain lifecycle) into its own leg, lands `per_try_timeout` as a usable standalone, and keeps each leg well under the ADR-0045 gate. Row 42 is now a three-leg row (§1.4).

### 2.3 per_try_timeout architecture: a shared per-attempt deadline ctx; distinguishing a per-try timeout from a client cancel *(Q-concurrency [shared half] → ADR-0250)*

The retry executor derives a per-attempt child `context` via `context.WithTimeout(reqCtx, perTryTimeout)` (when `per_try_timeout` is set) around each `doH{1,2}ClusterAction` call. The LOAD-BEARING distinction: a per-attempt-deadline expiry is a RETRIABLE local-origin timeout (the attempt failed; re-attempt if budget remains), whereas a PARENT-ctx (client) cancel is NOT retriable (the 42.1 H2 path returns `Status:0` + `*h2.Error` and `matches(0, false)` is FALSE — a client cancel is never retried). The executor must tell them apart: the per-attempt timeout fires the CHILD ctx (a known internal deadline), the client fires the PARENT. On the child deadline: `upstream_rq_per_try_timeout`++ + classify as retriable (mapped to the existing connect-failure/local-origin retriable shape, or its own per-try-timeout-is-retriable rule — D-H-RETRY). On the parent cancel: unchanged 42.1 behavior (not retried). The precise mechanism (a `context.Cause`/`errors.Is(ctx.Err(), context.DeadlineExceeded)` discriminator on the child vs the parent done-channel) is a SPEC pin (D-H-RETRY). This is a small, surgical addition to the 42.1 sequential executor (the non-hedge `per_try_timeout` case); the hedge path (42.2b) reuses the same per-attempt deadline.

### 2.4 hedgeExecutor architecture: a separate concurrent racer *(Q-concurrency → Fork: SEPARATE-EXECUTOR → ADR-0251)*

**Fork (chosen): a SEPARATE concurrent `hedgeExecutorH1`/`hedgeExecutorH2`.** The 42.1 `retryExecutorH1`/`retryExecutorH2` stay byte-identical for the no-hedge path. The `H{1,2}ClusterAction` closure switch gains a `hedgePolicy` branch (`if hp != nil && hp.triggersConcurrency() { return hedgeExecutorHN(...) }`) BEFORE the existing `if rp != nil { return retryExecutorHN(...) }`. The `hedgeExecutor` reuses the per-attempt unit but launches attempts as goroutines feeding a result channel, collecting the first acceptable result. Chosen over **the unified concurrent executor** (rejected: it would refactor the byte-stable 42.1 loop and route the common no-feature path through concurrency machinery — a byte-stability + perf risk; the 42.1 reviewer explicitly sanctioned keeping executors SEPARATE rather than forcing a premature shared abstraction) and **goroutine-per-attempt threaded into the shared loop** (rejected for the same reason — it threads concurrency into the sequential path). Separation isolates all goroutines/channels/cancellation to the hedge path; the sequential retry path never spawns a goroutine. The shared per-attempt unit (the body-replay + deadline-ctx + driver-call + classify + admission/outcome) is the natural reuse seam (a small extracted helper, OR duplicated ~30 LoC per the 42.1 H1/H2-separate precedent — a SPEC/PLAN call).

### 2.5 The fan-out scope + the split verification posture *(Q-scope → Fork: IMPLEMENT-FAN-OUT; Q-fanout-verify → Fork: SPLIT-BY-FIELD)*

42.2b implements the FULL `HedgePolicy`: `hedge_on_per_try_timeout` (cross-side-faithful) AND the `initial_requests`/`additional_request_chance` parallel fan-out (which the reference leaves `#not-implemented-hide:`). VERIFICATION SPLITS BY FIELD:
- **Cross-side** (the reference implements them): `per_try_timeout` (42.2a) + `hedge_on_per_try_timeout` (42.2b) — asserted against `contrib-v1.37.2` (final downstream status + `upstream_rq_per_try_timeout` + the hedge-as-retry counter, offset-invariant per `reference_round_robin_offset_randomized`).
- **Subject-side** (the reference no-ops them — a recorded DEPARTURE): the `initial_requests`/`additional_request_chance` fan-out — router-package unit tests (deterministic, no Docker) + a subject-side differential arm asserting N parallel upstream attempts + first-success-wins. The reference fires exactly 1 initial request, so the upstream-attempt COUNTS diverge cross-side; the offset-invariant DOWNSTREAM-2xx outcome (both sides return 200) STAYS cross-checkable (the `0075` recover-arm's offset-invariant downstream assertion). The subject-side-ONLY fan-out arm is a NEW verification posture for 42.2b (the reference no-ops the fields), NOT a `0075` inheritance. The departure is recorded in the BEHAVIOR_CONTRACT + ADR-0251 §Consequences.

### 2.6 first-acceptable-wins collector semantics + the goroutine lifecycle *(self-answered; pinned at SPEC, D-H-RACE)*

The concurrent collector: each in-flight attempt runs as a goroutine (body replay + per-attempt deadline ctx + `doH{1,2}ClusterAction` + classify + CB-admission + `RecordUpstreamResult`) and sends its `(ActionResponse, endpoint, err)` to a result channel. The collector `select`s the FIRST ACCEPTABLE (non-retriable per `matches`) response → returns it, cancels the in-flight losers via their child `context`, and drains their channel sends (no goroutine leak; the loser's late `RecordUpstreamResult` still fires so outlier detection counts it). If an attempt returns a RETRIABLE outcome and budget/`num_retries` remain, the executor may launch a replacement attempt (the retry-within-hedge interaction — D-H-RACE). If ALL attempts exhaust without an acceptable response, the LAST retriable response is returned (the 42.1 exhaustion semantics). `num_retries` + the `retry_budget` cap the TOTAL in-flight + sequential attempts cluster-wide (hedged attempts draw the same budget — `TryAcquireRetry`). The exact collector rules (the retry-vs-hedge interaction, the budget accounting under concurrency, the cancel/drain ordering, whether a `RecordUpstreamResult` per loser is correct vs double-counting) are SPEC pins (D-H-RACE) — the highest-risk area of 42.2b, to be live-pinned + unit-tested + `-race`-gated.

### 2.7 Response-flags posture: RX/URX + any hedge flag are a RECORDED DEPARTURE *(self-answered — the 42.1/41 precedent)*

Envoy emits `RX`/`URX` (retry) response flags + may annotate hedged requests on the access-log line. envoy-go has NO response-flags plumbing (`RESPONSE_FLAGS` hardcoded `-`; the 42.1 AMEND-RT7 + the phase-41 CB4 precedent). So any hedge/retry response flag is a RECORDED DEPARTURE; the differential asserts STATS (`upstream_rq_per_try_timeout`, `upstream_rq_retry`) + the final status code, NEVER the access-log line. §5.2.
