# Phase 38 Brainstorm — `subset` LB (FIFTH Load-balancing-family row; the family STAYS OPEN; the FIRST LB *wrapper* — a metadata-match selector over the existing policies)

**Status:** brainstorm complete (lifecycle-state 0 → 1). This document captures the design decisions reached during the brainstorm session for phase 38 (`load-balancer-subset`), the **FIFTH Load-balancing-family row**. Phase 38 lands `Cluster.lb_subset_config` (`Cluster.LbSubsetConfig`, `envoy.config.cluster.v3`) — endpoint-metadata subset selection. Unlike the project's five prior LB constructs (the phase-02 `roundRobin`, the phase-34 `leastRequest`, the phase-35 `randomLB`, the phase-36 `ringHashLB`, the phase-37 `maglevLB`), **subset LB is NOT an `Cluster.LbPolicy` enum value** — it is a *wrapper* triggered by the presence of `lb_subset_config`, that selects a subset of endpoints matching the route's `metadata_match` and then **delegates to the cluster's existing `lb_policy` as the child policy run within that subset**. Phase 38 is therefore the family's **FIRST wrapper** (all five incumbents are leaf `loadBalancer`s) and the first LB construct that introduces a NEW endpoint dimension (per-endpoint metadata) and a NEW producer plane (the route `metadata_match`).

The load-bearing facts that shape this brainstorm:

- **subset LB wraps `lb_policy`; it is not a sibling of it.** In Envoy, `lb_subset_config` is a field of `Cluster` orthogonal to `lb_policy`. When present, the cluster's host set is partitioned into precomputed *subsets* (one per distinct endpoint-metadata value-tuple per configured selector), and each subset is balanced by the cluster's `lb_policy` (round_robin / least_request / random / ring_hash / maglev). The wrapper resolves the route's `metadata_match` to a subset at pick time, then delegates `Pick` to that subset's child LB. **Consequence:** phase 38 builds a `subsetLB` that OWNS child `loadBalancer` instances (one per subset), built via the existing policy factory — it does not add a sixth leaf policy.
- **`Endpoint` gains its first dimension beyond the address.** Today `internal/cluster/cluster.go`'s `Endpoint` is `{Host, Port}` and `extractEndpoints` (`manager.go:533`) flattens every `LocalityLbEndpoints` group into a flat `[]Endpoint`, discarding metadata/locality/weight/priority/health. Subset LB requires the per-endpoint `envoy.lb` metadata (`LbEndpoint.metadata.filter_metadata["envoy.lb"]`, proto field 3) — so `Endpoint` grows a `Metadata` field and `extractEndpoints` captures it. This is the FIRST time `Endpoint` carries anything beyond `Host:Port`.
- **A NEW producer plane: the route `metadata_match` (static config, NAT-transparent).** Unlike the ADR-0235 hash key (request-DERIVED — a header value or source IP), the subset match is STATIC route config: `RouteAction.metadata_match.filter_metadata["envoy.lb"]` (proto field 4). It is parsed once at route-config build and threaded to the cluster pick via `context.Context` (the analogue of ADR-0237's hash-key producer). Because it is static config (not source-IP-derived), it is **NAT-transparent on BOTH differential sides regardless of plane** — a strictly cleaner cross-side proof than ring_hash's tcp source_ip leg (`reference_differential_hash_key_cross_side_infeasible`).
- **The seam EXTENDS again — the SECOND pick-input half.** ADR-0235 widened `loadBalancer.Pick` to carry the hash key (`Pick(hashKey uint64, hasHash bool)`); phase 38 widens it once more to also carry the resolved subset match (`Pick(hashKey uint64, hasHash bool, match SubsetMatch, hasMatch bool)`). The five leaf policies ignore `(match, hasMatch)`; `subsetLB` resolves `match` → its child → delegates `child.Pick(hashKey, hasHash, …)` (the hashKey passes straight through, so a ring_hash/maglev *child* inside a subset still routes by key). The exported `Cluster` surface stays BYTE-STABLE (the OPTION-C discipline ADR-0232 set). This is a seam BUILD (a new pick-input) → its own ADR, exactly as ADR-0235 was — contrasting maglev's/random's zero-seam reuse.
- **Health-independence is WHY subset was picked over the other three candidates.** The remaining family candidates are {subset LB, locality-weighted LB, priority load balancing, panic thresholds}. The latter three are gated by the absent health-checking boundary (the Upstream-robustness family's territory): panic thresholds key off the healthy-host percentage (with no health field, all hosts are always healthy → panic never fires), priority load balancing spills to lower priorities only when a level's healthy capacity drops (with no health, P0 is always "full" → never spills), and locality-weighted LB's production algorithm scales weight by host availability. Subset LB is the ONLY candidate fully decoupled from health — a pure metadata-match-then-delegate mechanism. It is therefore the right next family row BEFORE the Upstream-robustness family lands health checks.

### 2.2 Seam + child-policy architecture: a wrapper owning per-subset child LBs, ALL five children *(Q1 → ADR-0239/0240)*

**Decision (Approach A):** `subsetLB` is a `loadBalancer` wrapper that, at build time, enumerates subsets (per selector × distinct endpoint-metadata value-tuples) and builds a **child `loadBalancer` per subset via the existing policy factory** over that subset's endpoint slice; the seam widens to thread the route `metadata_match` alongside the hash key; at `Pick`, resolve match → child → delegate `child.Pick(hashKey, hasHash, …)`. ALL five child policies are supported uniformly (round_robin / least_request / random / ring_hash / maglev) — the hashKey passes straight through, so a hash-policy child routes by key WITHIN its subset.

**Rationale:** factory reuse makes "all children" barely harder than one — the per-subset child build is the existing build over a sub-slice, and the hashKey already flows through the seam. This is the most faithful shape (the reference honors `lb_policy` as the child) and keeps the exported `Cluster` surface byte-stable. Rejected: Approach C (round_robin-only child — a real parity gap, the reference balances each subset by the configured `lb_policy`) and Approach B (subset-awareness pushed into each of the five policies — scatters the logic, no clean wrapper, breaks the precomputed-subset model). The wrapper isolates ALL subset logic in `subset.go`; the five leaf policies stay untouched but for the behavior-neutral `Pick` signature widening.

**The seam-input widening (the load-bearing design point):** `cluster.go`'s `Pick` callers (the `Dial`/`AcquireH1` funnels, currently extracting `hashKeyFrom(ctx)`) also extract `subsetMatchFrom(ctx)` and pass the resolved match to `lb.Pick(...)`. The five leaf policies ignore `(match, hasMatch)`; `subsetLB.Pick` resolves the match to a subset and calls `child.Pick(hashKey, hasHash, match, hasMatch)` (the child ignores match too, but consumes hashKey). The match type is a small resolved key→value set (the route's `envoy.lb` struct, canonicalized — D-SS2). D-SS6 confirms the threading.

### 2.3 Producer-plane scope: HTTP `RouteAction.metadata_match` (38.1); weighted clusters → 38.2 *(Q2/Q2b → the 38.1/38.2 split)*

**Decision:** 38.1's producer is the HTTP router's `RouteAction.metadata_match` ONLY. The weighted-cluster plane (`RouteAction.weighted_clusters` routing + `WeightedCluster.ClusterWeight.metadata_match`) is DEFERRED to **38.2** as a pre-authorized by-plane split (§1.4). The tcp_proxy `metadata_match` plane is DEFERRED entirely (§8).

**Rationale:** `metadata_match` is STATIC route config (not request-derived), so it is NAT-transparent on both differential sides regardless of plane — the cleanest possible cross-side proof. The HTTP-router plane is self-contained: parse `RouteAction.metadata_match["envoy.lb"]`, attach it to the existing `clusterRouteAction` (which already carries `hashPolicies`), thread it via `WithSubsetMatch`. The brainstorm surfaced that the **weighted-cluster plane has a hidden prerequisite**: the router resolves a SINGLE `*cluster.Cluster` per route today (`clusterRouteAction`, `actions.go:201`); `RouteAction.weighted_clusters` (per-request weighted cluster selection) is unimplemented. Wiring `ClusterWeight.metadata_match` requires FIRST building weighted-cluster routing — a NEW routing primitive (an HTTP-routing-family concern) with its own blast radius and a near-certain ADR-0045 trip. The user chose to keep both planes in phase 38 but SPLIT them up front (38.1 then 38.2) rather than collapse them into one oversized leg. The tcp_proxy plane offers only one static match per listener (no per-route richness — a thin differential arm for double the producer wiring) and is deferred.

### 2.4 The subset-selection envelope: all 3 cluster-level fallbacks; per-selector fallback DEFERRED *(self-answered; pinned at SPEC, D-SS3)*

**Decision:** 38.1 consumes all three cluster-level `fallback_policy` values {NO_FALLBACK, ANY_ENDPOINT, DEFAULT_SUBSET} + `default_subset` (core subset semantics, cheap). It DEFERS the per-selector `LbSubsetSelectorFallbackPolicy` / `fallback_keys_subset` / `KEYS_SUBSET` machinery (§8) — the cluster-level fallback is the MVP's only fallback path. The exact fallback outcomes (NO_FALLBACK → the no-healthy-upstream response/stat; ANY_ENDPOINT → balance over the full host set; DEFAULT_SUBSET → balance over the `default_subset` match, falling through to NO_FALLBACK when the default matches zero hosts) are SPEC empirical pins (D-SS3).

**Rationale:** the three cluster-level fallback policies are the load-bearing subset semantics (what happens when a route's metadata_match selects no subset) and are cheap to implement uniformly in the wrapper. The per-selector fallback machinery (KEYS_SUBSET narrowing, fallback_keys_subset) is a refinement that the reference itself gates behind a `NOT_DEFINED` default (it inherits the cluster-level policy) — so deferring it keeps the MVP faithful for the common case (no per-selector override) and defers only the override path.

### 2.5 Differential strategy: static-config NAT-transparent cross-side subset affinity *(Q-differential → fixture envelope §6)*

**Decision:** the fixture `0064-lb-subset` chains an HTTP listener routing to a STATIC cluster carrying `lb_subset_config` (a `version` selector) over endpoints tagged with distinct `envoy.lb` metadata (`version: v1|v2`), on BOTH sides; the route table has header/path-routed routes each carrying a `RouteAction.metadata_match` pinned to one version. The driver sends requests via each route and asserts: **(a) subset affinity** — a v1-route's requests land ONLY on v1-tagged backends and a v2-route's ONLY on v2-tagged backends, on BOTH sides (the subset signature — the unsubsetted policy would spread across ALL backends); **(b) a fallback arm** — a route whose `metadata_match` matches no subset exercises the cluster's `fallback_policy` (NO_FALLBACK → no-healthy-upstream; or ANY_ENDPOINT → spreads to all); **(c)** cross-side byte-equivalence + a cross-side `StatsAsserter` (the `lb_subsets_*` stats cross-equal + `upstream_rq_total` cross-equal). The subset match is STATIC route config → NAT-transparent → TRUE cross-side on BOTH the affinity and fallback arms (strictly cleaner than ring_hash's tcp source_ip leg). Every live assertion proven via a deliberate-break with `-count=1` (`reference_differential_break_protocol_count1`) — the affinity break ("drop the metadata_match so requests spread across all backends" → fails affinity) and the fallback break ("misroute a no-match request" → fails the fallback arm) both bite. The backend-identity assertion uses the driver's known port→version mapping (the configured endpoint tags), per `reference_differential_asserter_dispatch` (the cross-side assertions run via `StatsAsserter`, not `SubjectAsserter`).

**Rationale:** subset LB's interesting property is SELECTION — requests with a given route metadata land only on the subset of backends carrying matching endpoint metadata. The static-config match is NAT-transparent on both sides (the route's metadata_match is identical config on subject and reference), so the cross-side affinity is asserted TRUE on both sides without the source-IP NAT obstacle that constrained ring_hash's tcp leg. The backend identity is knowable because the fixture's driver configures which `127.0.0.x:port` carries which `version` tag in the bootstrap — so it can assert v1-route requests hit only the v1 port-set. The maglev/ring_hash modular-invariant convention does NOT apply (subset affinity is a SET-membership property, not a hash-stability property) — the assertion is "every served backend ∈ the expected subset," with a spread check WITHIN the subset only if the subset has ≥2 hosts (the child policy distributes within it). D-SS7 pins the exact route/endpoint design + the flake-free protocol.

### 2.6 Deferred-policy posture: NO lb_policy reject-text change *(self-answered; pinned at SPEC, D-SS1)*

**Decision:** subset LB does NOT touch the `Cluster.LbPolicy` reject-text (the supported-list `… RING_HASH, MAGLEV` stays byte-stable) — because subset LB is NOT an `LbPolicy` enum value (it is the orthogonal `lb_subset_config` field). Any such reject is envoy-go's faithful reproduction of the reference's own `lb_subset_config` validation — a PARITY reject (NOT a departure), pending D-SS1 confirmation.

**Rationale:** the byte-stable-reject discipline (ADR-0080) still governs — but the touchpoint shifts from the lb_policy supported-list (untouched here) to the `lb_subset_config` validation messages. D-SS1 enumerates the exact reject set + wording so the blast radius is known up front, never discovered at the six-gate. NOTE this is the FIRST LB phase since least_request (34) NOT to change the lb_policy reject text — a deliberate consequence of subset being a wrapper, not an enum value.
