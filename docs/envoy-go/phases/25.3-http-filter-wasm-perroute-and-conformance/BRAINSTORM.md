### 2.1 Multi-plugin VM-sharing semantics: process-global registry keyed by (vm_id, code_hash, runtime) *(Q1 → ADR-0211 + in-place AMEND to ADR-0205 §Consequences)*

**Decision:** Multi-plugin VM-sharing at 25.3 uses a process-global `map[(vm_id, code_hash, runtime)]*RootVM` registry with refcount + sync.RWMutex, mirroring cpp-host's `WasmHandleBase` shared-ptr registry pattern at `proxy-wasm-cpp-host:include/proxy-wasm/wasm.h`. Each `PluginConfig.New` looks up existing `*RootVM` by the composite key; if present + match found, reuses + bumps refcount; if absent, constructs fresh + inserts. Plugin contexts (one per `PluginConfig` sharing the vm_id) are distinct `*PluginContext` children of the shared `*RootVM`, each with its own `root_id` + `configuration` bytes + capabilities. Cross-plugin shared-data is SHARED at the `*RootVM` scope (all plugins under one vm_id see the same `sharedDataMap`; mirrors upstream `Wasm`-level shared-data semantic). The registry primitive lives at `internal/wasm/registry.go` as an extension of the existing `internal/wasm/` framework primitive (NO new `internal/*` package). REFINES ADR-0205's anchor `*RootVM per *compiledConfig` → `*RootVM per (vm_id, code_hash, runtime)` shared across compiledConfig instances with matching identity.

**Rationale:** The cpp-host model is the upstream byte-faithful reference — the canonical Wasm Service operator pattern delegates to `vm_id`-keyed registry semantics across the upstream Envoy + Istio + Solo.io proxy-wasm plugin ecosystem. Diverging from the canonical pattern (per the explicit-opt-in `share_vm_with: []string` alternative OR the code-hash-only dedup alternative) would force operators to learn envoy-go-specific semantics that drift from the upstream operator manual + canonical WasmService discipline. The refcount + lifecycle complexity of the process-global registry is bounded (the registry is a small map + sync.RWMutex; the lifecycle hooks fire at `compiledConfig.New` + `compiledConfig.Close`; the registry singleton lives in `internal/wasm/` package init). Cross-plugin shared-data SHARED at `*RootVM` scope matches upstream semantics + enables the canonical operator pattern of "shared-data as cross-plugin communication channel within one vm_id."

**Anticipated ADRs:** ADR-0211 §Decision body anchors the process-global registry shape + the lifecycle hooks + the composite-key match discipline + the cross-plugin shared-data SHARED scope. ADR-0205 gains a one-line in-place AMEND acknowledgment paragraph in §Consequences noting the registry-keyed-by-`(vm_id, code_hash, runtime)` refinement (no new ADR number consumed; matches ADR-0202 §Consequences one-line AMEND precedent from 25.2 IMPL).

### 2.2 `failure_policy = FAIL_RELOAD` activation + reload state machine: upstream BackoffStrategy + envoy-go-strict floor *(Q2 → ADR-0211 sibling OR ADR-0212; SPEC settles)*

**Decision:** Honor `envoy.config.core.v3.BackoffStrategy.base_interval` + `max_interval` verbatim from `reload_config`; add envoy-go-strict hardcoded floor (`base_interval = max(operator_value, 100ms)` + `max_interval = max(operator_value, 1s)`) to prevent operator-misconfigured reload-storm. State machine `{Running, Reloading, Failed}` per-`*RootVM`; on uncaught panic in any guest hook → transition to Reloading + schedule next attempt at base_interval (using the `internal/clock/` Clock seam — third-co-consumer of ADR-0186 after phase-21 + 25.2's tick goroutine); on reload success → Running + reset backoff; on reload failure → double interval up to max_interval. Group-C `vm_reload_success` + `vm_reload_runtime_failure` + `vm_reload_backoff` counter triplet activates (project stat surface 128 → 131). `failure_policy = FAIL_OPEN` maps to bypass-on-failure (matches upstream); deprecated `fail_open: bool` maps onto `failure_policy = FAIL_OPEN` per AMEND-A1 ladder. New envoy-go-strict departure record (the hardcoded floor discipline; floor values NOT operator-tunable — mirrors phase-22.2 `:fileBytes()` 16 MiB cap pattern + the safety-first defaults precedent).

**Rationale:** Upstream `BackoffStrategy` is operator-tunable per the canonical reload semantics. envoy-go-strict adds a hardcoded floor as defense-in-depth: an operator who configures `base_interval = 1ms` would otherwise cause CPU spin reload-storm on every guest panic. The floor values (100ms base / 1s max) match phase-21's adaptive_concurrency safety-floor pattern. The Clock seam co-consumption RATIFIES ADR-0186 at third-co-consumer scope (after phase-21 itself + 25.2's tick goroutine). The state machine shape mirrors ADR-0178 (oauth2 token refresh) backoff/retry semantics + reuses the `internal/clock/` package primitives.

**Anticipated ADRs:** SPEC settles whether Q2 reload state machine bundles into ADR-0211 (the multi-plugin VM-sharing ADR — natural since the reload semantics interact with the registry refcount lifecycle) OR splits into a sibling ADR-0212 (with conformance harness shifting to ADR-0213). ### 2.3 `VmConfig.environment_variables` activation: upstream-parity + envoy-go-strict cap *(Q3 → ADR-0211 sibling OR ADR-0212; SPEC settles)*

**Decision:** Honor `EnvironmentVariables.host_env_keys: []string` (process-env allowlist passthrough at config-load time) + `key_values: map<string, string>` (explicit operator-configured pairs) per upstream semantics; `key_values` overrides `host_env_keys` on collision. envoy-go-strict cap: max 64 total entries + per-value 4 KiB cap (mirrors body-buffer / shared-data / dynamic-stats cap discipline established at 25.2).
