## 1. Purpose / Mission

Deliver the FIRST of the two deferred `metrics_service` knobs the 47.1 core leg strict-rejected: `report_counters_as_deltas=true`. When a bootstrap `stats_sinks[]` metrics_service entry carries `report_counters_as_deltas: true`, envoy-go's periodic registry-snapshot flush emits, per COUNTER family, the DELTA accumulated since the previous flush (`current − last_flushed`) rather than the cumulative absolute `Load()` value the 47.1 mapping emits (`mapping.go:31`). A PER-SINK last-value map (`map[string]uint64` keyed by full dotted name) holds the cross-flush state: each flush computes `delta = current − last[name]`, emits the delta as the COUNTER family value, then stores `current` as the new `last[name]`. The first flush (and the first appearance of any counter) emits `current − 0` = the absolute value; an unchanged counter emits a 0 delta and is STILL emitted (the full counter set every flush — D-MS-DELTA). GAUGES are NOT delta'd (the proto field is named `report_counters_as_deltas`; the live probe confirmed the reference leaves GAUGE families absolute — D-MS-DELTA-GAUGE), so the `*stats.Gauge` arm of the mapping type-switch (`mapping.go:35`) is UNCHANGED. The state is PER-SINK (two sinks can be configured with different `report_counters_as_deltas` values and flush/reconnect independently), so the delta-aware transform is sink-owned/sink-parameterized, NOT a mutation of the shared `Flusher` fan-out (`flusher.go:46`–`:50`) — 47.1 ships exactly one sink, but the per-sink framing is the correct boundary and costs nothing. This composes ENTIRELY on the landed 47.1 substrate (ADR-0262, squash `77f776bd`): NO new package, NO new go.mod module, NO new BackendKind, +0 stat surface. Byte-identical and value-identical to the 47.1 cumulative path when `report_counters_as_deltas` is absent/false (the full differential, including `0089`, is the regression anchor). It ANCHORS ADR-0263; **ROW 47 STAYS `in-progress`** (it flips `done` only at the FINAL sub-leg 47.2b IMPL per ADR-0106 + `reference_roadmap_split_phase_row_done`); the Observability family STAYS OPEN.

### 1.1 Empirical-finding-driven scope (amendment block per ADR-0044)

The §11 live probe (2026-06-29, contrib-v1.37.2 — an H1 downstream :10000 `stat_prefix=ingress_http` → an `hashicorp/http-echo` backend `dms-backend:5678`, K=7 requests fired ~350ms apart [deliberately spanning multiple flush windows], with a bootstrap `metrics_service` `stats_sinks[]` entry [V3 transport, **`report_counters_as_deltas: true`**, `grpc_service.envoy_grpc.cluster_name=c_metrics`] + `stats_flush_interval=1s`, exporting to a driver-owned h2c delta-aware `MetricsService` receiver reachable by `host.docker.internal:4319` on a shared bridge `dmsnet` per `reference_docker_probe_bridge_network`; **decode-ran proof: 90 `StreamMetricsMessage`s received, each carrying 87→177 `MetricFamily` entries; the deterministic COUNTER subset's per-flush deltas SUMMED to exactly 7==K**) CONFIRMED the brainstorm's delta hypotheses with NO structural amendment — the deltas knob behaves exactly as §2.2 of BRAINSTORM-47.2 hypothesized. The findings sharpen FOUR design pins:

- **AMEND-MSD-FIRST-FLUSH-ABSOLUTE (the first flush — and the first appearance of any lazily-instantiated counter — emits `current − 0` = the ABSOLUTE value; subsequent flushes emit the per-FLUSH latched delta).** Live finding (D-MS-DELTA): msg #1 carried each counter's full absolute boot value (`listener_manager.listener_create_success=32`, `cluster.backend.update_success=1`); `cluster.backend.upstream_rq_total` first appeared at msg #38 with `val=1` (the first request's delta from a zero/absent prior-flush value). So the delta baseline is 0 — `delta = current − last`, `last` initialized to 0 / the not-yet-seen counter's implicit 0. **Consequence for envoy-go:** the frozen `stats.Registry` has a FIXED counter set (no lazy instantiation — all counters registered before Freeze, ADR-0059), so envoy-go's per-sink last-value map starts empty (every `last[name]` defaults to 0) and the first flush emits each counter's full accumulated value as its "delta from 0" — matching the reference's first-flush-absolute. The per-sink map's zero-value default IS the correct baseline; no explicit "first flush is special" branch is needed (a `map[string]uint64` read of an absent key yields 0).
- **AMEND-MSD-ZERO-DELTAS-EMITTED (a counter whose per-flush delta is 0 is STILL emitted — the full counter set streams every flush, deltas included).** Live finding (D-MS-DELTA): every post-boot flush carried the FULL counter set (counter=26→59 families) with the unchanged counters reporting `val=0` (msg #41+: the subset counters all `val=0`, `counter=59(nz=2 z=57)` — 57 zero-delta counters present). The reference does NOT prune zero-delta counters. **Consequence:** envoy-go's existing whole-registry walk (`flusher.go:47` → `snapshot`) naturally emits EVERY counter each flush; the delta transform changes only the VALUE (absolute → `current−last`), not which counters appear — so envoy-go emits all counters with their delta (0 if unchanged), matching the reference. NO change to the emit-set; only the value arm.
- **AMEND-MSD-SUM-IS-THE-INVARIANT (a single flush's delta is PARTIAL; the SUM of a counter's per-flush deltas across all received flushes == its final cumulative == K — this is the `0090` assertion model, REPLACING 0089's `value==K` last-seen check).** Live finding (D-MS-DELTA-SUBJECT): the K=7 requests appeared as per-flush deltas **1 + 3 + 3** across msgs #38/#39/#40 (running sum 1→4→7), then `val=0` from msg #41 onward (idle) — the running sum stayed 7. A DELTA sink's LAST flush after convergence reads ≈0, so 0089's `Family(name).value == K` (last-seen-wins) assertion is MEANINGLESS for `0090`; the invariant is the SUM. The `0090` receiver accumulates a per-name running SUM of received values and the driver polls-to-converge until `FamilySum(subset) == K` on each side.
- **AMEND-MSD-CX-NOT-K (the deterministic subset for the delta-sum is the SAME 3-counter subset 0089 uses; `upstream_cx_total` is NOT == K and is correctly EXCLUDED).** Live finding (D-MS-DELTA-SUBJECT): `cluster.backend.upstream_cx_total` summed to **6**, not 7 (one HTTP/1.1 upstream connection was reused across two requests — connection count < request count), while `cluster.backend.upstream_rq_total`, `http.ingress_http.downstream_rq_total`, and `http.ingress_http.downstream_rq_2xx` each summed to exactly **7**. The 0089 subset (which already excludes all `_cx_` counters) is the correct delta-sum subset verbatim — `{cluster.<backend>.upstream_rq_total, http.<stat_prefix>.downstream_rq_total, http.<stat_prefix>.downstream_rq_2xx}`. No subset change from 0089.

Additional confirmed pins (no amendment): GAUGES stay ABSOLUTE under deltas (D-MS-DELTA-GAUGE — `cluster.backend.membership_total` constant `val=1`, `server.live` constant `val=1` across all 90 messages); the metric `type` stays `COUNTER` under deltas (not a new delta-type); deltas are NON-NEGATIVE (the registry's u64 counters are monotone — `current ≥ last` always — so no underflow handling is needed); the identifier-once lifecycle is UNCHANGED (msg #1 `ident=true`, msgs #2+ `ident=false`); +0 metrics_service self-stats (D-MS-STATS-FINAL-2); the reference BOOTS `report_counters_as_deltas:true` clean (D-MS-REJECT-2 — reference-parity-accept).

### 3.2 The per-sink last-value delta transform (`internal/statssink`)

The 47.1 mapping is the EXACT plug-in point. `internal/statssink/mapping.go:22` `snapshot(reg, nowMs) []*dto.MetricFamily` walks the frozen registry and emits, for each `*stats.Counter`, the absolute `float64(v.Load())` (`:31`). 47.2a adds a Counter-only delta transform parameterized by a PER-SINK last-value map:

- **The state:** a `map[string]uint64` of last-flushed Counter values keyed by full dotted `Name()`. Initialized empty; a read of an absent key yields 0 (the correct first-flush/first-appearance baseline — AMEND-MSD-FIRST-FLUSH-ABSOLUTE). The map is OWNED by the delta-aware sink (or its snapshotter), NOT the shared `Flusher` (two sinks flush/reconnect independently — per-sink state).
- **The transform (per flush, per Counter):** `cur := v.Load(); delta := cur - last[name]; last[name] = cur; emit float64(delta)`. Because counters are monotone u64 (`current ≥ last`), `delta` is non-negative — no underflow guard (re-confirmed: the registry's `Counter` only `Add`s). The COUNTER family `type` stays `COUNTER` (AMEND-MSD — not a new delta-type). The full counter set is emitted every flush, 0 deltas included (AMEND-MSD-ZERO-DELTAS-EMITTED) — the registry walk already emits every counter; only the VALUE arm changes.
- **GAUGES UNCHANGED:** the `*stats.Gauge` arm (`mapping.go:35`) emits the absolute `Load()` exactly as 47.1 (D-MS-DELTA-GAUGE — the reference leaves gauges absolute under deltas). No gauge state.
- **Placement (D-MSD-PLACEMENT — a PLAN call):** the per-sink delta state + transform may live as (a) a sink-owned `map[string]uint64` applied in the sink's `Submit`/writer path that rewrites COUNTER families to deltas, or (b) a per-sink `snapshotter` the `Flusher` invokes per sink (parameterizing the registry walk with the sink's delta mode + state), or (c) a small `delta.go` helper within the package consumed by the sink. **HARD CONSTRAINT (the SPEC pins, the PLAN realizes):** the shared absolute `snapshot()` batch slice (`flusher.go:47`) is fanned to EVERY sink (`:48`–`:49`); a delta sink MUST NOT mutate the shared `dto.MetricFamily`/`dto.Metric`/`dto.Counter` values in place (that would corrupt a sibling absolute sink and is non-idempotent across the two flush fan-out reads) — the delta transform builds the sink's OWN COUNTER families (or its own batch). With one sink today the cross-sink-corruption is theoretical, but the per-sink framing + the no-in-place-mutation rule is the correct boundary (BRAINSTORM-47.2 §Q-delta-state). The cleanest seam (PLAN to confirm): keep `snapshot()` producing absolute values, and have the delta-aware sink/snapshotter produce a delta batch from the absolute one (cloning the rewritten COUNTER families; GAUGE families may be shared as-is since they are not transformed).

## 8. Differential fixture taxonomy (+1: `0090` cross-side EXACT on the deterministic COUNTER subset's delta-SUM)

### 8.1 `0090-stats-sink-metrics-service-deltas` (cross-side EXACT — poll-to-converge the per-name running delta SUM)

The `0089` topology + workload VERBATIM (an H1 downstream `stat_prefix=hcm_local` → an `HTTPFixedBody` backend `c_backend`, K=7 deterministic 2xx requests, TWO driver-owned per-side `metricsservice` receivers on two separately-allocated host ports bound before either proxy starts, a SHORT `stats_flush_interval` [500ms], a node{id,cluster} fixed identically both sides, a hard `Close()` teardown) — with the bootstrap `metrics_service` `stats_sinks[]` entry carrying **`report_counters_as_deltas: true`** on BOTH sides. The delta sink breaks 0089's `value==K` last-seen assertion (the last idle flush reads ≈0), so `0090` asserts the **SUM of each deterministic counter's per-flush deltas across all received flushes == K** (AMEND-MSD-SUM-IS-THE-INVARIANT). SLEEPLESS: fire K (=7) requests, then poll-to-converge until each side's running per-name delta SUM == K (a release barrier, NEVER a `time.Sleep` — `reference_concurrency_differential_release_barrier`; the proxy flushes the snapshot every `stats_flush_interval`, so the sum converges as the post-K flushes arrive).

- **Assertions (cross-side EXACT, on the deterministic NAME SUBSET — the SAME subset 0089 uses; AMEND-MSD-CX-NOT-K excludes `_cx_`):** for `{cluster.c_backend.upstream_rq_total, http.hcm_local.downstream_rq_total, http.hcm_local.downstream_rq_2xx}` (all COUNTER): the family is received on both sides with `type==COUNTER` and a per-name running delta **SUM == K (=7)**; the `identifier.node.id`/`.cluster == <configured>` (msg #1, unchanged from 0089). The subset is chosen for cross-side delta-sum determinism (D-MS-DELTA-SUBJECT: each summed to exactly 7; `upstream_cx_total` summed to 6 under connection reuse and is EXCLUDED).
