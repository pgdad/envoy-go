Phase 47 delivers a **periodic gRPC metrics-export sink** — `envoy.extensions.stat_sinks.metrics_service.v3`/`envoy.config.metrics.v3.MetricsServiceConfig` driving the `envoy.service.metrics.v3.MetricsService.StreamMetrics` client-streaming RPC — the project's FIRST consumer of the bootstrap `stats_sinks[]` field (silently ignored to date per ADR-0064) and its FIRST **periodic, registry-snapshot** sink (all prior Observability sinks are per-request/event-driven).

The `Metric` interface exposes `Name() string` / `Type() MetricType` / `Format() string`; the concrete values come from `Counter.Load() uint64` (`internal/stats/counter.go:30`) and `Gauge.Load() int64` (`internal/stats/gauge.go:56`). **Only `Counter` and `Gauge` exist — histograms were deferred at phase 06.1 (ADR-0060)** — so the sink's metric-type mapping is closed to `COUNTER`/`GAUGE` (the `MetricFamily.type` `SUMMARY`/`HISTOGRAM` arms are unreachable, and `MetricsServiceConfig.histogram_emit_mode` is moot). ## 2. Design decisions

### 2.1 Row + subject confirmation: the Observability family continues with the metrics_service stats sink *(Q0 → phase 47 row registered)*

The Observability family stays open; the fourth row is the stats-sink subsystem via `metrics_service` (over the tap filter, and over opening a new family). Rationale: it composes on the phase-06.1 `Registry` + the phase-18 gRPC client at the lowest risk, continues the ALS/OTLP/tracing momentum, and reuses the already-proven cross-side stat-name compatibility.

### 2.2 Protocol: `metrics_service` (gRPC) *(Q1 → the transport)*

`metrics_service` (gRPC client-streaming) over statsd-UDP (lossy; new UDP seam), statsd-TCP (less-common; new raw-TCP-cluster dispatch), and `open_telemetry` metrics (heaviest proto). It mirrors the phase-44/45 streaming-sink precedent: a driver-owned gRPC receiver, a deterministic ordered transport, the `grpcclient.Dialer` reused.

### 2.3 Envelope + split axis: by-concern, 47.1 (cumulative/no-labels core) → 47.2 (deltas + tags-as-labels) *(Q-envelope + Q-split → ADR-0262 + anticipated ADR-0263)*

By-concern over flat. The cumulative/no-labels export + the flush subsystem + the differential is the self-contained core (47.1); `report_counters_as_deltas` (delta bookkeeping, flush-state internal to the sink) and `emit_tags_as_labels` (SN-rule label extraction, the Prometheus name model) are independent knobs layered on top, chartered by 47.2's own later brainstorm. Each leg lands a working, differential-provable sink.

### 2.4 The sink lifecycle: lazy stream establishment, identifier-once, reconnect-on-error *(self-answered; pinned at SPEC, D-MS-LIFECYCLE)*

The `MetricsServiceSink` mirrors the `OTLPExporter` shape (`internal/tracing/exporter.go`): a bounded channel fed by the `Flusher` (one batch per flush tick), a writer goroutine that lazily establishes the `StreamMetrics` stream on the first batch (sending the `identifier` once), `Send`s each `StreamMetricsMessage`, retries-once on a stream error (re-establishing + re-sending the identifier), and drops + counts on a full channel. `Close` is idempotent (`sync.Once`, the precedent). The `Flusher` is the NEW piece: a `time.NewTicker(stats_flush_interval)` loop that `Walk`s the registry, builds the batch, and hands it to the sink — started after `bs.Stats.Freeze()`, stopped on `ctx.Done()` with an optional final flush.

### 2.5 The structured mapping: `Registry` Counter/Gauge → MetricFamily (cumulative, no-labels) *(self-answered; pinned at SPEC, D-MS-FIELDS)*

Per metric from `Walk`: `MetricFamily{ name: <full internal dotted name>, type: COUNTER|GAUGE, metric: [{ counter|gauge: { value: float64(Load()) }, timestamp_ms: <flush time> }] }`. `emit_tags_as_labels=false` semantics → the full dotted name, zero `LabelPair`s (the `/stats` internal-name model, already cross-side name-compatible). The SPEC live-probe pins the exact reference `MetricFamily.name` form (dotted name with tags inlined), the `help` field (set or empty), and whether the reference sets `timestamp_ms` (left UNasserted regardless).

### 2.6 Deferred-policy posture: additive config; the metrics_service sink LIFTED from the ADR-0064 silent-ignore set; siblings explicitly boot-rejected *(self-answered; pinned at SPEC, D-MS-REJECT)*

The metrics_service `StatsSink.typed_config` moves from "silently ignored" (ADR-0064) to "parsed + enforced"; sibling `stats_sinks[]` TypeURLs (statsd / dog_statsd / graphite_statsd / hystrix / wasm / open_telemetry) are EXPLICITLY boot-rejected (`reference_strict_reject_sibling_typeurl_gap` — not left silently ignored); `report_counters_as_deltas=true`, `emit_tags_as_labels=true`, non-V3 `transport_api_version`, a non-default `histogram_emit_mode`, and `stats_flush_on_admin` are strict-rejected (ADR-0080); a missing/empty `grpc_service` cluster and a non-existent cluster boot-reject via the Dialer gate + a `HasCluster` check (the 46.2 `HasCluster` `log.Fatalf` boot-reject precedent — reference-parity).

### 2.7 Stat surface hypothesis: a small/zero `metrics_service`-sink self-counter set + incidental sink-cluster upstream stats *(self-answered; SPEC pins, D-MS-STATS)*

The metrics-service cluster is dialed as a normal cluster, so it incidentally emits the standard `upstream_cx_*`/`upstream_rq_*` cluster stats (a long-lived streaming connection — already-registered, no surface delta). The sink-specific self-counters (sent/dropped/reconnect, if any) are a small set whose EXACT names + scope + `+N` delta are SPEC-pinned against `contrib-v1.37.2` — note the self-referential subtlety: any self-counter registered before Freeze will ITSELF appear in the flushed `MetricFamily` set (a SPEC consideration; the reference may register none). Likely `+0` to `+2`.
