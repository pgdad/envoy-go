# Phase 30 — `pin-refresh-envoy-contrib`

**Status:** SPEC authored (lifecycle-state 1 → 2 at this commit; ready for the phase-30 PLAN authoring per `superpowers:writing-plans`). PLAN / PROGRESS artifacts still pending; land when this phase enters subsequent lifecycle states.

**What this phase is.** Phase 30 is a **flat infrastructure row** (NOT a §9 Network-filters-family row; not a member of any feature family — ROADMAP row 30, depends-on 29). It is the project's **FIRST reference-image pin change since ADR-0008** (the unchanged standard-image pin since phase 02), and the dedicated re-baselining phase mandated by `ENVOY_TARGET.md` doctrine **D-3.7** (*"the pin is changed only via a dedicated phase that re-baselines the differential suite"*). It does exactly one thing: swap the SHA-pinned differential reference image from the standard Envoy variant to the **contrib variant of the same upstream version** (`v1.37.2`), prove the contrib image is a behavioral **superset** (all 54 existing differential fixtures stay byte-identical green; the conformance gates — image-independent — re-run as sanity), and supersede ADR-0008 with **ADR-0227**. It ships **ZERO production LoC, ZERO new go.mod deps, ZERO new package/stat/fixture/fuzzer/BackendKind**; NO ADR-0045 split (~4–6 tasks).

**The corrected image identity (D30-1, executed at this SPEC session).** The phase-30 BRAINSTORM assumed the contrib variant ships as `envoyproxy/envoy-contrib:v1.37.2` (a separate Docker Hub repo). The D30-1 empirical pin **refuted** that: the `envoyproxy/envoy-contrib` repo exists but its release line stops at **v1.35.0** — there is **no v1.37.x tag** in it. The contrib variant for v1.37.2 ships instead as a **`contrib-`-prefixed tag inside the standard `envoyproxy/envoy` repo**: **`envoyproxy/envoy:contrib-v1.37.2`** (`docker inspect` digest `sha256:7edd5b0fd763d32c3dfcfd0061f9c2ea63eebd8cdf7f88d974d3adfc99453be8`, 299 MB vs the standard image's 263 MB — the extra compiled-in contrib extensions). The phase's premise is unchanged (same upstream version, contrib variant, unblocks the `kafka_broker` §9 subject); only the image **reference string** is corrected. See SPEC §1.2 (AMEND-D30) + §5.1.

**Why phase 30 exists (the downstream motivation).** It unblocks every Envoy **contrib** network filter — `kafka_broker` first (phase 31, the next §9 subject, selected at the phase-30 BRAINSTORM Q0 from {redis / kafka_broker / thrift}), whose canonical v3 proto (`envoy.extensions.filters.network.kafka_broker.v3.KafkaBroker`) is a contrib-only extension absent from the standard reference image AND lives in the `github.com/envoyproxy/go-control-plane/contrib` go module the project does not yet depend on. The `/contrib v1.32.4` dep + all kafka_broker work are **phase 31** (its own brainstorm). Phase 30 only swaps the image.
