# Phase 43 Brainstorm — per-protocol connection pooling (the FIFTH and FINAL Upstream-robustness-family row; the upstream connection-pool budget/queue + the H2 multiplex pool — closes the phase-41 `max_connections`/`max_pending_requests` deferral and SUPERSEDES ADR-0056)

**Status:** brainstorm complete (lifecycle-state 0 → 1). This document captures the design decisions reached during the brainstorm session for phase 43 (`connection-pooling`), the **FIFTH and FINAL Upstream-robustness-family row** (the family opened at phase 39 with active health checks, continued at phase 40 with passive outlier detection, phase 41 with circuit breakers, phase 42 with retries + hedging). Phase 43 lands the two deliverables the family has been deferring toward this row: (i) the **upstream connection-pool budget + pending wait-queue** — `max_connections` + `max_pending_requests` enforcement, the budgets phase 41 PARSED-and-registered-emit-0-but-DEFERRED precisely because envoy-go's synchronous-acquire-per-request model lacks the connection-pool *queue* those budgets need; and (ii) the **HTTP/2 multiplex connection pool** — cross-request stream multiplexing over reused upstream `ClientConn`s, which ADR-0056 deferred ("per-request fresh upstream H2 dial") and EXPLICITLY named the upstream-robustness family as its superseder. Where phase 41 caps in-flight *requests* (`max_requests`, fail-fast), phase 43 caps in-flight *connections* (`max_connections`, soft-throttle-then-pend) and amortizes the H2 handshake across requests — the fifth and final independent upstream-robustness dimension.

Phase 43 is the natural capstone of the phase-39/40/41/42 cluster-runtime substrate: it REUSES the per-request upstream lifecycle seams those phases built — the connection-acquire chokepoints (`Cluster.Dial`/`AcquireH1`/`DialH2`), the existing H1 LIFO connection pool (`c.h1Pool` + `AcquireH1`/`PutIdleH1`), the phase-41 per-priority `circuitBreaker` counter struct + its try-acquire/release discipline, and the `connWithGauge` upstream-conn close path that already drives `upstream_cx_active`. It ADDS the pending wait-queue the synchronous model lacks and the H2 connection pool the per-request-fresh discipline forbade.

The load-bearing facts that shape this brainstorm:

- **An H1 connection pool already exists; the budget/queue layer over it does NOT.** `Cluster` already carries `h1Pool map[string][]*PooledH1Conn` (a LIFO per-endpoint idle pool, `cluster.go:~97`, capped at `h1PoolMaxPerEndpoint = 1024`), with `AcquireH1` (`cluster.go:~455`, pool-hit fast path + pool-miss dial) and `PutIdleH1` (`cluster.go:~528`, keep-alive return). So envoy-go ALREADY reuses H1 keep-alive connections — phase 43 does NOT build the H1 pool, it adds the `max_connections` connection-creation cap + the `max_pending_requests` bounded wait-queue on top of it (the layer phase 41 deferred).
- **H2 is per-request-fresh-dial today (ADR-0056); the multiplex pool is THIS phase's deliverable.** `doH2ClusterAction` (`router_h2.go:~97`) calls `DialH2` (`dial_h2.go:~42`) per request and `defer cc.Close()` (`router_h2.go:~109`) immediately. The `h2.ClientConn` is ALREADY architecturally multiplex-capable (monotonic atomic `nextStreamID` never reset across calls, concurrent-safe `RoundTrip` (`h2/client.go:~479`), reads the peer's `SETTINGS_MAX_CONCURRENT_STREAMS` into `serverS.MaxConcurrentStreams` (`h2/client.go:~287`), a `goawayCh` GOAWAY signal, reusable across requests) — the ONLY thing forcing per-request-fresh is the router's close discipline. ADR-0056 §Consequences: "The upstream-robustness family, when it lands, brings H2 pooling and **supersedes ADR-0056 with a pooling-discipline ADR**. The pooling ADR will inherit the per-conn settings cache + max-concurrent-streams enforcement + GOAWAY-driven conn rotation as the load-bearing shape." Phase 43.2 IS that superseder.
- **`max_connections` PENDS, it does not 503 (unlike `max_requests`).** The phase-41 SPEC NARROWED enforcement to `max_requests` ONLY, recording: "`max_connections` is a soft throttle that PENDS rather than 503s, and `max_pending_requests` needs the connection-pool queue envoy-go's synchronous model lacks." This is the architectural heart of phase 43.1: at `max_connections`, a request that needs a NEW connection does not fail — it waits for a connection slot to free (a conn closes, or an idle conn returns to the pool); it only fails-fast with a **503 + `upstream_rq_pending_overflow`** when the bounded pending wait-queue (`max_pending_requests`) is itself full. So the two budgets are COUPLED: `max_connections` gates connection creation, `max_pending_requests` bounds the wait-queue in front of it.
- **The deferred emit-0 stats already exist — phase 43.1 ACTIVATES them, it does not invent them.** Phase 41 registered (emit-0, scoped to `circuit_breakers` clusters) `circuit_breakers.<default|high>.cx_open` (gauge — `max_connections`), `circuit_breakers.<default|high>.rq_pending_open` (gauge — `max_pending_requests`), `circuit_breakers.<default|high>.cx_pool_open` (gauge — `max_connection_pools`), `upstream_cx_overflow` (counter), `upstream_cx_pool_overflow` (counter). `upstream_rq_pending_overflow` is ALREADY LIVE (phase 41 wired it for `max_requests`; AMEND-CB2 — `max_pending_requests` shares the same counter). Phase 43.1 makes `cx_open` + `rq_pending_open` + `upstream_cx_overflow` go LIVE; whether the surface grows is the new-CB-bearing-fixture roster (~+14/CB cluster, the `0074` precedent) plus any reference-confirmed NEW names — a SPEC pin (§5, D-CP-STATS).
- **Determinism is again CONCURRENCY-driven — the phase-41 release-barrier model carries forward verbatim.** Filling `max_connections` with N held-open connections, confirming the pend with a polled gauge, firing the overflow, and releasing via a barrier is the EXACT `0074` shape — reuse `BlockingHoldResponder` (BackendKind 36) + the `/__release` control port + sequential-per-side + poll-the-gauge, NEVER a `time.Sleep` (`reference_concurrency_differential_release_barrier` + `reference_differential_band_sigma_margin`). For 43.2 the multiplex proof is a *count-ratio* assertion (many concurrent streams ride FEWER connections than requests) — possibly needing an H2-capable hold backend (a SPEC/PLAN call, D-CP-BACKEND). Phase 43 is the project's SECOND-and-THIRD concurrent-upstream-attempt control planes after hedging (42.2b), so `reference_concurrent_attempt_downstream_class_assertion` applies: assert the DOWNSTREAM response class (`downstream_rq_2xx` / the overflow 503), NOT the over-counting upstream class.

### 1.1 What phase 43 delivers as a self-contained whole (envelope: the budget/queue layer + the H2 multiplex pool)

Phase 43 lands per-protocol connection pooling across two by-concern legs, as a self-contained whole:

**Leg 43.1 — the budget substrate + pending wait-queue (ADR-0252):**

1. **The `activeConnections` + `pendingRequests` extension on `circuitBreaker`** — per-priority atomic counters added to the phase-41 `cbPriority` struct (`circuitbreaker.go:~17`), alongside the existing `activeRequests`/`maxRequests`. Plus the parsed `maxConnections`/`maxPendingRequests` budgets (phase 41 parses the `Thresholds` but stores no fields for these two — 43.1 stores them).
2. **The `max_connections` connection-creation cap** — a try-acquire at the connection-CREATION boundary (the `Cluster.Dial` raw-dial chokepoint + the `AcquireH1` pool-MISS slow path; a pool HIT reuses an already-counted connection and needs no permit, since idle pooled conns keep `upstream_cx_active` incremented). On the cap being reached, the request does NOT 503 — it PENDS (Fork-3 below).
3. **The `max_pending_requests` bounded wait-queue** — the standing queue the synchronous model lacks: a request that cannot get a connection (cap reached, no idle conn) joins a bounded wait-queue (`pendingRequests` < `maxPendingRequests`), blocking its own goroutine until a connection slot frees (a conn Close frees a permit; a `PutIdleH1` makes an idle conn available) — woken via a per-cluster/per-priority condition/channel. On the wait-queue itself being full ⇒ fail-fast **503 + `upstream_rq_pending_overflow`++** (the same counter `max_requests` uses — AMEND-CB2). `rq_pending_open` reads 1 while waiters exist; `cx_open` reads 1 while at `max_connections`.
4. **Activating the dormant emit-0 stats** — `circuit_breakers.default.cx_open` (gauge) + `circuit_breakers.default.rq_pending_open` (gauge) + `upstream_cx_overflow`/`upstream_rq_pending_overflow` (counters) go LIVE for DEFAULT priority; HIGH stays emit-0 (no priority routing; AMEND-CB-precedent).
5. **The differential fixture `0078-connection-pool-...`** — `max_connections:N` + `max_pending_requests:M` against `BlockingHoldResponder`: fill N held conns, fire M more → poll `cx_open==1`/`rq_pending_open==1` (the release barrier), fire one more → cross-side 503 (downstream class) + `upstream_rq_pending_overflow` delta; `/__release` → drain. §6.

**Leg 43.2 — the H2 multiplex connection pool (ADR-0253; SUPERSEDES ADR-0056):**

6. **The per-endpoint H2 `ClientConn` pool** — reuse `ClientConn`s across requests: acquire a conn with stream capacity, else dial a new one (budget-gated by the 43.1 `max_connections`), else PEND (the 43.1 wait-queue). Replaces the `router_h2.go:~109` `defer cc.Close()` per-request-fresh discipline with an acquire-from-pool / return-to-pool lifecycle.
7. **`max_concurrent_streams` enforcement** — the codec reads `serverS.MaxConcurrentStreams` (`h2/client.go:~287`) but does not enforce it; 43.2 adds the per-conn active-stream count + the `min(local-cap, peer-advertised)` guard governing when a conn is "full" and a new conn must be dialed.
8. **GOAWAY-driven conn rotation** — a conn that receives GOAWAY (the `goawayCh` signal already exists) is marked draining: no new streams assigned, closed when its last in-flight stream finishes. The ADR-0056 §Consequences "GOAWAY-driven conn rotation" shape.

## 2. Design decisions

### 2.1 Subject confirmation: per-protocol connection pooling — the connection-pool budget/queue + the H2 multiplex pool *(Q-subject → phase 43 row registered)*

The subject is the LAST Upstream-robustness candidate: the phase-41-deferred `max_connections`/`max_pending_requests` enforcement (over a connection-pool queue) + the ADR-0056-deferred H2 multiplex pool. No new go.mod module (`cluster.v3.CircuitBreakers` is already a dep, consumed by phase 41; the `h2` codec is in-tree). The MVP envelope is the by-concern 2-leg split; the deferred edges (`max_connection_pools`, `per_host_thresholds`, `max_requests_per_connection`, HIGH binding) are §8.

### 2.2 Ambition: the FULL build — budget/queue AND a real H2 multiplex pool *(Q-ambition → Fork 1)*

**Fork 1 (chosen): the full build.** BOTH the budget/pending-queue layer AND a real H2 multiplex connection pool (reopening + superseding ADR-0056). Chosen over **budget-enforcement-only** (rejected: leaves the "per-protocol connection POOLING" name half-delivered — it would only add budgets over the existing model and leave H2 per-request-fresh, with ADR-0056 standing; the name and the family-closing mandate call for the pool itself) and **no-queue hard-503** (enforce `max_connections` as a fail-fast 503 like `max_requests`, no pending queue — rejected: a RECORDED DEPARTURE from the reference, which soft-throttles `max_connections` by pending; the phase-41 SPEC explicitly identified the missing queue as the reason to defer to THIS row, so building it is the point).

### 2.3 Split axis: by-concern, 43.1 (budget + queue) then 43.2 (H2 pool) *(Q-split → Fork 2 → ADR-0252 + ADR-0253)*

**Fork 2 (chosen): by-concern.** 43.1 = the budget substrate + pending wait-queue (`max_connections` + `max_pending_requests` over the EXISTING model — H1 pool + H2 per-request-fresh; activate the emit-0 stats). 43.2 = the H2 multiplex pool (supersede ADR-0056). Chosen over **by-protocol** (43.1 H1 + budgets / 43.2 H2 pool + budgets — rejected: H2 gets no budget enforcement until leg 2, and the queue substrate spans both legs, coupling them) and **single flat phase** (rejected: exceeds the ADR-0045 gate; §1.4). The by-concern axis (i) isolates the risky ADR-0056 supersession + the novel multiplex machinery to leg 2, (ii) lands a complete, differential-provable budget/queue feature in leg 1 that discharges the phase-41 deferral, and (iii) gives leg 2 the budgets-already-enforced substrate so the H2 pool work is purely the pool + multiplexing.

### 2.4 The enforcement lifecycle: try-acquire-or-PEND at connection creation; the wait-queue wakes on permit-free/idle-return *(self-answered; pinned at SPEC, D-CP-LIFECYCLE)*

`max_connections`: a request needing a NEW connection (H1 pool-miss, or any H2 dial in 43.1's pre-multiplex world / a pool-miss in 43.2) try-acquires a connection permit (`activeConnections` < `maxConnections`). A pool HIT (H1 idle conn, or a 43.2 H2 conn with stream capacity) needs no permit. On the cap being reached, the request joins the wait-queue (`max_pending_requests` below) — it does NOT 503. Release: a connection permit frees on conn Close (the `connWithGauge` path); an idle H1 conn becomes available on `PutIdleH1`; an H2 conn frees a stream slot on stream finish. Each of these wakes a waiter. `max_pending_requests`: a request that cannot immediately get a connection increments `pendingRequests` (if < `maxPendingRequests`) and blocks until woken (a permit/idle-conn/stream-slot frees) or until its own context cancels; on the wait-queue being full ⇒ 503 + `upstream_rq_pending_overflow`. The PRECISE semantics — whether `max_connections` counts pooled-idle H1 conns or only in-use (the phase-41 D-CB-LIFECYCLE question, now load-bearing), the exact wake fairness (FIFO vs LIFO), the wait-queue-full vs permit-free race, the context-cancel-while-pending release point, and whether the reference's `max_connections` pend is observable as a gauge transition before the overflow — are SPEC pins (D-CP-LIFECYCLE), executed live against `contrib-v1.37.2`.

### 2.5 The H2 multiplex pool: acquire-with-capacity / dial-budget-gated / pend; stream-count + GOAWAY *(self-answered; pinned at SPEC, D-CP-H2POOL)*

A per-endpoint pool of reusable `ClientConn`s. Acquire: pick a pooled conn whose active-stream count < `min(local-cap, peer MaxConcurrentStreams)`; else dial a new conn (budget-gated by 43.1's `max_connections`); else PEND (43.1's wait-queue, woken by a stream-slot freeing). A stream finishes ⇒ decrement the conn's stream count ⇒ the conn re-offers capacity (or closes if draining + empty). GOAWAY ⇒ mark the conn draining (no new streams), close on last-stream-finish. The exact pool keying (per-endpoint vs per-host-per-priority), the new-conn-vs-wait-for-stream-slot preference when both a dial-permit and a busy-but-not-full conn are available, the `min(local, peer)` local cap default, and the reference's connection-vs-stream accounting (does the reference count an H2 conn against `max_connections` per conn or per stream) are SPEC pins (D-CP-H2POOL).

### 2.6 Deferred-policy posture: additive config (the existing `circuit_breakers` surface); NO new reject surface anticipated *(self-answered; pinned at SPEC, D-CP-REJECT)*
