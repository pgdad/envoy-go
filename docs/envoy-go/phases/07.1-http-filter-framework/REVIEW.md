**M-5. `internal/filter/http/cors/cors.go::getMethod` reads `:method` from the headers map via `headers.Get(":method")`, which Go's `http.Header.Get` canonicalizes the colon-prefixed pseudo-header name in a way that returns empty.** *(`internal/filter/http/cors/cors.go:205–207` getMethod helper; cf. PROGRESS Task 18 review-loop 2 lines 1536–1538 noting this exact bug was found + fixed in HCM dispatch with raw-map access `req.Header[":method"]`)*

Task 18 review-loop 2 documented that `req.Header.Get(":method")` calls `textproto.CanonicalMIMEHeaderKey(":method")` which doesn't preserve the leading colon, so the lookup returns `""` even when the pseudo-header is present. The fix in HCM dispatch (commit `d7afd6a`) switched to raw-map access `req.Header[":method"]`. **However**, `cors.go:206` still uses the canonicalizing `headers.Get(":method")` form. In practice this works because the cors filter is reached AFTER HCM dispatch has injected `:method` (so for the actual cors filter to read the method correctly, the injection-and-read must use compatible forms).

Looking more carefully: HCM dispatch INJECTS `:method` via `req.Header[":method"] = []string{req.Method}` (raw-map write); cors's getMethod READS via `headers.Get(":method")` which canonicalizes the lookup key. Since the raw-map write stored the value under literal `:method` and the canonicalizing read looks up under `textproto.CanonicalMIMEHeaderKey(":method")` which is NOT `:method`, **the read should fail and return ""**. But cors_test.go and the chain_integration_test all pass — so something is masking this. Either: (a) the test environment uses a different injection form; (b) Go's stdlib has special-case behavior for the colon-prefix; (c) the read path is somehow tolerant.

Quick verification needed: `go doc textproto.CanonicalMIMEHeaderKey` says it accepts only ASCII letters, digits, hyphens; non-conforming keys are returned unchanged. The leading `:` is non-conforming, so CanonicalMIMEHeaderKey returns `:method` unchanged — meaning `headers.Get(":method")` DOES find the value at `req.Header[":method"]`. The Task 18 review-loop 2 finding (which was about a DIFFERENT lookup pattern — checking for ABSENCE of `:method` via `if req.Header.Get(":method") == ""`) was a real bug because the absence-check returned "" both for "key absent" and "key present with empty value", which isn't useful for an idempotency guard. The cors.go usage is reading-after-known-injection, not absence-checking, so it works.

**Disposition:** Accept (initial concern was a false alarm; the cors.go pattern is correct after closer inspection). **No action required**; the doc-comment at `cors.go:198–204` could be tightened to explicitly note that `:method` survives canonicalization because of the colon-prefix tolerance in `CanonicalMIMEHeaderKey`, but this is cosmetic. Logged for awareness only.
