# Phase 36 Brainstorm — `ring_hash` (THIRD Load-balancing-family row; the family STAYS OPEN; the seam-EXTENDING hash policy)

**Status:** brainstorm complete (lifecycle-state 0 → 1). This document captures the design decisions reached during the brainstorm session for phase 36 (`load-balancer-ring-hash`), the **THIRD Load-balancing-family row** — landed on the ADR-0232 LB acquire/release seam that phase 34 (`least_request`) built and phase 35 (`random`) first reused. Phase 36 lands `Cluster.LbPolicy RING_HASH` (`envoy.config.cluster.v3`) — the project's **fourth LB policy** (after the phase-02 `roundRobin`, the phase-34 `leastRequest`, and the phase-35 `randomLB`) and its **first consistent-hashing policy**. Unlike random/least_request/round_robin, RING_HASH needs a **request-derived hash key** to pick: it is the policy ADR-0232 §Consequences names as requiring the seam's **PICK-INPUT-half widening** — "the hash-keyed RING_HASH/MAGLEV will additionally require widening `Pick` to receive a request-derived hash key … the next LB phase that lands a hash policy must plan for it, NOT expect the zero-churn drop-in." Phase 36 IS that phase.

The load-bearing facts that shape this brainstorm:

- **The seam must EXTEND, not just reuse.** ADR-0232's PICK-INPUT half is explicitly NOT general: `Pick()` takes no arguments. RING_HASH selects an endpoint by mapping a request-derived hash key onto a Ketama ring, so it requires `Pick` to RECEIVE that key. Phase 36 widens the unexported `loadBalancer` interface to `Pick(hashKey ...) (Endpoint, func(), error)` (exact signature pinned at SPEC, D-RH7) and the three existing policies (roundRobin/leastRequest/randomLB) ignore the new input. This is a **seam-EXTENDING** change → a seam ADR (ADR-0235) PLUS the policy ADR (ADR-0236) — the phase-34 TWO-ADR shape (seam + policy) recurs, in contrast to phase-35's single-ADR reuse.
- **The exported `Cluster` surface stays BYTE-STABLE — the hash key rides `ctx` (Q-seam).** Phase 34 chose OPTION C precisely to keep the exported `Cluster` surface byte-stable (zero consumer churn). Phase 36 preserves that: the consumer (tcp_proxy / the HTTP router) computes the hash key and stuffs it in the `context.Context`; `cluster.go` extracts it (a new context-key + `withHashKey`/`hashKeyFrom` helpers) and threads it to the widened internal `lb.Pick(hashKey)`. `Dial(ctx)`/`AcquireH1(ctx)` already take `ctx` → **NO exported-signature churn** across the seven Pick-path consumers (tcp_proxy/router/httpclient/thriftproxy/redisproxy/grpcclient/dial_h2). `PickEndpoint()` (no `ctx` — the httpclient `URL.Host` rewrite + the thriftproxy no-healthy-host probe) passes no key → RING_HASH falls back to a random pick there (Envoy's documented no-hash fallback). This mirrors Envoy's `LoadBalancerContext::computeHashKey()` posture exactly (the LB consumes an optional uint64 from context).
- **RING_HASH has a config message** (`Cluster.RingHashLbConfig`) — the first LB-config-parse arm since least_request. Direct inspection of the v1.32.4 module cache during this brainstorm confirms `Cluster_RING_HASH` is `Cluster_LbPolicy` enum value **2**, with a `Cluster.RingHashLbConfig` message carrying `minimum_ring_size` (`UInt64Value`), `maximum_ring_size` (`UInt64Value`), and `hash_function` (an enum: `XX_HASH` default, `MURMUR_HASH_2`). There IS a config-parse arm + PGV-parity gate (the exact PGV bounds — `min ≤ max`, both `≤ 8388608` — pinned at SPEC, D-RH1). This is heavier than random's zero-config surface and on par with least_request's `choice_count` arm.
- **Two hash-input planes (Q1 — BOTH).** The hash key originates in the data plane: tcp_proxy's `hash_policy: source_ip` (the downstream remote IP) and the HTTP router's route-level `hash_policy` (a key-source subset — header + connection-properties source-ip likely land; cookie/query/filter-state deferred — pinned at SPEC, D-RH6). Both reduce to a single uint64 fed to `Pick` — the seam extension is uniform across planes; only the COMPUTE differs. The user chose BOTH planes; the pre-authorized 36.1/36.2 split (Q-split) sequences them.
- **The distinguishing proof is AFFINITY (+ spread), not distribution.** RING_HASH's signature property is precisely what random does NOT have: STABILITY — the same hash key always maps to the same backend. Fixture(s) bind the differential client to MULTIPLE `127.0.0.x` source IPs and assert BOTH (a) **affinity** — all conns from one source IP pin to ONE backend, stable across the burst — and (b) **spread** — distinct source IPs land on different ring positions (not all-to-one). Asserted PER SIDE: cross-side host *identity* depends on byte-exact ring/hash reproduction (a SPEC empirical pin — D-RH2; if infeasible, per-side affinity+spread bands like 0059/0060). This is the strongest TRUE claim that positively separates RING_HASH from random (which would scatter the same key) and round_robin (which rotates regardless of key).

ZERO new go.mod dep (the EXISTING core `/envoy v1.32.4` dep carries the enum + config + the `type.v3.HashPolicy` + `RouteAction.HashPolicy`; D-RH1 confirms).

**Rationale (the Q0 choice among 6 candidates):** RING_HASH is the natural next primary-`LbPolicy`-enum completion (ROUND_ROBIN/LEAST_REQUEST/RANDOM done → RING_HASH/MAGLEV remain among the primary enum values; subset/locality/priority/panic are orthogonal MODIFIERS, not primary policies, and several are gated by the absent health-checking boundary). It exercises the seam-extension ADR-0232 explicitly anticipated, delivering the durable PICK-INPUT-half asset that maglev (the cheap follow-on) reuses. It is a canonical, well-understood, demonstrable capability (consistent hashing → affinity). The hash-input plumbing is real work, but it is the work the family was designed to eventually absorb.

**Anticipated ADRs:** ADR-0235 (the seam extension) + ADR-0236 (the ring_hash policy) — the phase-34 two-ADR (seam + policy) shape — §7. DECISIONS tail STAYS **ADR-0234** at this brainstorm; next-free **ADR-0235**.

### 2.2 Scope envelope: BOTH PLANES *(Q1 → pre-authorized 36.1/36.2; ADR-0235 + ADR-0236)*

**Decision:** Deliver the hash-input plumbing for BOTH data planes: (a) tcp_proxy `hash_policy: source_ip` (the downstream remote IP → uint64 key); (b) the HTTP router route-level `hash_policy` (a key-source subset — header + connection-properties source-ip likely land; cookie/query/filter-state defer, D-RH6). Plus `RING_HASH` accepted by `cluster.Manager` (the config parse + PGV gate + the byte-stable-reject text change) and the `ringHashLB` (the Ketama ring + lookup). DEFERS (§8): MAGLEV, the `load_balancing_policy` extension point, the deferred HTTP key-source sources, cookie generation, weighted-ring richness, locality/panic.

**Rationale:** The user chose BOTH planes deliberately (over the recommended tcp-only MVP), accepting the larger envelope in exchange for demonstrating consistent hashing across both the project's flagship data planes in one phase. The seam extension is plane-agnostic (both planes reduce to a uint64 fed to `Pick`), so the marginal cost of the second plane is the per-plane hash-COMPUTE + config-parse, not a second seam. The pre-authorized 36.1/36.2 by-plane split (Q-split) keeps each leg small and independently shippable: 36.1 proves the seam + policy + one plane end-to-end (the tcp_proxy plane, reusing the 0059/0060 harness); 36.2 layers the HTTP plane on the now-proven seam.

### 2.3 The hash-key delivery: ctx-carried; the exported surface stays byte-stable *(Q-seam → ADR-0235)*

**Decision:** The hash key rides `context.Context`. The consumer (tcp_proxy on new-connection / the HTTP router per-request) computes the hash and stuffs it in `ctx` via a new `withHashKey(ctx, key)` helper; `cluster.go`'s `Dial`/`AcquireH1` extract it via `hashKeyFrom(ctx)` and thread it to the widened internal `lb.Pick(hashKey)`. The exported `Cluster` method signatures (`Dial(ctx)`/`AcquireH1(ctx)`) are UNCHANGED — they already take `ctx` — so NONE of the seven Pick-path consumers (tcp_proxy/router/httpclient/thriftproxy/redisproxy/grpcclient/dial_h2) churn their call sites except the two that actually compute a hash (tcp_proxy, router). `PickEndpoint()` (no `ctx` — httpclient's `URL.Host` rewrite + thriftproxy's no-healthy-host probe) passes no key → `ringHashLB` falls back to a random pick (Envoy's documented no-hash fallback). The exact internal `Pick` signature (an `*uint64` vs a small `hashCtx` struct vs `(uint64, bool)`) + the context-key type + the no-hash fallback semantics are pinned at SPEC (D-RH7).

**Rationale:** Phase 34 chose OPTION C specifically to keep the exported `Cluster` surface byte-stable, and that discipline is worth preserving — widening the exported `Dial`/`AcquireH1`/`PickEndpoint` signatures would churn all seven consumers and re-open a surface the family deliberately froze. Carrying the hash via `ctx` is exactly how Envoy threads it (the LB consumes an optional `computeHashKey()` from the `LoadBalancerContext`); it localizes the change to (i) the one internal interface widening and (ii) the two consumers that actually produce a hash. The non-hash consumers and the three non-hash policies are entirely untouched.

### 2.4 Q-split: pre-authorized 36.1/36.2 by plane, confirm at SPEC/PLAN *(Q-split)*

**Decision:** A flat family row 36 with a PRE-AUTHORIZED by-plane escape valve — **36.1** = the ctx-carry seam extension + `ringHashLB` + manager accept/parse + the tcp_proxy `source_ip` plane (first end-to-end demonstrable hash); **36.2** = the HTTP route `hash_policy` plane. The FINAL ADR-0045 re-check at SPEC/PLAN decides whether to CONSUME the split (vs collapse to a single flat row 36).

### 2.5 Differential strategy: affinity + spread (multi-source-IP); per-side; cross-side host-identity deferred to D-RH2 *(Q-differential → fixture envelope §6)*

**Decision:** The fixture(s) bind the differential client to MULTIPLE `127.0.0.x` source IPs (the harness feasibility pinned at D-RH8) over a multi-endpoint STATIC cluster with `lb_policy: RING_HASH`, and assert BOTH: **(a) affinity** — all conns from a single source IP pin to ONE backend, stable across the burst (the consistent-hash signature property — RANDOM scatters the same key, round_robin rotates regardless); **(b) spread** — distinct source IPs land on different ring positions (not all-to-one — a degenerate single-entry ring would fail this). Asserted via the EXISTING `DistributionAsserter` with **PER-SIDE** semantics: cross-side host *identity* (does source-IP X pin to the SAME backend on both subject and reference?) requires byte-exact ring construction + key hashing (xxHash64/murmur2 + the Ketama layout) — a SPEC empirical pin (D-RH2). IF byte-exact reproduction is feasible, the fixture asserts cross-side-exact host identity (the strongest claim); IF NOT, it falls back to per-side affinity+spread bands (the 0059/0060 precedent). PLUS a cross-side `StatsAsserter` prong on cluster counters (cross-equal-vs-per-side disposition per D-RH4 — anticipated identical to 0059/0060). 36.1 → a tcp_proxy fixture (`0061-lb-ring-hash`, source-IP affinity); 36.2 → an HTTP fixture (header-based affinity). A ring-config boot-reject dir if D-RH1's PGV gate warrants one (a separate dir per `reference_differential_fixture_dispatch_constraint`). Every live assertion proven via a deliberate-break with `-count=1` (`reference_differential_break_protocol_count1`) — the affinity break ("scatter the same key" → fails affinity) and the spread break ("collapse to one ring entry" → fails spread) both bite.

**Rationale:** RING_HASH's interesting property is AFFINITY (stability), not distribution — the proof must positively separate it from random (same key → SAME backend, not a fresh draw) and round_robin (key-determined, not rotation). The multi-source-IP harness (binding the client to `127.0.0.x`, x∈{2,3,4,…}) is what makes BOTH affinity AND spread observable in one fixture: each distinct IP is a distinct key (affinity within an IP, spread across IPs). Cross-side host identity is the hard part — it depends on reproducing Envoy's exact ring (the hash function over the endpoint identifiers + the Ketama replication count + the lookup direction); D-RH2 determines whether that is byte-feasible, and the fixture's assertion strength follows. The per-side fallback (affinity+spread bands) is always available and is the 0059/0060 precedent. The deliberate-breaks are sharp: an implementation that scattered (accidentally implemented random) fails affinity; one that collapsed the ring fails spread.
