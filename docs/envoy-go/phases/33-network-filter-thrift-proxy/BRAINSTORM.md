# Phase 33 Brainstorm — `thrift_proxy` (SEVENTH §9 Network-filters-family row; the project's SECOND terminal routing proxy; the §9 family CLOSES after it)

**Status:** brainstorm complete (lifecycle-state 0 → 1). This document captures the design decisions reached during the brainstorm session for phase 33 (`network-filter-thrift-proxy`), the **SEVENTH §9 Network-filters-family row** (after the phase-26 family-parent + first three filters, the phase-27 `sni_cluster` flat row, the phase-28 `zookeeper_proxy` parent row, the phase-29 `mongo_proxy` parent row, the phase-31 `kafka_broker` flat row, and the phase-32 `redis_proxy` parent row; the phase-30 contrib pin-refresh was an infra row, not a family member). Phase 33 lands `envoy.filters.network.thrift_proxy` — the project's **SECOND terminal routing proxy** (after redis_proxy at phase 32). Like redis_proxy, thrift_proxy IS the connection terminator: it decodes a Thrift message, **routes** by method name to an upstream cluster, **round-trips** the request through a pooled upstream connection, and writes the reply back downstream. There is no `tcp_proxy` behind it, so there is **no passive-observe MVP** — the filter must actually serve traffic to be a valid Envoy config. **Thrift is the LAST §9 Network-filters candidate; after phase 33 phase-done the §9 Network-filters family CLOSES.**

The load-bearing facts that distinguish thrift from redis and shape this brainstorm:

- **Thrift REUSES the framework seam redis BUILT.** redis_proxy landed the framework's SIXTH structural extension — the upstream connection-pool / cluster-routing seam (ADR-0230, `internal/filter/network/upstreampool.go`) — and ADR-0230 EXPRESSLY names "thrift / a latency-or-fan-out sub-phase" as its anticipated second consumer. Phase 33 consummates that anticipation as a **REUSE** (Q-seam): the MVP consumes `UpstreamConn`/`NewUpstreamConn`/`Send`/`Reader`/`Close` unchanged (one-conn-per-downstream, synchronous single-flight, positional/FIFO reply correlation). So unlike redis, thrift lands **ZERO new framework seam** — it is a pure consumer of the existing seam plus a new filter package.
- **Thrift is a CORE `/envoy` extension, NOT `/contrib`** (a brainstorm-time correction — see §2.1). The cold-start framing (`next-prompt.txt` / `STATE.md` at master tip) repeatedly described thrift as "a `/contrib` extension like kafka_broker." Direct inspection of the vendored go module cache REFUTES this: `thrift_proxy/v3` lives in `github.com/envoyproxy/go-control-plane/envoy@v1.32.4/extensions/filters/network/thrift_proxy/v3` (CORE `/envoy`), exactly where `redis_proxy/v3` lives — NOT in `/contrib@v1.32.4` (where `kafka_broker/v3` lives). So thrift_proxy is core-`/envoy`, like redis_proxy. Anticipated **ZERO new go.mod dep** regardless (both `/envoy v1.32.4` and `/contrib v1.32.4` are already deps from ADR-0008 / ADR-0228) — but the REASON is "the existing core `/envoy` dep already carries it," NOT "it consumes the contrib dep." The TypeURL + dep are pinned at SPEC (D-T1, the D32-1 precedent — `proto.MessageName`, never the docs string).
- **Thrift's defining complexity is the transport×protocol matrix.** Where RESP is a single length-prefixed type system, a Thrift message is a TRANSPORT frame (`framed` / `unframed` / `header`) wrapping a PROTOCOL message (`binary` / `compact` / `twitter`). The MVP picks ONE transport×protocol pair (Q1) and decodes only the message-begin envelope (method name + message type + seq_id) under `payload_passthrough` (skip the struct body); the rest of the 3×3 matrix + full struct parsing defer.

The next sessions author the SPEC then the PLAN then the IMPL (lifecycle-state 1 → 2 for phase 33, skill `superpowers:writing-plans` scoped to **SPEC authoring** per the kafka-31 single-flat-row precedent — NO parent-SPEC/sub-phase split, since Q-split chose a single flat row). ## 2. Design decisions

### 2.1 Subject confirmation: `thrift_proxy` — core `/envoy`, NOT `/contrib` *(Q0 → phase 33 row registered)*

**Decision:** Phase 33 = `envoy.filters.network.thrift_proxy` (proto `envoy.extensions.filters.network.thrift_proxy.v3.ThriftProxy`; the module + import path + TypeURL pinned at SPEC, D-T1). The SOLE remaining §9 candidate (after redis_proxy landed at phase 32); confirmed WITH a brainstorm-time dep-framing correction.

**The `/contrib`-vs-core correction (brainstorm finding):** The cold-start framing at master tip (`next-prompt.txt` lines 14/20/43; `STATE.md` next-skill block) repeatedly described thrift_proxy as "a `/contrib` extension, like kafka_broker," consuming "the existing `github.com/envoyproxy/go-control-plane/contrib` v1.32.4 dep." Direct inspection of the vendored go module cache during this brainstorm REFUTES this:

```
github.com/envoyproxy/go-control-plane/envoy@v1.32.4/extensions/filters/network/thrift_proxy/v3   ← CORE /envoy (where thrift lives)
github.com/envoyproxy/go-control-plane/envoy@v1.32.4/extensions/filters/network/redis_proxy/v3    ← CORE /envoy (redis, for contrast)
github.com/envoyproxy/go-control-plane/contrib@v1.32.4/.../filters/network/kafka_broker/v3        ← /contrib (kafka, for contrast)
```

`thrift_proxy/v3` lives in the CORE `/envoy` module, exactly where `redis_proxy/v3` lives — NOT in `/contrib`. So thrift_proxy is a CORE extension, like redis_proxy (and UNLIKE kafka_broker). The downstream consequence ("ZERO new go.mod dep") is UNCHANGED — both `/envoy v1.32.4` (ADR-0008) and `/contrib v1.32.4` (ADR-0228) are already deps — but the REASON is "the existing CORE `/envoy` dep already carries it," exactly the redis D32-1 finding, NOT "it consumes the contrib dep added at phase 31." The reference image is likewise unaffected: thrift_proxy is a core extension present in BOTH the standard and the contrib Envoy images; the project boots the contrib image (ADR-0227, a behavioral superset), so the cross-side fixture boots there regardless. This correction is recorded so the SPEC's D-T1 confirms the CORE module path (anticipated `github.com/envoyproxy/go-control-plane/envoy/extensions/filters/network/thrift_proxy/v3`) and a clean `go mod tidy` (ZERO new dep) — NOT the `/contrib` path.

**Rationale:** thrift is the last §9 candidate; the family closes after it. redis was chosen over thrift at the phase-32 Q0 precisely because RESP is far leaner than Thrift's transport×protocol matrix + method-routing + nested sub-filter chain — so thrift inherits the heavier-protocol risk, mitigated here by (a) REUSING the now-built upstream-pool seam (Q-seam) and (b) scoping to ONE transport×protocol pair + payload_passthrough (Q1).

**Anticipated ADR:** ADR-0231 (the thrift_proxy filter; see §7) — ONE ADR (no parent-umbrella ADR since no split; no seam ADR since the seam is REUSED).

### 2.2 Scope envelope: single-pair single-route terminal *(Q1 → single flat row; ADR-0231)*

**Decision:** Deliver a single-pair single-route-terminal MVP: ONE transport×protocol pair (the chosen pair pinned at SPEC by probing the reference default — D-T2), the **Thrift message-begin codec** (transport frame + method name + message type + `seq_id`) under `payload_passthrough` (skip the struct body), `route_config` consumed as a match-all/single-method route to ONE upstream cluster, the **REUSED** upstream connection round-trip (one-conn-per-downstream, synchronous single-flight, positional/FIFO correlation), a **router-only** nested thrift-filter sub-chain, and the global `thrift.<stat_prefix>.request*/response*` **stat roster**. Every deferred field (§1.2 / §8) is either PARSE-ACCEPTED-behavior-DEFERRED or PARSE-REJECTED at config load — the disposition per field pinned empirically at SPEC (D-T4). The differential mirrors the single-route round-trip behavior exactly (downstream-RESPONSE byte-equivalence — §2.5).

**Rationale:** Because thrift_proxy is the connection TERMINATOR (no `tcp_proxy` behind it), there is no observational MVP — the leanest coherent slice is a real proxy that routes a single method (or match-all) to one cluster and round-trips a Thrift message. Picking ONE transport×protocol pair isolates the load-bearing decode surface (thrift's signature complexity) to its smallest faithful form; `payload_passthrough` further bounds it to the message-begin envelope (method name + type + seq_id — exactly what routing needs), skipping the recursive struct-skip of arg bodies. The full 3×3 matrix, full struct parsing, and full route_config richness each add surface for zero additional seam-or-routing-validation value at the MVP. Wire framing (the chosen transport + protocol) is adopted VERBATIM from upstream (`reference_wire_format_both_sides_see_same_bytes` — both the reference Envoy and envoy-go speak the same Thrift bytes to the same backend; this EXTENDS to the downstream RESPONSE bytes, which thrift_proxy GENERATES — §2.5).

### 2.3 The upstream connection-pool / cluster-routing seam: REUSED unchanged *(Q-seam → §3.1; ADR-0230, no new ADR)*

**Decision:** The thrift MVP REUSES the ADR-0230 upstream connection-pool / cluster-routing seam (`internal/filter/network/upstreampool.go`) UNCHANGED: `NewUpstreamConn(dial, onRequest)` over a dial closure (`cluster.Cluster.Dial`, keeping `internal/filter/network` free of an `internal/cluster` import — the `upstreamcluster.go` decoupling discipline), `Send`/`Reader`/`Close`, one-conn-per-downstream, synchronous single-flight, positional/FIFO reply correlation. Thrift's `seq_id` is parse-validated (decoded, available for assertions / a future feature) but NOT correlation-load-bearing for the MVP (the synchronous single-flight pump reads exactly one reply per `Send` — positional correlation suffices; the seq_id echo is verified, not relied upon for demux). The deferred ADR-0230 surface (seq_id-keyed correlation / a shared per-host pool / a >1-depth pending queue / the two-goroutine pipelined model / the ADR-0223 per-conn mutex) stays DEFERRED — a future thrift latency/fan-out sub-phase consumes it (exactly the "thrift / a latency-or-fan-out sub-phase reuses/extends it" surface ADR-0230 names).

**Rationale:** ADR-0230 was deliberately landed redis-scoped (YAGNI) at 32.1 with thrift named as the anticipated SECOND consumer. The thrift MVP is a synchronous request-response proxy over a single connection — exactly the one-conn-per-downstream synchronous single-flight model the seam already provides. EXTENDING the seam now (seq_id-keyed multiplexing / a shared pool) would be speculative generalization against a feature (out-of-order multiplexing) the MVP does not exercise — the speculative-generalization trap the YAGNI scoping was designed to avoid. Reusing it unchanged VALIDATES the seam-scoping discipline (the seam's first reuse is clean → the redis-scoping was right-sized) and keeps phase 33 framework-ZERO-touch. The `upstream_cx_*` per-side pooling-stat asymmetry the reference may exhibit (its pool internals vs envoy-go's one-conn-per-downstream) is pinned per-side, NOT equality (the redis D-P32-9 / `reference_close_direction_framework_gap` precedent — D-T9).

### 2.4 Thrift reply correlation is POSITIONAL for the MVP, despite seq_id *(self-answered — single-flight bounds it)*

**Decision:** Unlike RESP (no correlation id), the Thrift protocol DOES carry a correlation identifier — the `seq_id` (i32) in the CALL message, echoed in the REPLY. But for the single-flight MVP (one request in flight per connection at a time), reply correlation is POSITIONAL: per upstream connection, the synchronous pump sends one request and reads exactly one reply (a degenerate depth-1 FIFO queue — the redis 32.1 model). The seq_id is decoded and MAY be validated (the reply's seq_id == the request's seq_id), but it is NOT used to demultiplex concurrent in-flight requests (none exist at the MVP). The exact multiplexing model is REUSED from ADR-0230 (one upstream conn per downstream conn). seq_id-keyed demux (multiple in-flight requests, replies returning out of order, matched by seq_id) is DEFERRED with the rest of the multiplexing surface (§8).

**Rationale:** Thrift's seq_id makes out-of-order multiplexing POSSIBLE (the deferred surface), but the MVP's single-flight envelope keeps the pending queue trivially depth-1 and in-order — so positional correlation is faithful and simpler than a seq_id→request map. This mirrors the redis §2.4 positional-correlation decision (reached there because RESP has NO correlation id; reached here DESPITE seq_id existing, because single-flight makes it moot). Validating the seq_id echo (without relying on it for demux) is a cheap correctness check the SPEC may add to the differential.

### 2.5 Differential strategy: synthesized Thrift backend + cross-side StatsAsserter + downstream-response equivalence *(self-answered → fixture envelope §6)*

**Decision:** Hermetic fixtures with a NEW BackendKind — a synthesized **`TCPThriftResponder`** that speaks minimal Thrift in the chosen transport×protocol pair (canned REPLY frames for the exercised methods: a success REPLY struct, an application EXCEPTION, etc.); chain `[thrift_proxy]` as the TERMINAL on BOTH sides (the contrib reference Envoy `envoyproxy/envoy:contrib-v1.37.2` + envoy-go; NO `tcp_proxy` — thrift_proxy terminates) routing the match-all/single-method route to that backend; the driver sends real Thrift CALL messages as a Thrift client would. The differential proof is TWO-pronged: (1) **downstream-RESPONSE byte-equivalence** — the Thrift reply bytes returned to the client must be byte-identical cross-side (the §9 SECOND row whose downstream RESPONSE bytes are load-bearing — after redis-32; because thrift_proxy GENERATES the downstream response by proxying, it does not pass observed bytes through); (2) **cross-side `StatsAsserter`** over the mirrored `thrift.<stat_prefix>.request*`/`response*` counters. `upstream_cx_*`/pooling stats that depend on connection-reuse internals are pinned per-side (not equality) where the reference diverges (`reference_close_direction_framework_gap` / redis D-P32-9 precedent — D-T9). Every assertion proven live via a deliberate-break with `-count=1` (`reference_differential_break_protocol_count1`). The reference parses the full message (`reference_differential_reference_parses_full_message` — the `TCPThriftResponder` replies are fully-valid Thrift frames; any abandon-at-close `*.failure` asymmetry pinned per-side, not equality). NO real Thrift server.

**Rationale:** A terminal routing proxy's correctness is its downstream responses — so (like redis, unlike the sniffer rows) the load-bearing proof is downstream-response byte-equivalence PLUS stat parity. A synthesized `TCPThriftResponder` with canned replies keeps the upstream deterministic (a real Thrift server adds container weight + a real service definition + nondeterministic framing). The cross-side fixture boots on the contrib reference image (thrift_proxy is a core extension, present in the standard image too — but the project standardized on the contrib image at ADR-0227, a behavioral superset). The new BackendKind (anticipated value 33) is the thrift analogue of the `TCPRedisResponder` (BackendKind 32) — synchronous, positional, with a seq_id-echo in the reply (validated, not demux-load-bearing — §2.4).

### 2.6 Deferred-active-feature posture: parse-accept vs parse-reject per field *(per Q1 — pinned at SPEC, D-T4)*

**Decision:** The deferred surface (§1.2 / §8) splits into (a) PARSE-ACCEPTED-behavior-DEFERRED fields (the config parses without error, kept at defaults in fixtures, behavior lands later — the redis `prefix_routes` / mongo `header_delay` precedent) and (b) PARSE-REJECTED fields (config-load error — the strict posture for fields whose silent-ignore would be a correctness hazard). The per-field disposition is pinned empirically at SPEC (D-T4) by matching the reference Envoy's own parse behavior. Anticipated: `transport`/`protocol` enum values for the un-chosen pairs + `route_config` richness + the non-router `thrift_filters` + `max_requests_per_connection` + `access_log` parse-accepted (they have safe defaults or are observ-only); a required `stat_prefix` (and possibly a required `route_config`) PARSE-REJECTED when absent; whether the reference rejects an un-implemented transport/protocol value, or accepts it and fails at runtime, is the key D-T4 pin (it governs whether the MVP's "one pair" is enforced at parse or at decode).

**Rationale:** Parse-accepting unconsumed fields keeps the config-parse surface faithful (the reference accepts a config with `thrift_filters` set; envoy-go must too) while the behavior lands later or stays a coverage boundary. The exact split is an empirical pin because silent-ignore-vs-reject is a per-field upstream-faithfulness question, not a design choice (`reference_wire_format_both_sides_see_same_bytes` generalized to config parse).

### 2.7 Stat surface: global request/response counters under `thrift.<stat_prefix>.` *(self-answered per §9 precedent; SPEC pins roster)*

**Decision:** Mirror upstream's thrift stat families under the `thrift.<stat_prefix>.` scope: the GLOBAL request/response counters (`request`, `request_call`, `request_oneway`, `request_invalid_type`, `request_decoding_error`, `response`, `response_reply`, `response_success`, `response_error`, `response_exception`, `response_invalid_type`, `response_decoding_error`, `response_business_exception`, … — the exact roster + which are eager pinned at SPEC, D-T3) — a FIXED, table-bounded roster (NOT per-method-dynamic, contrast redis's per-command-dynamic / kafka's per-api-key — Thrift's global stats are not keyed on the method name; the method name drives ROUTING, not a counter, in the MVP). A new `thrift.` Prometheus tag-extractor arm at `internal/stats/name.go` (the kafka INLINE / mongo MULTI-label / redis SINGLE-label-hoist contrast — the shape pinned at SPEC, D-T3). Because the roster is FIXED (not wire-derived per-method), `stats.IsValidName` is likely satisfied BY CONSTRUCTION (the redis static-table posture, D-P32-7) — UNLESS the reference emits per-route or per-method stats with wire-derived segments (then the `IsValidName` guard at the codec boundary is load-bearing — D-T7; the `FuzzThriftDecode` no-panic fuzzer needs it regardless). The latency-histogram family is DEFERRED project-wide (ADR-0060). The close-direction-keyed counters `cx_destroy_local_with_active_rq` / `cx_destroy_remote_with_active_rq` are DEFERRED as a coverage boundary (the §9 close-direction-zero-touch posture — §2.8). The stat-count DELTA is `1091 → 1091 + roster` (roster TBD at SPEC).

**Rationale:** The global request/response counters are the load-bearing thrift observability surface. Because thrift's global stats are NOT keyed on the (open-ended) method name, the roster is fixed and table-bounded (contrast redis's per-command / kafka's per-api-key) — likely satisfying `IsValidName` by construction. The exact roster + the prom-arm shape + whether any per-route/per-method stat is wire-derived are pinned at SPEC against the reference.

### 2.8 Close-direction counters: DEFERRED as a coverage boundary *(self-answered per AMEND-R9; pinned at SPEC, D-T8)*

**Decision:** Thrift's `cx_destroy_local_with_active_rq` / `cx_destroy_remote_with_active_rq` counters are CLOSE-DIRECTION-keyed (local vs remote close while a request is active). The network framework records close TYPE, not DIRECTION (`reference_close_direction_framework_gap`). Per the §9 close-direction-zero-touch posture (AMEND-R9 — redis_proxy added NO `cx_destroy_*` counters; the framework-surgery sub-phase that would add close-direction keying is deferred project-wide), the thrift MVP DEFERS these two counters as a BEHAVIOR_CONTRACT coverage boundary rather than touch the framework. Confirmed at the SPEC probe (D-T8 — verify the reference's close-direction counter behavior; record the deferral; if the round-trip exercises an active-request close, pin the subject-side value as a coverage-boundary record).

**Rationale:** Touching the framework to key close counters by direction is a framework-SURGERY sub-phase (the `reference_close_direction_framework_gap` lesson — mongo-29.2 D-P4 / kafka-31 `*.failure` precedent). Phase 33 is a framework-ZERO-touch consumer row; deferring the two close-direction counters keeps it so.
