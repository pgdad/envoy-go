3. **Proto-config parsing of `envoy.extensions.filters.http.ext_proc.v3.ExternalProcessor`,** the canonical filter-level config message. Per `go-control-plane/envoy v1.32.4` (proto pin via ADR-0008 → Envoy v1.37.2 → proto v3), phase 19 consumes the dual-mode service envelope + the processing-mode envelope + the mutation envelope + the mode-override envelope + the error-posture envelope. **Consumed at runtime (the MVP-envelope fields; the SPEC §10 empirical-pin block does the exhaustive proto-field roster against reference Envoy v1.37.2):**

   - `grpc_service` (`*core.GrpcService`) AND `http_service` (`*ExtProcHttpService`) — mutually exclusive (only one MUST be set; PARSE-REJECT if both or neither). BOTH arms consumed per Q3.
   - `processing_mode` (`*ProcessingMode{request_header_mode, response_header_mode, request_body_mode, response_body_mode, request_trailer_mode, response_trailer_mode}`) — Headers + BUFFERED-body envelope per Q2: header modes ∈ {SEND, SKIP, DEFAULT}; body modes ∈ {NONE, BUFFERED}; trailer modes SKIP / PARSE-REJECT (trailers out of envelope); STREAMED + BUFFERED_PARTIAL + FULL_DUPLEX_STREAMED PARSE-REJECT (envoy-go-strict).
   - `failure_mode_allow` (bool) — on processor error/timeout, false → request denied with 500-class local reply; true → request proceeds without processor mutations (mirrors phase-18 ext_authz `failure_mode_allow`).
   - `message_timeout` (`*durationpb.Duration`) + `max_message_timeout` (`*durationpb.Duration`) — per-message deadline (default and bound for `override_message_timeout` extensions; SPEC §10 pin §19.P10 confirms the override-message-timeout proto-extension wire shape).
   - `request_attributes` (`[]string`) + `response_attributes` (`[]string`) — CEL-attribute-name allowlists for which envoy attributes are sent to the processor in request_headers / response_headers messages (the allowlist is honored per the proto's attribute-name registry; ADR-0165's 6 new callback methods feed the populated set).
   - `allow_mode_override` (bool) + `allowed_override_modes` (`[]*ProcessingMode`) — Full mode-override per Q5: when `allow_mode_override=true`, the filter re-evaluates ProcessingMode mid-stream after each `ProcessingResponse.mode_override` arrival (validated against the allow-list when configured).
   - `disable_immediate_response` (bool) — when true, `ImmediateResponse` arrivals are PARSE-REJECT-at-stream-time (processor protocol violation).
   - `mutation_rules` (`*v31.HeaderMutationRules`) — header-mutation safety validation (mirrors phase-10 header_mutation protected-header discipline; rejects mutations on protected pseudo-headers per the rules' allow/deny matchers).
   - `route_cache_action` (`ExternalProcessor_RouteCacheAction` enum ∈ {DEFAULT, CLEAR, RETAIN}) — supersedes the legacy `disable_clear_route_cache` bool (SPEC §10 pin §19.P5 confirms precedence + defaults interaction).
   - `forward_rules` (`*HeaderForwardingRules{allowed_headers, disallowed_headers}`) — top-level request-header filtering before the headers message is sent to the processor (the same ListStringMatcher discipline as phase-18 ext_authz top-level `allowed_headers`).
   - `stat_prefix` (string) — counter namespace extension if set (SPEC §10 pin §19.P4 confirms interaction with HCM stat namespace).
   - The gRPC-mode `ProcessingRequest`/`ProcessingResponse` bidi-stream envelope per the `Process` RPC; the gRPC-mode `CommonResponse{header_mutation, body_mutation, clear_route_cache, status}` → mutation mapping (§2.4); the `ImmediateResponse{status, headers, body, grpc_status, details}` → `SendLocalReply` deny mapping (§2.4).

   **Deferred fields** (silent-ignore under the inline-deferral discipline; full roster at §8): `metadata_options` (forwarding_namespaces + receiving_namespaces) — couples to the dynamic-metadata family already deferred at phases 16 + 17 + 18; `observability_mode` + `send_body_without_waiting_for_header_response` + `deferred_close_timeout` — STREAMED-only flags out of envelope per Q2; `filter_metadata` — couples to dynamic-metadata family; `disable_clear_route_cache` — subsumed by `route_cache_action` per the proto's own field comment (SPEC §10 pin §19.P5 confirms precedence); BUFFERED_PARTIAL + STREAMED + FULL_DUPLEX_STREAMED body modes — out of envelope per Q2; trailer modes (request/response_trailer_mode anything other than SKIP) — out of envelope per Q2; `ExtProcOverrides.{async_mode, request_attributes, response_attributes, metadata_options, grpc_initial_metadata}` — proto-flagged `[#not-implemented-hide:]` upstream + dynamic-metadata coupling (§2.6).

4. **Dual-mode stage dispatcher (Decision #2 → ADR-0168 + ADR-0169 + ADR-0170).** The grpc_service/http_service mutually-exclusive pair selects the transport at config-load time → produces a `processorClient` interface on the `compiledConfig`. The gRPC arm establishes a bidi-stream `Process` RPC (NEW `*grpcclient.ProcessorClient` wrapper extending the existing unary `*AuthClient`; ADR-0169) per HTTP transaction — `Send(*ProcessingRequest) error` + `Recv() (*ProcessingResponse, error)` + `CloseSend() error`. The HTTP arm POSTs a `ProcessingRequest` per stage as JSON (via `protojson`) to the configured HTTP service URI and parses the JSON `ProcessingResponse` (NEW codec; ADR-0170); per the proto constraint at `ExternalProcessor.HttpService` field comment, http_service ONLY supports headers (request + response) — body and trailer modes PARSE-REJECT when http_service is set. Both arms converge on a stage-by-stage `applyProcessorResponse` value — `{mutate-and-continue, immediate-response, error}` plus the header/body mutation set + (on immediate_response) the response status/body/headers/grpc_status. The dispatcher is async: each stage's outbound send + recv parks the decode/encode dispatch goroutine on the per-stream resume channel (mirroring the phase-09 fault async-resume primitive — `StopIteration` + a goroutine performing the call + `cb.ContinueDecoding/Encoding()` on completion) so the HCM dispatch goroutine is not blocked on network I/O. `OnDestroy` cancels the in-flight call's `context.Context` and `CloseSend`s the bidi stream.

5. **Filter-callback shape: BOTH `StreamDecoderFilter` AND `StreamEncoderFilter`.** Phase 19 is the FIRST §9 family-row to ship both — decoder side for request_headers/request_body stages + encoder side for response_headers/response_body stages. Static blank-identifier compile-time checks for BOTH interfaces. The decode-side surface: `DecodeHeaders(headers, endStream)` resolves per-route → caches `*compiledPerRoute` on filter state → if request_header_mode ∈ {SEND, DEFAULT}, returns `HeaderStopIteration` and fires the request_headers stage outbound call; if SKIP, returns `HeaderContinue`; on processor response, applies header_mutation per `CommonResponse.header_mutation` + advances ProcessingMode per `ProcessingResponse.mode_override` (when `allow_mode_override`). `DecodeData` participates when request_body_mode = BUFFERED — buffers via the ADR-0128 decode-side body-buffering primitive, fires the request_body stage outbound call once the full body is buffered, applies body_mutation per `CommonResponse.body_mutation` (replace/clear). `DecodeTrailers` SKIP/PARSE-REJECT (out of envelope per Q2). The encode-side surface mirrors decode for response_headers/response_body (with a CONDITIONAL ADR-0044 escape-valve at SPEC time per §19.P11 + §19.P12 — see §3.3).

6. **ProcessingRequest / ProcessingResponse stage state machine (Decision #1 + #4 → ADR-0171 + ADR-0172).** Per Q2 Headers+BUFFERED-body envelope: the bidi-stream state machine carries per-direction ProcessingMode + the current outstanding stage. Stages fire in proto-faithful order: request_headers → (if body BUFFERED) request_body → upstream → response_headers → (if body BUFFERED) response_body → downstream. Each stage's `ProcessingRequest` carries the populated set (request.http for headers; body bytes for body stages); each `ProcessingResponse` carries a `CommonResponse{header_mutation, body_mutation, status, clear_route_cache}` or an `ImmediateResponse{status, headers, body, grpc_status, details}`. The state machine is single-in-flight: at most one outstanding stage at any time (no STREAMED interleaving in the MVP envelope). After each `ProcessingResponse`, the filter re-evaluates ProcessingMode (per Q5: if `allow_mode_override=true` and `ProcessingResponse.mode_override` is set and is in the `allowed_override_modes` allow-list when configured, the new mode takes effect for SUBSEQUENT stages — §19.P1 confirms whether mode_override applies to the CURRENT or NEXT message). `mutation_rules` gates header_mutation safety validation; rejected mutations classify the stage as `dispInvalid` (counter increment; mirrors phase-18 ext_authz `validate_mutations`).

7. **CommonResponse mutation discipline (Decision #3 → ADR-0172).** Per Q4 Full proto-faithful: each `ProcessingResponse.CommonResponse` consumed proto-faithful:
   - `header_mutation` (`*HeaderMutation{set_headers, remove_headers}`) — applied to the current direction's header map (decode-side for request stages, encode-side for response stages). `set_headers` uses `HeaderValueOption.append_action` per the 4-arm dispatch (mirrors phase-18 ext_authz `OkHttpResponse.headers` discipline + ADR-0161 gRPC-mode portion). `remove_headers` is a `[]string` removed wholesale.
   - `body_mutation` (`*BodyMutation{oneof{body, clear_body}}`) — body replacement (string-or-bytes per the proto; SPEC §10 pin §19.P11 confirms whether `OverwriteBody` per ADR-0131 covers decode-side body replacement or whether a parallel decode-side primitive is needed) or full-clear. Honored only when the corresponding body_mode is BUFFERED (otherwise: silent-ignore per envoy-go-strict — the processor sent a body_mutation for a stage with no body buffered; counter increment as `spurious_msgs_received`).
   - `status` (`CommonResponse_ResponseStatus` enum ∈ {CONTINUE, CONTINUE_AND_REPLACE}) — CONTINUE is the default; CONTINUE_AND_REPLACE means the processor has fully replaced the request/response (combined with body_mutation+clear semantics; SPEC §10 pin §19.P11 confirms wire shape).
   - `clear_route_cache` (bool) — combined with the top-level `route_cache_action` per the precedence rule (SPEC §10 pin §19.P5 confirms). When clear, invokes `cb.ClearRouteCache()` (reuses the phase-10/phase-17 HCM-side primitive).

   `ImmediateResponse{status, headers, body, grpc_status, details}` — `SendLocalReply` deny-style emission at any stage (NOT just request_headers — the FIRST §9 row with multi-stage deny capability). `grpc_status` field added when the downstream is gRPC and the processor wants to terminate the request as a gRPC error (SPEC §10 pin §19.P2 confirms downstream-protocol-detection logic for the gRPC-status preservation). Mirrors phase-18.2 ext_authz gRPC-mode `DeniedHttpResponse` discipline.

8. **Mode-override discipline (Decision #5 → ADR-0171).** Per Q5 Full proto-faithful: when `allow_mode_override=true`, each `ProcessingResponse` MAY carry a `mode_override` (`*ProcessingMode`) field. The filter re-evaluates the effective ProcessingMode per direction (decoder or encoder) after the override arrives; subsequent stages use the new mode. When `allowed_override_modes` is non-empty, the override is validated against the allow-list (any mode not in the list is rejected; rejection classifies the message as `spurious_msgs_received` per the canonical Envoy counter; SPEC §10 pin §19.P1 confirms timing — CURRENT vs NEXT message). `max_message_timeout` bounds the per-message override timeout extensions (`override_message_timeout` proto extension; SPEC §10 pin §19.P10 confirms wire shape). STREAMED-only flags (`observability_mode`, `send_body_without_waiting_for_header_response`, `deferred_close_timeout`) PARSE-REJECT (out of envelope per Q2; envoy-go-strict; SPEC author confirms disposition vs silent-ignore at §19.P10).

### 2.9 Deny-path wire shape *(self-answered → ADR-0167 + ADR-0172)*

The exact byte-shape of the deny response (header-set ordering, content-length synthesis, content-type defaulting) is a SPEC §10 empirical-pin §19.P2 against reference Envoy v1.37.2 — mirroring the phase-09/11/12/16/17/18 `SendLocalReply` wire-shape empirical-pin discipline. ext_proc is the FIRST §9 row whose deny-path can fire at **multiple stages** — not just request_headers but also request_body + response_headers + response_body. On a non-immediate processor error with `failure_mode_allow=false`: 500-class local reply (per reference Envoy default; §19.P2 confirms). ADR-0167 anchors the filterStats + the deny-path mechanism; ADR-0172 anchors the deny-path header-set construction + grpc_status handling + multi-stage capability.

### 3.1 NEW: `*ProcessorClient` bidi-stream wrapper EXTENDING `internal/grpcclient/` *(ADR-0169)*

A new typed wrapper composed alongside the existing unary `*AuthClient` in the same `internal/grpcclient/` package — NOT a new framework family. Public surface (the SPEC author confirms the exact signature at §19.P pin):
