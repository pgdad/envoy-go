## 1. Mission summary

Phase 19 lands `envoy.filters.http.ext_proc` — Envoy's canonical external-processor filter, the FIRST §9 family-row whose configuration **delegates per-stage mutation decisions for both the request AND the response to an external service over a bidirectional gRPC stream** (or a JSON-transcoded HTTP POST per stage) — as the TWELFTH production HTTP filter in envoy-go after cors (07.1), fault (09), header_mutation (10), local_ratelimit (11), csrf (12), buffer (13), compressor (14), bandwidth_limit (15), rbac (16), jwt_authn (17), and ext_authz (18 with its 18.1+18.2 split). Per the phase-19 BRAINSTORM's 6-question dialogue the MVP envelope is: **Headers + BUFFERED body** processing mode (`ProcessingMode.{request,response}_{header,body}_mode` per Q2 — STREAMED + BUFFERED_PARTIAL + FULL_DUPLEX_STREAMED PARSE-REJECT envoy-go-strict; trailers SKIP-only); **Both service modes proto-faithful** (`grpc_service` bidi-stream + `http_service` JSON-transcoded headers-only per the proto's constraint at `ExtProcHttpService` per Q3); **Full mutation proto-faithful** (`CommonResponse.{header_mutation, body_mutation, clear_route_cache, status}` CONTINUE/CONTINUE_AND_REPLACE + multi-stage `ImmediateResponse{status, headers, body, grpc_status, details}` + `mutation_rules` gating per Q4); **Full mode-override proto-faithful** (`allow_mode_override` + `allowed_override_modes` + mid-stream re-eval + `max_message_timeout` bounding `override_message_timeout` extensions per Q5); **per-route 5th-canonical REUSE** (`ExtProcPerRoute{oneof{disabled(bool) | overrides(ExtProcOverrides)}}` maps onto the existing ADR-0125 5th canonical — the SECOND CONSECUTIVE §9 row to REUSE rather than add per Q6; NO ADR-0125 amendment paragraph).

Phase 19 is also: (i) the FIRST §9 family-row to ship a **bidirectional gRPC stream** as a load-bearing transport — phase 18.2 established unary gRPC infrastructure at `internal/grpcclient/`; phase 19 EXTENDS it with a typed bidi-stream wrapper (`*ProcessorClient` alongside the unary `*AuthClient`) per ADR-0169. (ii) the FIRST §9 family-row whose framework story is dominated by **REUSE rather than NEW** — FIVE prior framework primitives are consumed load-bearing (ADR-0158 Dialer + ADR-0165 6 callbacks + ADR-0128 decode-side body-buffering + ADR-0166 plaintext h2c upstream + phase-09 async-resume); ONE NEW primitive (the bidi-stream wrapper extending ADR-0158) + ONE NEW filter-local JSON codec (`ProcessingRequest`/`ProcessingResponse` per ADR-0170) + TWO IN-SESSION-CONFIRMED encode-side framework deltas (ADR-0174 symmetric `EncoderFilterCallbacks` extension at 19.1 + ADR-0175 encode-side body-buffering primitive at 19.2 — both REFUTED at §5.P11/§5.P12 as the empirical scrape confirmed the gaps). (iii) the FIRST §9 family-row to ship **BOTH `StreamDecoderFilter` AND `StreamEncoderFilter` participation** in a single filter package — the decoder side handles request stages, the encoder side handles response stages. Phase-14 compressor's encode-only shape (`Decoder: nil`) is the only prior precedent for encode-side participation; phase 19 spans both. (iv) the FIRST §9 family-row whose MVP envelope spans two structurally distinct service-call transports (gRPC bidi vs HTTP JSON POST) AND two structurally distinct feature classes (headers-only vs +BUFFERED-body) — the cross-product is the dominant ADR-0045 split-readiness driver (§3). (v) the FIRST §9 family-row whose deny-path (`ImmediateResponse`) can fire at **multiple stages** — request_headers AND request_body AND response_headers AND response_body — not just at request_headers as in every prior §9 row.

**This parent master SPEC carries the cross-cutting design that applies to BOTH sub-phases** — the dual-mode `compiledConfig` envelope concept, the shared per-stage state-machine value, the error-posture surface, the full §5 empirical-pin block (all 13 §10 pins resolved IN-SESSION this session per ADR-0004 — they span both sub-phases, so they live here once), the §6 empirical-finding-driven scope-revision (amendment) block, and the §7 ADR anchor map. It points down to each sub-phase's authoritative SPEC for the per-surface detail.

After phase 19, the project has proven its twelfth §9 engineering claim: *envoy-go's HTTP filter framework hosts a both-decode-and-encode-side external-processor filter that ships a stage-by-stage representation of each HTTP transaction to an external processor over either a bidirectional gRPC `Process` stream or per-stage HTTP-JSON POSTs, parks the per-stage dispatch goroutine on an async-resume leg while each stage's outbound call is in flight, applies the processor's `CommonResponse` mutations (`header_mutation` per direction per stage; `body_mutation` body/clear when the corresponding `body_mode` is BUFFERED; `status` CONTINUE/CONTINUE_AND_REPLACE; `clear_route_cache` interacting with the top-level `route_cache_action`), honors the processor's `ImmediateResponse` deny at any stage via `SendLocalReply` with optional `grpc-status` trailers when the downstream is gRPC, re-evaluates the per-direction `ProcessingMode` when the processor returns a `mode_override` validated against `allowed_override_modes`, and respects the `failure_mode_allow` / `message_timeout` / `max_message_timeout` error posture when the processor is unreachable — with OBSERVABLE-OUTCOMES byte-equivalent to reference Envoy v1.37.2 on every axis except the documented divergence-windows (STREAMED body modes, trailer modes, observability_mode, the dynamic-metadata family, the `[#not-implemented-hide:]` ExtProcOverrides fields).*

## 3. Split rationale — ADR-0045 invoked, empirically confirmed (ADR-0176)

The phase-19 BRAINSTORM §1.4 flagged ADR-0045 split-readiness **HIGH** — the SECOND §9 family-row to flag HIGH after phase 18 — and instructed the SPEC author to treat single-row as the exception requiring justification, not the default. **This SPEC author's call is: SPLIT.** The §5 empirical-pin resolution executed in this session CONFIRMS the HIGH leaning AND ENLARGES it: TWO conditional ADRs (ADR-0174 + ADR-0175) anticipated as POSSIBLE at BRAINSTORM §3.3 have BOTH been EMPIRICALLY REFUTED-AT-SPEC-TIME against the current envoy-go framework surface — confirming both fire load-bearing rather than provisionally. The drivers, now empirically grounded:

1. **The proto surface is large.** §5.P1 enumerated a **22-field `ExternalProcessor` message** + `ProcessingMode` (6) + `ExtProcPerRoute` (oneof 2 arms) + `ExtProcOverrides` (7) + `ExtProcHttpService` (1 — minimal wrapper) + `HeaderForwardingRules` (2) + `MetadataOptions` (2 nested) + the `service/ext_proc/v3` `ProcessingRequest` (6-arm oneof + 3 top-level) + `ProcessingResponse` (7-arm oneof + 3 top-level) + `HttpHeaders`/`HttpBody`/`HttpTrailers`/`HeadersResponse`/`BodyResponse`/`TrailersResponse`/`CommonResponse` (5 fields incl. ResponseStatus enum)/`BodyMutation` (3-arm oneof)/`ImmediateResponse` (5)/`HeaderMutation`/`GrpcStatus`. This is **larger than phase 18's proto surface** — phase 19 spans two proto packages (`extensions/filters/http/ext_proc/v3` for the filter config + `service/ext_proc/v3` for the bidi-stream payloads); phase 18 spanned `extensions/filters/http/ext_authz/v3` + `service/auth/v3` of similar shape but smaller cardinality.
2. **Two structurally distinct transports × two structurally distinct feature classes.** §5.P10 confirmed the `grpc_service` (bidi-stream `Process`) and `http_service` (per-stage JSON POST) arms diverge entirely in the call-and-marshal layer; §5.P9 + the `ProcessingMode` BodySendMode enum walk confirmed the headers-only and BUFFERED-body envelopes are structurally distinct sub-surfaces (the headers stages run synchronously per-stage; the BUFFERED-body stages add the decode-side ADR-0128 reuse + the NEW encode-side body-buffering primitive ADR-0175). Four quadrants — gRPC headers / gRPC body / HTTP headers / HTTP body — of which three are in MVP envelope (HTTP-mode body PARSE-REJECT per the proto's own constraint at `ExtProcHttpService` documented in §5.P10).
3. **Two CONFIRMED framework deltas, not one (REFUTED §5.P11 + §5.P12).** §5.P11's encode-side body-buffering scrape REFUTED the existence of the primitive on master tip (`chain.go:403` comment: "encode-side StopIterationAndBuffer is park-only" — no replay buffer) — **ADR-0175 fires load-bearing in 19.2**. §5.P12's encode-side callback symmetry scrape REFUTED the existence of the 6-method surface on `EncoderFilterCallbacks` (`callbacks.go:160-184` — the encode-side interface carries only ContinueEncoding + EncodeHeaders/Data/Trailers + OverwriteBody; the 7 ADR-0144+0165 accessors are decode-side-only) — **ADR-0174 fires load-bearing in 19.1**. The brainstorm anticipated 0-2 conditional ADRs; the empirical scrape confirms BOTH fire. Each is comparable in scope to phase-18.2 ADR-0165 + phase-13 ADR-0128 — substantial framework-primitive lifts.
4. **Full mutation faithfulness + Full mode-override** are each substantial sub-surfaces; §5.P3/P4 + the proto walk confirmed the `header_mutation` per-direction-per-stage + `body_mutation` body/clear + `status` CONTINUE/CONTINUE_AND_REPLACE + `mutation_rules` per-header gating + `ImmediateResponse` multi-stage + `mode_override` mid-stream re-eval surfaces.

LoC estimate (refined post-§5 + the two confirmed framework deltas): ~5500–7000 LoC production (filter package ~2500–3500 + `*ProcessorClient` bidi-stream wrapper ~250–400 + JSON codec ~400–700 + ADR-0174 callback-surface extension ~250–400 + ADR-0175 encode-side body-buffering primitive ~400–700 + two test-helpers + fixture drivers ~700–1100). **Well above the ADR-0045 1500-LoC trigger.** Combined task count estimated at ~35–45 across both sub-phases — crosses both ADR-0045 thresholds (~25 tasks, ~1500 LoC) emphatically.

The **structurally clean cut is by feature-class** (§2's table) — the BRAINSTORM §1.4 RECOMMENDED option, confirmed by the empirical pin findings. Rationale for choosing split-by-feature-class over split-by-service-mode (the phase-18 precedent):

- **Split-by-feature-class places the two framework deltas at distinct sub-phase boundaries** — ADR-0174 (encode-side callback symmetry, needed for `response_attributes` population at response_headers stage) lands at 19.1; ADR-0175 (encode-side body-buffering, needed for `response_body_mode = BUFFERED`) lands at 19.2. Each sub-phase's framework lift is bounded and reviewable independently.
- **gRPC is the "real" deployment shape for ext_proc** — the `http_service` arm is a proto-constrained-to-headers-only secondary mode (per the `ExtProcHttpService.http_service` doc-comment quoted at §5.P10). Splitting by service-mode would put the major surface in 19.2 and the minor (headers-only HTTP) in 19.1 — inverted from phase 18.x where the HTTP arm was the foundational larger half.
- **Headers-stage MVP is operationally useful in itself** — 19.1 alone delivers a usable ext_proc filter (header injection, mutation, immediate_response deny, mode-override). 19.2 extends to body manipulation. The phase-13 buffer + phase-14 compressor + phase-18.1 ext_authz pattern (foundational scaffold first, feature-extension second) holds.
- **The body-stage framework primitives (ADR-0175) land alongside their consumers** at 19.2, avoiding the "framework introduced at sub-phase N, first consumer at sub-phase N+M" anti-pattern.

The split is SPEC-time (ADR-0045), decided in this session after the empirical-pin resolution + the §5.P11/§5.P12 in-session REFUTATIONS. **ADR-0176 records the split-application decision in full at this SPEC commit** (mirroring phase-08's ADR-0084 + phase-18's ADR-0164 documentation-of-application ADRs). ## 4. Cross-cutting decisions (apply to BOTH 19.1 and 19.2)

### 4.1 Dual-mode `compiledConfig` envelope + the per-stage state-machine convergence

Both sub-phases share one `compiledConfig` shape and one per-stage state-machine value. The `ExternalProcessor.grpc_service` and `ExternalProcessor.http_service` fields are NOT in a proto oneof (§5.P1 finding — both are top-level optional fields with operator-side mutual-exclusion); the envoy-go factory enforces mutual-exclusion at parse time. The selected arm is resolved at config-load time → produces a `processorClient` interface on the `compiledConfig` (the gRPC arm produces a `*grpcclient.ProcessorClient` bidi wrapper; the HTTP arm produces an HTTP-JSON per-stage POST client). Both transport arms converge on a per-stage `ProcessingResponse` value; the response-application logic (apply `CommonResponse.header_mutation` per direction; if `body_mode = BUFFERED` apply `body_mutation`; if `status = CONTINUE_AND_REPLACE` apply combined-replacement; if `clear_route_cache` interact with `route_cache_action`; OR if `immediate_response` is set, emit `SendLocalReply` and terminate stream; OR if `mode_override` is set and `allow_mode_override` is true, validate against `allowed_override_modes` and update per-direction ProcessingMode) is **mode-agnostic** — the same logic applies regardless of whether the response arrived over the bidi-stream or the JSON POST. The bidi-stream lifecycle (`OnDestroy` cancels in-flight call + `CloseSend` at stream-end) is gRPC-mode-specific; the per-stage POST cancellation (`OnDestroy` cancels in-flight `http.Client.Do`) is HTTP-mode-specific. 19.1 defines the envelope with **headers stages only** (body-modes PARSE-REJECT anything other than NONE); 19.2 extends to BUFFERED-body. ADR-0168 anchors the envelope; its §Decision lands at 19.1 IMPL and is **amended at 19.2 IMPL** to lift the body-mode PARSE-REJECT.

### 4.2 `grpc_service` and `http_service` are top-level optional fields — the factory rejects both-or-neither

§5.P1 confirmed that `ExternalProcessor.grpc_service` (#1) and `ExternalProcessor.http_service` (#20) are NOT in a proto `oneof` (unlike `ExtAuthz.services` which IS a oneof at phase 18). Both are top-level optional message-typed fields. The envoy-go factory must reject a config with both set OR neither set with envoy-go-strict errors (mirrors the phase-18 ext_authz empty-services-oneof discipline + extends to a both-set check). The exact field-doc text is quoted at §5.P1 ("Only one of `grpc_service` or `http_service` can be set. It is required that one of them must be set.").

### 4.3 V3-only proto pin (ADR-0008) + GoogleGrpc PARSE-REJECT

The `grpc_service` field is a `*core.GrpcService`; its `GoogleGrpc` arm PARSE-REJECTs envoy-go-strict (envoy-go uses the Go `google.golang.org/grpc` library; only the `EnvoyGrpc` cluster-reference arm is consumed) — inherited from phase-18.2 ADR-0157 §Decision AMENDMENT. The proto's `core.GrpcService.initial_metadata` SILENT-IGNORED for MVP (couples to a future control-plane metadata family); `core.GrpcService.retry_policy` SILENT-IGNORED for MVP (gRPC retry is a follow-up). The `ExtProcHttpService.http_service.server_uri.uri` is V3-only-validated per ADR-0008 (the `HttpUri.uri` field is bound to the V3 proto pin).

### 4.4 Deferred-field discipline (inline-deferral per phase-11 SPEC §8.1)

Both sub-phases honor the inline-deferral discipline (no omnibus deferral ADR; deferrals grouped by family-coupling, auditable in the ADR-0040 deferral trail). The cross-cutting deferral set surfaced by §5.P1's exhaustive proto-field roster: STREAMED + BUFFERED_PARTIAL + FULL_DUPLEX_STREAMED `BodySendMode` enum values (out of envelope per Q2; PARSE-REJECT envoy-go-strict — the streaming-body framework lift is deferred to a follow-up phase); request_trailer_mode + response_trailer_mode anything other than SKIP (trailers out of envelope per Q2); `observability_mode` (#17) + `send_body_without_waiting_for_header_response` (#21) + `deferred_close_timeout` (#19) (STREAMED-only flags out of envelope per Q2 — PARSE-REJECT envoy-go-strict); `metadata_options` (#16) + `filter_metadata` (#13) (dynamic-metadata family — already blocked at phases 16+17+18 forward-pointers); `ExtProcOverrides.{async_mode, request_attributes, response_attributes}` (proto-flagged `[#not-implemented-hide:]` upstream — silent-ignore per the not-implemented convention) + `ExtProcOverrides.{metadata_options, grpc_initial_metadata}` (dynamic-metadata family + initial-metadata family — both already deferred per phase-18.2 SPEC §2.6 + §8); the `CommonResponse.trailers` field (proto-flagged `[#not-implemented-hide:]`); `ProcessingResponse.dynamic_metadata` (dynamic-metadata family); `ProcessingRequest.metadata_context` (dynamic-metadata family — populated as empty proto for forward-compat); `HttpHeaders.attributes` (proto-flagged DEPRECATED + `[#not-implemented-hide:]` — superseded by `ProcessingRequest.attributes`). ### 5.1 §19.P1 — `ProcessingResponse.mode_override` timing (RATIFIED-AND-REFINED)

**Probe:** Verbatim read of `ProcessingResponse.mode_override` proto doc-comment in `external_processor.pb.go`.

The `ProcessingResponse.mode_override` field doc-comment states: *"Override how parts of the HTTP request and response are processed for the duration of this particular request/response only. Servers may use this to intelligently control how requests are processed based on the headers and other metadata that they see. This field is only applicable when servers responding to the header requests. If it is set in the response to the body or trailer requests, it will be ignored by Envoy. It is also ignored by Envoy when the ext_proc filter config `allow_mode_override` is set to false, or `send_body_without_waiting_for_header_response` is set to true."*

**Disposition: RATIFIED-AND-REFINED.** The brainstorm §2.5 hypothesis ("mid-stream re-evaluation") holds, but with three REFINEMENTS captured: (a) `mode_override` is ONLY honored when received in response to `request_headers` or `response_headers` ProcessingRequests — `mode_override` arriving in a body-stage or trailer-stage response is IGNORED (not classified as `spurious_msgs_received`; silently dropped per the proto doc "it will be ignored by Envoy"); (b) `mode_override` is also ignored when `allow_mode_override=false`; (c) the third gate (`send_body_without_waiting_for_header_response=true`) is irrelevant for envoy-go since that flag is STREAMED-only and PARSE-REJECTs per §19.P10. The override's effect propagates to SUBSEQUENT stages — the proto doc does not state CURRENT-vs-NEXT explicitly, but the "for the duration of this particular request/response only" wording + the "ignored on body/trailer responses" wording together imply that mode_override on a request_headers response affects the request body/trailer stages and the response stages going forward; mode_override on a response_headers response affects only the response body/trailer stages going forward. §6 amendment 1 documents.

### 5.2 §19.P2 — `ImmediateResponse.{status, grpc_status}` + downstream-protocol detection (RATIFIED)

**Probe:** Verbatim read of `ImmediateResponse` field types/doc-comments in `external_processor.pb.go` + `GrpcStatus` field shape + `ExtAuthz.DownstreamProtocol()` callback semantics in `internal/filter/http/callbacks.go`.

`ImmediateResponse` has 5 fields: `status` (`*v32.HttpStatus`, PGV-required — "The response code to return"); `headers` (`*HeaderMutation`, optional — "Apply changes to the default headers, which will include content-type"); `body` (`[]byte`, optional — "The message body to return with the response which is sent using the text/plain content type, or encoded in the grpc-message header"); `grpc_status` (`*GrpcStatus`, optional — "If set, then include a gRPC status trailer"); `details` (`string`, optional — "A string detailing why this local reply was sent, which may be included in log and debug output (e.g. this populates the %RESPONSE_CODE_DETAILS% command operator field for use in access logging)"). `GrpcStatus` is `{status uint32}` — the gRPC status code as an integer.

**Disposition: RATIFIED.** The deny-path wire shape mirrors phase-18.2 ext_authz `DeniedHttpResponse` discipline with three additions: (a) `headers` is a `*HeaderMutation` (a sum of `set_headers []HeaderValueOption` + `remove_headers []string`), NOT a plain `[]HeaderValueOption` — the IMPL applies the SET-or-APPEND-or-REMOVE discipline of `HeaderMutation` rather than the simpler add-only of `DeniedHttpResponse.headers`; (b) the gRPC-downstream-detection logic for grpc_status trailer injection is by request-header `content-type: application/grpc` (the standard gRPC-over-h2 marker that HCM observes on the decode side) — NOT via the `DownstreamProtocol()` callback (which returns `"HTTP/1.1"`/`"HTTP/2"`, not gRPC-vs-non-gRPC) — the IMPL sniffs the request `content-type` to determine whether to translate `grpc_status` to a `grpc-status: <uint32>` trailer; (c) `body` is sent with `content-type: text/plain` per proto doc by default, OR encoded in the `grpc-message` header for gRPC downstreams (per the same proto doc-line). The local-reply emission goes through `SendLocalReply(status, body, headers)` per ADR-0085 + the existing phase-09/11/12/16/17/18 deny-path discipline. §6 amendment 2 documents. ext_proc is the FIRST §9 row whose deny-path can fire at **multiple stages** (request_headers + request_body + response_headers + response_body — body-stage variants land at 19.2).

### 5.3 §19.P3 — `mutation_rules` header-rejection discipline (RATIFIED)

**Probe:** Verbatim read of `ExternalProcessor.mutation_rules` proto doc-comment + `HeaderMutationRules` type (cross-referenced in `config/common/mutation_rules/v3/mutation_rules.pb.go`).

`ExternalProcessor.mutation_rules` (#9) is `*v31.HeaderMutationRules`; its doc-comment states: *"Rules that determine what modifications an external processing server may make to message headers. If not set, all headers may be modified except for "host", ":authority", ":scheme", ":method", and headers that start with the header prefix set via `header_prefix` (which is usually "x-envoy"). Note that changing headers such as "host" or ":authority" may not in itself change Envoy's routing decision, as routes can be cached. **Disposition: RATIFIED.** The brainstorm §2.4 hypothesis (`mutation_rules` gating; envoy-go-strict header-mutation safety validation per phase-10 header_mutation discipline) holds. Built-in unconditional protections (host/:authority/:scheme/:method/x-envoy-*) apply as floor when `mutation_rules` is unset; when `mutation_rules` is set, the operator's rules SUPERSEDE the built-in floor (per the proto doc "all headers may be modified except for..." — the "except for" set is the default floor; an explicit `mutation_rules` config replaces it). §6 amendment 3 documents.

### 5.5 §19.P5 — `route_cache_action` precedence vs `disable_clear_route_cache` (RATIFIED)

**Probe:** Verbatim read of `ExternalProcessor.disable_clear_route_cache` (#11, bool) doc + `ExternalProcessor.route_cache_action` (#18, enum) doc + `ExternalProcessor_RouteCacheAction` enum value docs in `ext_proc.pb.go`.

`disable_clear_route_cache` doc: *"Prevents clearing the route-cache when the `clear_route_cache` field is set in an external processor response. The route-cache-clear emission goes through the existing `cb.ClearRouteCache()` HCM-side primitive (already used by phase-10 header_mutation + phase-17 jwt_authn). §6 amendment 5 documents. **The `route_cache_action` field also only applies to "in response to request headers"** — per the enum value doc — so the IMPL only consults it on the request_headers stage response; body-stage and response-stage `CommonResponse.clear_route_cache` arrivals do NOT trigger route-cache-clear (the proto doc "This field is ignored in the response direction" on `CommonResponse.clear_route_cache` confirms; ADR-0172 documents).

### 5.7 §19.P7 — `clear_route_cache` + per-route override re-resolution after route changes (RATIFIED-PENDING-IMPL-TIME)

**Probe:** Cross-references against phase-10 header_mutation's `cb.ClearRouteCache()` plumbing + phase-17 jwt_authn's per-route re-resolution discipline + the existing framework TPFC resolution machinery at `internal/filter/http/perroute.go`.

When `cb.ClearRouteCache()` fires mid-stream (triggered by `route_cache_action = CLEAR` OR `route_cache_action = DEFAULT + CommonResponse.clear_route_cache = true`), the framework re-resolves the HCM route. The re-resolution MAY select a different RouteEntry → a different `ExtProcPerRoute` config. The question: does the new per-route config take effect on SUBSEQUENT stages of the current bidi-stream, or does the stream continue with the originally-resolved per-route?

**Disposition: RATIFIED-PENDING-IMPL-TIME.** The framework's per-route resolution discipline (`RequestRouteConfig()` callback per ADR-0073 — most-specific override) is goroutine-safe and re-callable; the IMPL settle is whether to re-resolve at each subsequent stage's outbound-call construction time (cache-invalidating) or to lock in the per-route at first resolution (cache-on-first-use). The phase-10 header_mutation precedent uses cache-on-first-use; the phase-17 jwt_authn precedent uses cache-on-first-use. The phase-19 IMPL recommendation (subject to fixture-harness empirical confirmation against reference Envoy v1.37.2): **cache-on-first-use** — the per-route config resolved at `DecodeHeaders` time stays in effect for the entire bidi-stream's lifetime, even across `ClearRouteCache` invocations. ### 5.9 §19.P9 — `ProcessingMode` default-application discipline (RATIFIED)

**Probe:** Verbatim read of `ProcessingMode_HeaderSendMode` enum value docs + `ProcessingMode_BodySendMode` enum value docs + `ProcessingMode` field docs in `processing_mode.pb.go`.

`HeaderSendMode` enum:
- `DEFAULT (0)`: *"The default HeaderSendMode depends on which part of the message is being processed. By default, request and response headers are sent, while trailers are skipped."*
- `SEND (1)`: *"Send the header or trailer."*
- `SKIP (2)`: *"Do not send the header or trailer."*

`BodySendMode` enum:
- `NONE (0)`: *"Do not send the body at all. This is the default."*
- `STREAMED (1)`: *"Stream the body to the server in pieces as they arrive at the proxy."*
- `BUFFERED (2)`: *"Buffer the message body in memory and send the entire body at once. If the body exceeds the configured buffer limit, then the downstream system will receive an error."*
- `BUFFERED_PARTIAL (3)`: *"Buffer the message body in memory and send the entire body in one chunk. If the body exceeds the configured buffer limit, then the body contents up to the buffer limit will be sent."*
- `FULL_DUPLEX_STREAMED (4)`: full-duplex streaming mode (no explicit doc-comment in proto).

`ProcessingMode` field docs all read "Default is X" — `request_header_mode` "Default is SEND"; `response_header_mode` "Default is SEND"; `request_body_mode` "Default is NONE"; `response_body_mode` "Default is NONE"; `request_trailer_mode` "Default is SKIP"; `response_trailer_mode` "Default is SKIP".

**Disposition: RATIFIED.** The brainstorm §2.2 open question ("DEFAULT semantics") resolves crisply per the enum docs: `HeaderSendMode.DEFAULT` IS context-sensitive — for header fields, DEFAULT == SEND; for trailer fields, DEFAULT == SKIP. The envoy-go IMPL translates `DEFAULT` → SEND at parse time for `request_header_mode` + `response_header_mode`; translates `DEFAULT` → SKIP for `request_trailer_mode` + `response_trailer_mode`. `BodySendMode` has no DEFAULT enum value — the zero value is `NONE` and the field doc explicitly states "Default is NONE". Phase-19 MVP envelope per Q2 PARSE-REJECTs `STREAMED`, `BUFFERED_PARTIAL`, `FULL_DUPLEX_STREAMED` (envoy-go-strict); `NONE` + `BUFFERED` are the consumed values (BUFFERED arms PARSE-REJECT in 19.1 — activate at 19.2). For trailer-modes, anything other than `SKIP` PARSE-REJECTs envoy-go-strict (trailers out of envelope per Q2). §6 amendment 9 documents.

### 5.10 §19.P10 — Bidi-stream half-close + STREAMED-only flag disposition + override_message_timeout + GoogleGrpc (RATIFIED)

**Probe:** Verbatim read of `external_processor_grpc.pb.go` (the `Process` RPC client/server interfaces) + `ExternalProcessor.observability_mode` (#17) doc + `ExternalProcessor.send_body_without_waiting_for_header_response` (#21) doc + `ExternalProcessor.deferred_close_timeout` (#19) doc + `ExternalProcessor.message_timeout` (#7) + `ExternalProcessor.max_message_timeout` (#10) + `ProcessingResponse.override_message_timeout` (#10) docs.

**Bidi-stream shape.** `ExternalProcessor.Process` is `bidirectional streaming` per `external_processor_grpc.pb.go`:

```go
type ExternalProcessorClient interface {
    Process(ctx context.Context, opts ...grpc.CallOption) (ExternalProcessor_ProcessClient, error)
}
type ExternalProcessor_ProcessClient interface {
    Send(*ProcessingRequest) error
    Recv() (*ProcessingResponse, error)
    grpc.ClientStream  // carries CloseSend() error + Context() context.Context + RecvMsg/SendMsg
}
```

The bidi-stream lifetime is per HTTP transaction (one `Process` stream per request). Client `Send` enqueues a `ProcessingRequest` to the server; `Recv` blocks until a `ProcessingResponse` arrives; `CloseSend` signals end-of-stream from the client side after the final stage. The server's `Process` interface is the symmetric pair (server Send sends ProcessingResponse; server Recv receives ProcessingRequest; server closes the stream via returning from `Process`). The client's `CloseSend` is invoked at stream-end (after the response_body or response_trailers stage completes, OR after the processor sends `ImmediateResponse`, OR on `OnDestroy` to abort).

**STREAMED-only flag disposition.**
- `observability_mode` (#17, bool) doc: *"If true, send each part of the HTTP request or response specified by ProcessingMode without pausing on filter chain iteration. It is 'Send and Go' mode..."*. STREAMED-coupled (the "Send and Go" semantics require streaming the body without waiting for processor responses); out of envelope per Q2. **PARSE-REJECT envoy-go-strict** if set to `true`.
- `send_body_without_waiting_for_header_response` (#21, bool) doc: *"Send body to the side stream server once it arrives without waiting for the header response from that server. It only works for STREAMED body processing mode. For any other body processing modes, it is ignored."* STREAMED-only; out of envelope per Q2. **PARSE-REJECT envoy-go-strict** if set to `true`. Note: the proto says "for any other body processing modes, it is ignored" — so the silent-ignore-when-not-applicable disposition is also acceptable. envoy-go-strict picks PARSE-REJECT for the consistency of fail-loud-on-unsupported-config discipline.
- `deferred_close_timeout` (#19, durationpb.Duration) doc: *"Specifies the deferred closure timeout for gRPC stream that connects to external processor. Currently, the deferred stream closure is only used in `observability_mode`..."*. observability_mode-coupled; out of envelope. **PARSE-REJECT envoy-go-strict** if set to non-zero (a zero-or-unset Duration is the no-op default — accepted silently).

**override_message_timeout wire shape.** `ProcessingResponse.override_message_timeout` (#10, `*durationpb.Duration`) doc: *"When ext_proc server receives a request message, in case it needs more time to process the message, it sends back a ProcessingResponse message with a new timeout value. When Envoy receives this response message, it ignores other fields in the response, just stop the original timer, which has the timeout value specified in `message_timeout` and start a new timer with this `override_message_timeout` value and keep the Envoy ext_proc filter state machine intact. Has to be >= 1ms and <= `max_message_timeout`. Such message can be sent at most once in a particular Envoy ext_proc filter processing state. To enable this API, one has to set `max_message_timeout` to a number >= 1ms."*. So: (a) override_message_timeout takes effect ONLY if max_message_timeout >= 1ms (otherwise IGNORED → `override_message_timeout_ignored` counter); (b) the new timeout must be in [1ms, max_message_timeout] (out-of-range IGNORED); (c) the `ProcessingResponse` carrying override_message_timeout is OTHERWISE IGNORED — its other fields (CommonResponse, ImmediateResponse, etc.) are not consumed; (d) at most ONCE per stage's processing state.

**`message_timeout` + `max_message_timeout` defaults.** `message_timeout` (#7, `*durationpb.Duration`, PGV `gte=0s, lte=1h0m0s`) — default 200ms per proto doc. `max_message_timeout` (#10, `*durationpb.Duration`, PGV `gte=0s, lte=1h0m0s`) — default 0 (which disables the override API).

**GoogleGrpc disposition.** Inherited from ADR-0157 §Decision AMENDMENT (phase-18.2). `core.GrpcService.GoogleGrpc` arm PARSE-REJECT envoy-go-strict (envoy-go uses `google.golang.org/grpc` directly; the C++ Google gRPC library config is permanently out of scope). The `core.GrpcService.initial_metadata` SILENT-IGNORED for MVP; `core.GrpcService.retry_policy` SILENT-IGNORED for MVP.

**Disposition: RATIFIED** across all sub-items. §6 amendment 10 documents.

### 5.11 §19.P11 — Encode-side body-buffering primitive existence/shape (REFUTED — ADR-0175 fires)
