# Phase 53 Brainstorm — `priority` load balancing (SEVENTH Load-balancing-family row; the family STAYS OPEN; the SECOND health-gated candidate to land)

**Status:** brainstorm complete (lifecycle-state 0 → 1). This document captures the design decisions reached during the brainstorm session for phase 53 (`load-balancer-priority`), the **SEVENTH Load-balancing-family row**. Phase 53 lands `LocalityLbEndpoints.priority`-driven priority-tier selection — Envoy's overflow/failover mechanism across priority levels (P0, P1, P2, ...), where traffic is drawn from the lowest-numbered ("highest priority") tier as long as it has enough healthy capacity, spilling to the next tier as that capacity degrades, computed via the SAME `configured-weight × min(1, (overprovisioning_factor/100) × healthy_fraction)`-shaped waterfall the phase-52 `localityWeightedLB` already implements for localities (`ClusterLoadAssignment.Policy.overprovisioning_factor`, reused verbatim — not a new concept). Structurally, phase 53 is the **SECOND wrapper reusing the phase-52 `localityWeightedLB` shape almost exactly**: group endpoints by a per-endpoint identity dimension (locality → priority), build one child `loadBalancer` per group via the existing `buildLeafLB` factory, weighted-random-draw a group per `Pick` by an effective-load computation, delegate unchanged. It needs **zero new `Pick` parameters** — the family's now-established cheapest-wrapper shape, first proven by phase 52.

The load-bearing facts that shape this brainstorm:

- **`Endpoint` gains its THIRD dimension.** `internal/cluster/cluster.go`'s `Endpoint` is `{Host, Port, Metadata, Locality, LocalityWeight}` (`Metadata` at phase 38/ADR-0240; `Locality`/`LocalityWeight` at phase 52/ADR-0269). `extractEndpoints` (`manager.go:771-795`) already reads `group.GetPriority()` in NEITHER phase — the flatten function's own per-group loop currently discards it (confirmed by direct inspection of `LocalityLbEndpoints` at both phase-38 and phase-52 brainstorms, which explicitly noted `priority` "stays discarded — couples to the priority-LB candidate"). Phase 53 captures it: a `Priority uint32` field, defaulting to `0` (the reference default) when absent.
- **The SAME per-tier grouping + factory-child + weighted-draw shape phase 52 established for locality — reapplied one axis over.** `priorityLB` groups the cluster's endpoints by distinct `Priority` value (arbitrary N tiers — NOT hardcoded to 2), builds one child `loadBalancer` per tier via the EXISTING `buildLeafLB` factory (a per-tier LEAF-only child; see the composition decision below — NOT a nested `localityWeightedLB`), and at `Pick` draws a tier by its effective LOAD (not "weight" — the reference's own terminology distinguishes locality "weight" from priority "load", though both use the identical overprovisioning-scaled-by-health shape) before delegating `child.Pick(hashKey, hasHash, match, hasMatch)` UNCHANGED.
- **Composition with `locality_weighted_lb_config` is EXPLICITLY DEFERRED, mirroring phase 52's own subset-composition posture (user Q2, this brainstorm).** In reference Envoy, a `HostSet` is organized by priority FIRST and can ALSO be locality-weighted WITHIN a tier — the "correct" general architecture nests a per-tier `localityWeightedLB` inside `priorityLB`. This brainstorm's Q2 dialogue chose to KEEP THEM INDEPENDENT for the MVP (a cluster configuring BOTH multi-tier `priority` values on its `LocalityLbEndpoints` AND `common_lb_config.locality_weighted_lb_config` is REJECTED at build — a recorded departure, exact wording pinned at SPEC), for the same reason phase 52 gave for punting subset composition: composing them faithfully is a real architecture question (per-tier health scoping interacting with `localityWeightedLB`'s constructor) that deserves its own dialogue rather than an assumption baked in here, and this project's precedent (phase-38 subset ↔ phase-52 locality-weighted, twice-deferred) is to defer wrapper-of-wrapper composition deliberately rather than assume a precedence.
- **Priority's own per-TIER panic/health computation is NOT simply "reuse the cluster-wide `inPanic` gate one layer higher" — it is the SPEC's single load-bearing empirical unknown, mirroring phase 52's D-LW3/D-LW4 shape.** Locality-weighted (phase 52) reused the EXISTING cluster-wide `clusterHealth.inPanic` gate verbatim, consulted one layer higher than the leaf policies (§2.5 of that brainstorm) — because locality weighting is a WITHIN-panic-mode concept (when the whole cluster panics, locality weighting is bypassed entirely). Priority load balancing is different: the reference's own priority-load algorithm computes each tier's healthy/degraded percentage AS PART OF deciding how much load that tier gets — a tier's own health IS the input to the waterfall, not a gate that bypasses it. Whether cluster-WIDE panic (aggregated across all tiers) ALSO exists as a further bypass on top of the per-tier waterfall, and exactly how the two composed concepts (`healthy_panic_threshold` and per-tier load) interact in the reference, is **SPEC-BLOCKING** (D-P1 below) — this brainstorm does not assume an answer, per the project's live-probe-over-assumption discipline established at every prior LB phase.

The phase-44.1/phase-52 sibling-reject lesson does not apply structurally here (noted for completeness — this is a REASON that lesson doesn't need reapplication, not evidence it does).

### 2.2 Composition scope: kept independent; BOTH-configured (priority tiers + locality-weighted) is an explicit reject *(Q2 → self-contained scope boundary, this brainstorm's dialogue)*

### 2.3 Child-policy scope: mirror `localityWeightedLB`/`subsetLB` — ALL five children via factory reuse *(self-answered; unanimous precedent, ADR-0270)*

**Decision:** `priorityLB` is a `loadBalancer` wrapper that, at build time, groups the cluster's endpoints by `Priority` value and builds a **child `loadBalancer` per tier via the existing policy factory** (`buildLeafLB`) over that tier's endpoint sub-slice — ALL five policies (round_robin/least_request/random/ring_hash/maglev) supported uniformly, exactly the `subsetLB`/`localityWeightedLB` shape. At `Pick` (outside any panic bypass — §2.5), weighted-random-select a tier by effective load, then delegate `child.Pick(hashKey, hasHash, match, hasMatch)` unchanged.

**Rationale:** this question was asked and answered identically at BOTH phase 38 (Q3) and phase 52 (Q3) — unanimous precedent across every prior wrapper. Re-asking it a third time would not surface new information; factory reuse makes "all children" barely harder than one, it is the most faithful shape, and it keeps the exported `Cluster` surface byte-stable. Self-answered rather than re-litigated as a live question this session.

### 2.4 Effective-load computation: the phase-52 waterfall formula, applied per-tier rather than per-locality *(self-answered envelope; exact interaction with panic SPEC-BLOCKING, D-P1)*

**Decision:** each tier's EFFECTIVE LOAD is computed via the SAME shape as phase 52's `effectiveWeight` (`locality.go:118-123`: `min(1, (overprovisioningFactor/100) × healthyFraction)`), but as a CASCADING WATERFALL across tiers in priority order rather than a single normalize-and-draw over siblings: P0 receives `min(100, effectiveLoad(P0))` percent; the REMAINDER (if any) is offered to P1 by the identical rule against P1's own healthy fraction; any further remainder cascades to P2, and so on, until 100% is allocated or tiers are exhausted (the standard "priority spillover" shape named by the candidate). This is NOT assumed to be byte-for-byte identical to phase 52's SINGLE-LAYER weighted draw (locality has no cascade — all localities are peers) — it is a genuinely different aggregation (waterfall vs. flat-normalize), sharing only the per-group effective-availability primitive. D-P4 (SPEC-BLOCKING) live-probes the reference to pin the exact cascade formula and confirm/refute the assumed shape.

**Rationale:** the effective-availability primitive (`min(1, overprovisioning × healthy_fraction)`) is ALREADY proven correct for locality weighting (phase 52's D-LW3 empirical pin); reusing it as the per-tier availability input is the minimal-new-surface choice. The CASCADE (as opposed to locality's flat normalize-and-draw) is the one genuinely new algorithmic shape this phase introduces, and per the project's formula-fidelity discipline (`reference_percent_cap_cross_multiply`, generalized — first invoked at phase 52's D-LW3) it is verified live, not assumed.

### 2.5 Panic-mode interaction: the phase's single most load-bearing empirical unknown *(self-answered envelope; SPEC-BLOCKING, D-P1)*

**Decision:** UNLIKE phase 52 (which cleanly reused the EXISTING cluster-wide `inPanic` gate "one layer higher" — §2.5 of that brainstorm, since locality weighting is purely a WITHIN-panic-mode-bypass concept), this brainstorm does NOT assume priority's panic interaction mirrors that shape. Two readings are equally plausible from the proto/doc surface alone: (a) cluster-wide `healthy_panic_threshold` (aggregated across ALL tiers' hosts) is a further bypass ABOVE the per-tier waterfall — if the WHOLE cluster is in panic, `priorityLB` delegates to a flat all-tiers-all-hosts child, exactly mirroring phase 52's shape; OR (b) panic is computed PER-TIER — each tier independently asks "is MY healthy fraction below the panic threshold?" and, if so, that tier offers 100% of its OWN hosts (health-ignoring) as its contribution to the waterfall, before the cascade proceeds to the next tier. **D-P1 is SPEC-BLOCKING** and executes a live probe against the reference (a 2-tier cluster, degrading P0's health across the full range including past its own would-be panic threshold while P1 stays fully healthy, observing whether P0's request share ever again include unhealthy-host traffic, and whether cluster-aggregate health state affects the outcome) to pin which reading — or a third, unanticipated one — is correct. envoy-go reproduces whatever is found bit-for-bit.

**Rationale:** this is the phase's single most load-bearing empirical unknown — exactly the role D-LW3 (the effective-weight formula) played for phase 52. Every prior LB phase's most novel mechanism was pinned via a live probe, never assumed; the panic/per-tier-health interaction is this phase's analogous unknown, and this brainstorm deliberately does not pre-commit to either reading.

### 2.6 Differential strategy: static + full-failover arms only, NOT a partial-spillover band *(Q4 → fixture envelope §6)*

**Decision:** the fixture `0096-lb-priority` configures TWO priority tiers of HTTP backends on BOTH sides. **Arm (a) — static:** with P0 fully healthy, assert 100% of traffic lands on P0, 0% on P1 (no failover at full health — the contrapositive of arm (b)). **Arm (b) — full failover:** fail active health checks on ALL of P0's hosts (reusing the phase-39 substrate + `reference_health_check_propagation_warmup`'s poll-to-convergence gate, NOT a sleep), then assert traffic fails over 100% to P1. NO third partial-spillover arm (a fractional band asserting, e.g., "40% of P0 down → X% to P1") — the user's Q4 answer explicitly declined this in favor of the cheaper 2-arm proof, accepting that the fractional waterfall formula (§2.4/D-P4) is verified analytically at SPEC (a live-probe empirical pin) rather than fixture-proven as a banded statistical property. Cross-side byte-equivalence + a cross-side `StatsAsserter`. Every live assertion proven via a deliberate-break with `-count=1` (`reference_differential_break_protocol_count1`) — e.g. "drop the priority field so both tiers merge into P0" defeats arm (a); "skip the health-degradation step" defeats arm (b).

**Rationale:** locality-weighted's defining property was a RATIO (statistical, needing a band); priority's defining property named by the candidate itself is FAILOVER — a hard 100%/0% boundary, which a 2-value assertion proves cleanly without statistical margin-tuning risk (the phase-35 `0060` and phase-52 `reference_differential_band_sigma_margin` re-tuning lessons, avoided here by design rather than by luck). The user's choice keeps the fixture cheaper and flake-risk-free while still proving the load-bearing "failover" property the candidate is named for.
