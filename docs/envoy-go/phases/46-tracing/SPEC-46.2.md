## 1. Purpose / Mission

Deliver envoy-go's SECOND tracing exporter — the Zipkin provider — completing the THIRD Observability-family row. When an HCM `tracing` block carries a recognized **Zipkin** provider (`envoy.tracers.zipkin` → `ZipkinConfig`), envoy-go runs the SAME full-fidelity sampling/request-id decision the 46.1a engine already produces (provider-agnostic — the `x-request-id` byte-14 trace-reason, the three Percent knobs, the incoming-context-continues-authoritatively precedence), builds the SAME per-request SERVER `Span` (start at dispatch, end at the `accesslog_emit.go` seam), but (a) extracts/continues/injects the trace context in the **B3** format (the `b3` single header AND the `X-B3-*` multi-header set) instead of W3C `traceparent`, and (b) EXPORTS each sampled span to the configured Zipkin collector as a **v2 JSON** span over an HTTP/1 `POST` to the `collector_cluster` (via `httpclient.Client.ClusterDispatch`), instead of the OTLP unary gRPC `TraceService.Export`. It is the FIRST non-gRPC tracing exporter (the OTLP/ALS/OTLP-logs sinks are all gRPC) and the FIRST consumer of the phase-22 `httpclient.ClusterDispatch` HTTP-over-cluster primitive (ADR-0177) outside the Lua/wasm `httpCall` surface. It composes ENTIRELY on substrates already built — the 46.1a/46.1b `internal/tracing` engine + span model + `Exporter` seam, the phase-22 `httpclient` layer, and the cluster manager — adding ZERO new Go packages and ZERO new go.mod modules. Byte-identical when no `tracing` provider is configured (the regression anchor stays the full differential). It ANCHORS ADR-0261; **the 46.2 IMPL six-gate FLIPS ROADMAP row 46 (`tracing`) → `done`** (the FINAL chartered tracing leg, per ADR-0106 + `reference_roadmap_split_phase_row_done`); the Observability family STAYS OPEN (stats sinks + the tap filter remain future rows — there is NO family-close at 46.2, per the phase-46 BRAINSTORM §1.3).

### 1.1 Empirical-finding-driven scope (amendment block per ADR-0044)

The §11 live probe (2026-06-28, contrib-v1.37.2 — an H1 downstream → a real HTTP backend, with an HCM `tracing` block [Zipkin provider, `random_sampling=100%`] exporting to a driver-owned HTTP Zipkin collector, all on a shared bridge per `reference_docker_probe_bridge_network`; **decode-ran proof: `tracing.zipkin.spans_sent: 8` + 6 `reports_sent` POSTs captured at the collector, every span `kind:"SERVER"` with the deterministic tag subset**) drove these amendments. The transport, the wire model, the propagation format, AND the boot-reject posture all DIFFER from the OTLP leg — the Zipkin leg is genuinely a second exporter, not a re-skin.

- **AMEND-ZIPKIN-WIRE (the Zipkin exporter POSTs a v2 JSON span ARRAY over HTTP/1 — `POST <collector_endpoint>` `Content-Type: application/json`, chunked — to the `collector_cluster`; the span `name` is the request AUTHORITY not the constant `"ingress"`; `timestamp`/`duration` are MICROseconds; the attribute roster maps to 14 STRING `tags` [the OTLP-16 MINUS `node_id`/`zone`]).** Live finding (D-TRACE-ZIPKIN-WIRE): the reference POSTs to `collector_endpoint` (probed `/api/v2/spans`) on `collector_cluster`, `Content-Type: application/json`, the body a JSON ARRAY of span objects (Zipkin v2 JSON model). Each span: `traceId` (lowercase hex, 32 chars under `trace_id_128bit:true` else 16), `id` (16-hex span-id), `parentId` (16-hex, conditional — see AMEND-ZIPKIN-SHARED), `name` (the request authority — the `Host`/`:authority` value, e.g. `127.0.0.1:10000`; NOT the OTLP `"ingress"` constant), `kind:"SERVER"` (string), `timestamp`/`duration` (int64 MICROseconds — NOT the OTLP nanos), `localEndpoint:{serviceName?,ipv4,port:0}` (ipv4 env-specific; `serviceName` only with a configured node; port 0), `annotations:[{timestamp,value:"ss"}]` (a single server-send annotation; timing), and `tags` — 14 STRING tags = the OTLP 16-attr roster MINUS `node_id` + `zone`: `http.method`/`http.url`/`http.protocol`/`http.status_code`/`component`(=`proxy`)/`upstream_cluster`/`upstream_cluster.name`/`downstream_cluster`(=`-`)/`response_flags`(=`-`)/`request_size`/`response_size`/`user_agent`/`peer.address`/`guid:x-request-id` (+ `guid:x-client-trace-id` when present). **Framework-gap note (`reference_tracing_upstream_cluster_framework_gap`):** envoy-go emits `upstream_cluster`/`upstream_cluster.name` EMPTY (the picked-cluster name is not plumbed to the `accesslog_emit.go` span seam — `UpstreamCluster:""`, the 46.1b as-built) and `peer.address` is env-specific (the downstream remote IP) — so all three are KEY-PRESENT-only / value-UNasserted cross-side (§8.1), NOT value-deterministic. This REPLACES the brainstorm §6 "Zipkin v2 vs v1" open guess with the pinned v2-JSON-array shape + the concrete 14-tag roster + the authority-as-name finding.
- **AMEND-ZIPKIN-IDS (the root span `id` == the low-64 of `traceId`; the trace-id width follows `trace_id_128bit`; a continued trace preserves the incoming width).** Live finding: a fresh ROOT span's `id` equals the low 64 bits of its `traceId` (probed traceId `f66f439f8da5c950`+`84ac017ed6103f43`, id `84ac017ed6103f43`; under `trace_id_128bit:false` the 64-bit `id`==`traceId` exactly). `trace_id_128bit:true` → 32-hex `traceId`; false/unset → 16-hex. A CONTINUED trace keeps the incoming trace-id width verbatim.
- **AMEND-ZIPKIN-SHARED (`shared_span_context` toggles the continued-span model: true ⇒ the server span REUSES the incoming span-id as its own `id` + emits `"shared":true` + NO `parentId`; false ⇒ a CHILD span with a fresh `id` + `parentId` = the incoming span-id; the Envoy default is true).** Live finding: with `shared_span_context:true` (the Envoy default for an unset `*BoolValue`) every span carries `"shared":true`, and a continued span takes the incoming B3 span-id as its OWN `id` with no `parentId` (the shared client-server span model). With `shared_span_context:false` (config A) a continued span is a CHILD: a fresh `id` + `parentId` = the incoming span-id, no `shared` field. A fresh root under `shared:true` still emits `"shared":true` (id==low64(traceId), no parentId).
- **AMEND-ZIPKIN-B3 (B3 INJECT toward the upstream is the MULTI-HEADER `X-B3-*` set [NOT the single `b3`]; B3 EXTRACT accepts BOTH the single `b3` and the multi-header `X-B3-*`).** Live finding (D-TRACE-ZIPKIN-B3): the reference INJECTS `X-B3-TraceId` (16/32 hex), `X-B3-SpanId` (16 hex), `X-B3-Sampled` (`1`/`0`), and `X-B3-ParentSpanId` (16 hex, present ONLY when the trace was continued = the incoming span-id) toward the upstream — NOT the single `b3` header. It EXTRACTS from EITHER the single `b3` header (`<traceid>-<spanid>-<sampled>[-<parentspanid>]`, 64-or-128-bit traceid) OR the multi-header `X-B3-{TraceId,SpanId,ParentSpanId,Sampled,Flags}`. The sampled-bit is honored (`1`→sampled, `0`→not) and a continued trace's sampled-bit bypasses the local sampling caps — the SAME precedence the 46.1a `Decide` already implements (provider-agnostic; the `x-request-id` byte-14 nibble engine is unchanged — probed `9`/`b`). 46.2 adds ONLY the B3 codec; the decision engine is reused verbatim.
- **AMEND-ZIPKIN-TRANSPORT (the Zipkin exporter uses the phase-22 `httpclient.Client.ClusterDispatch` HTTP-over-cluster primitive — NOT `grpcclient.Dialer`/`OTLPTracesClient`; the collector cluster is plain HTTP/1, NO `http2_protocol_options{}`/`UseH2` gate).** Live finding: the collector cluster is dialed as a normal HTTP/1 cluster (no H2 framing). envoy-go's transport seam is `httpclient.Client.ClusterDispatch(ctx, collectorCluster, *http.Request, *cluster.Manager)` (`internal/httpclient/httpclient.go:269`, ADR-0177 — the phase-22 HTTP-call-over-cluster primitive already consumed by `internal/wasm/http_call.go`), which does `clusterMgr.Get` (the cluster-exists gate) + `PickEndpoint` + a stdlib HTTP/1 `POST`. The `Host` header on the POST is `collector_hostname` when set, else the `collector_cluster` name (probed: unset → `zipkin_cluster`, set → `my-zipkin.example.com`). This is the FIRST non-gRPC tracing exporter and the FIRST `ClusterDispatch` consumer outside Lua/wasm.
- **AMEND-ZIPKIN-BOOT-REJECT (the reference BOOT-REJECTS a missing Zipkin collector cluster — UNLIKE the PERMISSIVE OTLP path; so envoy-go's cluster-exists gate is REFERENCE-PARITY here, NOT an envoy-go-strict departure).** Live finding (D-TRACE-ZIPKIN-REJECT): with `collector_cluster` pointing at a NONEXISTENT cluster the reference EXITS 1 at config init — `envoy.tracers.zipkin: unknown cluster '<name>' initializing config`. This CONTRASTS the 46.1b AMEND-TRACE-NO-BOOT-REJECT (OTLP boots permissively on a missing cluster); the Zipkin tracer requires the collector cluster to exist at config load. envoy-go's `httpclient.ClusterDispatch` → `clusterMgr.Get` miss returns `errClusterNotFound`; 46.2 pre-checks the cluster exists at exporter build (the `ExporterProvider` Zipkin arm) → a `log.Fatalf` boot failure that MATCHES the reference (no departure to document for the missing-cluster case). The `collector_endpoint_version` values OTHER than `HTTP_JSON` (`HTTP_PROTO` → `application/x-protobuf` proto body; `GRPC`; the deprecated `0`) and `split_spans_for_request` are envoy-go-strict REJECTS (§2, §6).

### 3.0 Split disposition — leg 46.2 of the by-exporter 2-leg split; the FINAL chartered tracing leg (NO sub-split)

46.2 is the SECOND and FINAL leg of the by-exporter split (46.1 core+OTLP / 46.2 Zipkin+B3). ### 3.1 Config parse — provider-type DISPATCH (`internal/tracing/config.go` `NewConfig`)

The 46.1a `NewConfig` (`internal/tracing/config.go:44`) parses the HCM `tracing` message and TODAY accepts ONLY the OpenTelemetry provider (the `otelTypeName` gate at `:70` rejects every other `typed_config` type). 46.2 generalizes the provider arm to DISPATCH on the `typed_config` proto type:

- Blank-import the Zipkin config proto's package is ALREADY covered (`internal/tracing/config.go:10` imports `tracev3 "…/config/trace/v3"`, which carries BOTH `OpenTelemetryConfig` and `ZipkinConfig`; the `bootstrap.go` blank-import registry [ADR-0016] resolves the `Any` typed_config). Confirm `(&tracev3.ZipkinConfig{}).ProtoReflect().Descriptor().FullName()` (`envoy.config.trace.v3.ZipkinConfig`) as the `zipkinTypeName` sibling of `otelTypeName`.
- The parsed config grows a provider-kind discriminant. The packaging (a `ProviderKind` enum + a tagged `TracingConfig`, vs a per-provider sub-struct) is a PLAN call (D-TRACE-ZIPKIN-CONFIG-SHAPE). The Zipkin fields to carry: `CollectorCluster` (`collector_cluster`, required), `CollectorEndpoint` (`collector_endpoint`, the POST path), `CollectorHostname` (`collector_hostname`, the POST `Host`; empty ⇒ the cluster name), `TraceID128Bit` (`trace_id_128bit`), `SharedSpanContext` (`shared_span_context.value`; ABSENT ⇒ the Envoy default `true`). The three Percent sampling knobs + the `x-request-id` engine are SHARED (provider-agnostic) — unchanged.
- **STRICT-REJECT arms (ADR-0080; byte-stable wording at PLAN), Zipkin-specific:** `collector_endpoint_version` ∈ {`HTTP_PROTO`, `GRPC`, `DEPRECATED_AND_UNAVAILABLE_DO_NOT_USE`(0)} (only `HTTP_JSON`(1) accepted — each its own reject arm per `reference_strict_reject_sibling_typeurl_gap`); `split_spans_for_request==true`; an empty `collector_cluster`. The SHARED HCM-level rejects (`verbose`/`max_path_tag_length`/`custom_tags`/`spawn_upstream_span`) carry from the 46.1a arms unchanged.
- **PARSE-ACCEPT (Zipkin):** `collector_cluster` (non-empty), `collector_endpoint`, `collector_endpoint_version==HTTP_JSON`, `trace_id_128bit`, `shared_span_context`, `collector_hostname`. The cluster-exists + HTTP-reachable gate is enforced at exporter build (§3.7) as a `log.Fatalf` boot failure — REFERENCE-PARITY (AMEND-ZIPKIN-BOOT-REJECT), NOT a departure.

### 3.2 The transport — `httpclient.Client.ClusterDispatch` (NOT `grpcclient`; the phase-22 HTTP-over-cluster primitive)

The Zipkin exporter POSTs over HTTP/1, NOT gRPC. The transport seam is `httpclient.Client.ClusterDispatch(ctx, clusterName, *http.Request, *cluster.Manager) (*http.Response, error)` (`internal/httpclient/httpclient.go:269`, ADR-0177): it does `clusterMgr.Get(clusterName)` (returns `errClusterNotFound` on a miss — the cluster-exists gate, AMEND-ZIPKIN-BOOT-REJECT), `cl.PickEndpoint()` (LB-selects an endpoint, rewrites `URL.Host`), honors the cluster's `UpstreamTLSConfig()` (TLS vs plaintext), and runs a stdlib HTTP/1 `http.Client.Do` with the receiver's timeout/retry policy. The collector cluster needs NO `http2_protocol_options{}` (HTTP/1) — UNLIKE the OTLP H2/gRPC requirement. The exporter constructs an `*http.Request` (method `POST`, URL path = `collector_endpoint`, `Host` = `collector_hostname`‖cluster-name, `Content-Type: application/json`, body = the v2 JSON span array) and calls `ClusterDispatch`. A non-2xx response or a dispatch error is the drop-with-`reports_failed` path (§3.3). This is the FIRST `ClusterDispatch` consumer outside Lua/wasm — the threading of the `*httpclient.Client` + `*cluster.Manager` to the exporter is a boot-wiring task (§3.7; D-TRACE-ZIPKIN-TRANSPORT-WIRING).

### 3.3 The `ZipkinExporter` — a SECOND `tracing.Exporter` impl (`internal/tracing`)

A new `ZipkinExporter` satisfying the EXISTING seam `type Exporter interface { Export(*Span); Close() error }` (`internal/tracing/exporter.go:56`), mirroring the `OTLPExporter`'s bounded-channel + writer-goroutine + size/interval/close-buffer + drop-newest + idempotent-`Close` shape (`exporter.go:73`), but:

- On flush, encode the buffered `[]*Span` to a Zipkin **v2 JSON span array** (the new encoder, §3.5) rather than `buildExportTraceRequest`/`toProto`; build the `*http.Request` (§3.2); call `httpclient.ClusterDispatch`; on a 2xx, `spansSent.Add(len(batch))`; on a non-2xx/error, retry-once-then-drop (the `reports_failed`/`spans_dropped` path).
- The tracer-scoped counters are Zipkin-specific (§7): the envoy-go subset of the reference `tracing.zipkin.*` roster.
- The `ZipkinExporter` is built by the `ExporterProvider` (§3.7) on the Zipkin provider arm — keyed by `collector_cluster` (memoized, the `OTLPExporter` precedent). The `Exporter` seam means the HCM wiring (`builtins.Deps.TracingExporters` → the per-HCM `Exporter` handle) is UNCHANGED — it already holds an interface; 46.2 just makes the concrete impl polymorphic.

### 3.4 B3 propagation — the `b3` single-header + `X-B3-*` multi-header codec (`internal/tracing`, the `traceparent` analog)

A new B3 codec (a `b3.go` file alongside `propagation.go`), the Zipkin analog of the 46.1a W3C engine:

- **`ExtractB3(h http.Header) (TraceContext, bool)`** — parse EITHER the single `b3` header (`<traceid>-<spanid>-<sampled>[-<parentspanid>]`; traceid 16-or-32 hex; sampled `0`/`1`/`d`[debug]) OR, when absent, the multi-header `X-B3-TraceId` / `X-B3-SpanId` / `X-B3-ParentSpanId` / `X-B3-Sampled` / `X-B3-Flags`. Reuse the EXISTING `TraceContext{TraceID,ParentID,Sampled,TraceState}` shape (`propagation.go:12`) — the B3 path leaves `TraceState` empty (no Zipkin tracestate). A continued B3 trace continues authoritatively (the 46.1a `Decide` precedence is propagation-format-agnostic — it consumes a `TraceContext` regardless of the wire codec; D-TRACE-ZIPKIN-DECIDE-SEAM, §12, confirms `Decide` takes the extracted context rather than re-extracting `traceparent` internally — a small 46.1a refactor may be needed so `Decide` accepts an already-extracted `(TraceContext, bool)` for either codec).
- **`InjectB3(h http.Header, traceID, spanID, parentID, sampled, shared)`** — write the MULTI-HEADER `X-B3-*` set (AMEND-ZIPKIN-B3): `X-B3-TraceId` (hex, width per `trace_id_128bit`), `X-B3-SpanId` (the SERVER span's outbound span-id), `X-B3-Sampled` (`1`/`0`), and `X-B3-ParentSpanId` ONLY when continued. `reference_wire_format_both_sides_see_same_bytes` — adopt the reference header set + casing verbatim.
- The `b3` extract is an UNTRUSTED-input boundary → a fuzzer (`FuzzExtractB3`, §6).

### 3.5 The Zipkin v2 JSON span encoder + the span shape (§11 D-TRACE-ZIPKIN-WIRE, AMEND-ZIPKIN-WIRE/IDS/SHARED)

A new encoder (`zipkin.go`) mapping the internal `Span` (`internal/tracing/span.go:40`) to the Zipkin v2 JSON model (stdlib `encoding/json` — ZERO new modules), the Zipkin analog of `(*Span).toProto`:

- The encoder emits a JSON object per span: `traceId` (hex, 16/32 per `trace_id_128bit`), `id` (16-hex span-id), `parentId` (conditional — present iff continued AND NOT shared, AMEND-ZIPKIN-SHARED), `name` (the request authority — see below), `kind:"SERVER"`, `timestamp`/`duration` (int64 MICROseconds — `Start.UnixMicro()` / `End.Sub(Start).Microseconds()`), `localEndpoint:{serviceName?,ipv4,port}` (env-derived — UNasserted), `shared:true` (only when `shared_span_context`), and `tags` (the 14 STRING tags). A batch is a JSON ARRAY of these.
- **Span `name` = the request authority.** The 46.1b `BuildServerSpan` hardcodes `Name="ingress"` (the OTLP constant). For Zipkin the name is the `Host`/`:authority`. The span model must carry the authority so each exporter names appropriately: either (a) the `Span` carries BOTH (a neutral `Authority` field; the OTLP encoder uses `"ingress"`, the Zipkin encoder uses `Authority`), or (b) `BuildServerSpan` becomes provider-aware. The packaging is a PLAN call (D-TRACE-ZIPKIN-SPAN-NAME) — prefer (a): keep the `Span` provider-neutral (carry the superset) and let each exporter's encoder shape it.
- **The 14 tags** = the 46.1b 16-attr roster MINUS `node_id` + `zone` (those two are OTLP-only; Zipkin folds node identity into `localEndpoint.serviceName`). The `Span.Attrs` already carry all 16 as `KV`; the Zipkin encoder selects the 14 (drop `node_id`/`zone`) — a deterministic filter, not a re-plumb. `guid:x-client-trace-id` stays conditional.
- **ids** — the encoder derives `id` and `traceId` from the `Span.TraceID`/`SpanID` ([16]byte/[8]byte). Under `trace_id_128bit:false` the trace-id is the low 64 bits (16-hex); the root `id` == that low-64 (AMEND-ZIPKIN-IDS). The exact id-derivation (does envoy-go generate the span-id as the low-64 of the trace-id for a root, matching the reference, or independently? — a cross-side `id`/`traceId` VALUE is UNasserted anyway, but the SELF-consistency [root id==low64 traceId] may be asserted subject-side) is a PLAN pin (D-TRACE-ZIPKIN-ID-DERIVE).
- `annotations` (the single `"ss"`) is timing-only — UNasserted; whether envoy-go emits it at all is an IMPL decision (it carries no cross-side-deterministic value; likely OMITTED unless a probe shows a collector requires it — D-TRACE-ZIPKIN-ANNOTATIONS, §12).

### 3.6 HCM wiring (`internal/filter/hcm`) — provider-aware propagation + export on the EXISTING seams

The 46.1b span lifecycle (decision + request-id + span-start at `connection.go` dispatch; span-end + sample + export at the `accesslog_emit.go` seam) is REUSED. 46.2 makes two points provider-aware:

- **Propagation:** at the dispatch seam, INJECT via `InjectB3` (Zipkin) instead of `InjectTraceparent` (OTel), keyed by the provider kind on the HCM `TracingConfig`. The EXTRACT likewise dispatches (`ExtractB3` vs `ExtractTraceparent`) before `Decide`. The `x-request-id` stamp is unchanged.
