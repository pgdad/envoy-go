## 1. Mission summary

Phase 18 lands `envoy.filters.http.ext_authz` — Envoy's canonical external-authorization filter, the FIRST §9 family-row whose configuration **delegates the allow/deny decision itself to an external service over a network call** — as the ELEVENTH production HTTP filter in envoy-go after cors (07.1), fault (09), header_mutation (10), local_ratelimit (11), csrf (12), buffer (13), compressor (14), bandwidth_limit (15), rbac (16), and jwt_authn (17). Per the phase-18 BRAINSTORM's 6-question dialogue the MVP envelope is: **Both service modes proto-faithful** (`grpc_service` + `http_service`); **request body included** proto-faithful (`with_request_body` reusing the phase-13 ADR-0128 decode-side body-buffering primitive); **Full gRPC `AttributeContext` population** (source/destination Peers incl. `principal` via the phase-16 ADR-0144 `DownstreamPrincipal()` reuse + `certificate`/`tls_session` honored as `include_*`-gated; full `request.http`; `context_extensions`); **Full header-side mutation** (request-side filtering + allow-path upstream injection + deny-path downstream copying); **per-route 5th-canonical REUSE** (`ExtAuthzPerRoute{oneof{disabled(bool) | check_settings(CheckSettings)}}` maps onto the existing ADR-0125 5th canonical — the FIRST §9 row to REUSE an ADR-0125 canonical rather than add one; NO ADR-0125 amendment paragraph).

Phase 18 is also: (i) the FIRST §9 family-row to introduce **gRPC infrastructure** in envoy-go — the repo currently has zero `google.golang.org/grpc` usage of any kind; the `grpc_service` mode requires a brand-new gRPC-client framework primitive at NEW `internal/grpcclient/` (ADR-0158). (ii) the THIRD CONSECUTIVE §9 row to introduce TWO new framework primitives (after phase-16 rbac + phase-17 jwt_authn) — the gRPC-client outbound primitive + an HTTP-outbound auth-check (ADR-0159). (iii) the FIRST §9 row whose MVP envelope spans two structurally distinct service-call transports selected by a proto `oneof` — the dominant ADR-0045 split-readiness driver (§3). (iv) the FIRST §9 row to consume the phase-13 ADR-0128 decode-side body-buffering machinery as a *consumer* rather than its introducer.

**This parent master SPEC carries the cross-cutting design that applies to BOTH sub-phases** — the dual-mode `compiledConfig` envelope concept, the shared `checkDisposition` value, the error-posture surface, the full §5 empirical-pin block (all 13 §10 pins resolved IN-SESSION this session per ADR-0004 — they span both sub-phases, so they live here once), the §6 empirical-finding-driven scope-revision (amendment) block, and the §7 ADR anchor map. It points down to each sub-phase's authoritative SPEC for the per-surface detail.

After phase 18, the project has proven its eleventh §9 engineering claim: *envoy-go's HTTP filter framework hosts a decode-side external-authorization filter that ships request attributes to a separate process/service over either an HTTP POST or a gRPC `Authorization/Check` call, parks the decode dispatch goroutine on an async-resume leg while the outbound call is in flight, converges both transports on a common `{allow, deny, error}` disposition, applies bidirectional header mutation on the allow path and emits the auth service's status/body/headers verbatim via `SendLocalReply` on the deny path, and honors the `failure_mode_allow` / `status_on_error` error posture when the auth service is unreachable — with OBSERVABLE-OUTCOMES byte-equivalent to reference Envoy v1.37.2 on every axis except the documented divergence-windows (`response_code_details`, the dynamic-metadata family, `allowed_client_headers_on_success` encode-side participation, the Runtime family).*

## 3. Split rationale — ADR-0045 invoked, empirically confirmed (ADR-0164)

The phase-18 BRAINSTORM §1.4 flagged ADR-0045 split-readiness **HIGH** — the FIRST §9 family-row to flag HIGH rather than MODERATE — and instructed the SPEC author to treat single-row as the exception requiring justification, not the default. **This SPEC author's call is: SPLIT.** The §5 empirical-pin resolution executed in this session CONFIRMS the HIGH leaning rather than narrowing it (contrast phase-17, where the §11 resolution NARROWED the LoC estimate enough to keep single-row). The drivers, now empirically grounded:

1. **The proto surface is large.** §5.P1 enumerated a **28-field `ExtAuthz` message** + `HttpService` (4 fields) + `AuthorizationRequest` (2) + `AuthorizationResponse` (5) + `BufferSettings` (3) + `ExtAuthzPerRoute`/`CheckSettings` (2/3) + the `auth/v3` `CheckRequest`/`CheckResponse`/`DeniedHttpResponse`/`OkHttpResponse` (1/4/3/6) + `AttributeContext` with nested `Peer`/`Request`/`HttpRequest`/`TLSSession` (7/2/13/1). This is the largest single-filter proto surface in the §9 family to date.
2. **Two structurally distinct transports.** §5.P10 + §5.P11 confirmed the `grpc_service` and `http_service` arms diverge entirely in the call-and-marshal layer — a gRPC h2 dial + `CheckRequest`/`CheckResponse` protobuf marshalling path vs an `http.Client` POST + header-filtering + HTTP-response-parsing path. They share only the `compiledConfig` envelope + the `checkDisposition`-application logic.
3. **A brand-new gRPC-client framework primitive built from scratch.** envoy-go has **zero** `google.golang.org/grpc` usage. §5.P1 confirmed the `envoy.service.auth.v3` bindings (incl. the `Authorization/Check` client stub at `external_auth_grpc.pb.go`) DO ship in `go-control-plane v1.32.4` — so no codegen is required — but the dial + connection-management + error-classification layer is a heavier lift than phase-17's `internal/jwks/` (which built on the `net/http` stdlib).
4. **Full `AttributeContext` population + Full header-side mutation + request-body inclusion** are each substantial sub-surfaces; §5.P3/P4/P8 confirmed the population/gating/matcher detail; together they push the filter-package LoC well past phase-17's ~2399.

LoC estimate (refined post-§5): ~2400–3600 LoC production (filter package ~1300–1900 + `internal/grpcclient/` ~450–800 + the HTTP-outbound auth-check ~200–350 + the two test-helpers ~250–400). **Well above the ADR-0045 1500-LoC trigger.** Combined task count estimated at ~26–34 across both sub-phases — crosses both ADR-0045 thresholds (~25 tasks, ~1500 LoC).

The **structurally clean cut is by service-mode** (§2's table). This mirrors the phase 05 (downstream-h2 → upstream-h2) + phase 06 (stats-prometheus → access-log) + phase 07 (http-filter-framework → listener-chain-completion) + phase 08 (admin-endpoints → graceful-drain) precedents for surface-split-with-framework-primitive-on-the-second-half: 18.1 lands the foundational filter scaffold + the simpler HTTP transport; 18.2 lands the heavier gRPC transport + the strategic `internal/grpcclient/` primitive that future `ext_proc` + `global_ratelimit` reuse.

The split is SPEC-time (ADR-0045), decided in this session after the empirical-pin resolution. **ADR-0164 records the split-application decision in full at this SPEC commit** (mirroring phase-08's ADR-0084 documentation-of-application ADR). This is a SPEC-time ADR-count revision: the BRAINSTORM §7 anticipated 8 ADRs (ADR-0156..ADR-0163); this SPEC adds ADR-0164 (the split-application ADR) per ADR-0044's SPEC-time-anticipation-revision discipline — 9 ADRs total, next-free after phase 18 is ADR-0165.

## 4. Cross-cutting decisions (apply to BOTH 18.1 and 18.2)

### 4.1 Dual-mode `compiledConfig` envelope + the `checkDisposition` convergence

Both sub-phases share one `compiledConfig` shape and one `checkDisposition` value. The `ExtAuthz.services` oneof is resolved at config-load time → produces a `checkFn` closure on the `compiledConfig`. Both transport arms converge on a common `checkDisposition` value: `{class: allow|deny|error, headerMutations: …, denyStatus: …, denyBody: …, denyHeaders: …}`. The disposition-application logic (apply allow-path header mutations + optional `cb.ClearRouteCache()` → `HeaderContinue`; OR `cb.SendLocalReply(status, body, headers)` → `HeaderStopIteration`; OR apply the `failure_mode_allow` / `status_on_error` posture on `error`) is **mode-agnostic and lands in 18.1**. 18.1 defines the envelope with the `grpc_service` arm PARSE-REJECTing; 18.2 activates the gRPC arm. ADR-0157 anchors the envelope; its §Decision lands at 18.1 IMPL and is **amended at 18.2 IMPL** to activate the gRPC arm.

### 4.2 The `services` oneof is NOT PGV-required — the factory rejects an empty config itself

§5.P1 confirmed the `ExtAuthz.services` oneof carries NO PGV `required` constraint — a config with neither `grpc_service` nor `http_service` set passes `ExtAuthz.validate()`. Both sub-phases' factory paths must reject an empty `services` oneof themselves with an envoy-go-strict error (mirrors the phase-17 `internal/jwks` PARSE-REJECT-for-missing-`http_uri` PGV-mirror discipline). The only hard PGV scalar constraints on the `ExtAuthz` surface are `transport_api_version` (must be a defined enum value) and `BufferSettings.max_request_bytes` (`> 0`); `GrpcService_EnvoyGrpc.cluster_name` is `min_len: 1`; `ExtAuthzPerRoute.override` IS PGV-required with `disabled` constrained `const: true`. Everything else is embedded-message validation only. Both sub-phases' SPECs specialize the envoy-go-side defensive PGV-mirror validation discipline.

### 4.3 V3-only proto pin (ADR-0008)

`transport_api_version` non-V3 PARSE-REJECTs in both sub-phases (mirrors the ADR-0008 V3-only discipline). The `core.GrpcService.GoogleGrpc` arm PARSE-REJECTs envoy-go-strict (envoy-go uses the Go `google.golang.org/grpc` library; only the `EnvoyGrpc` cluster-reference arm is consumed) — this is an 18.2 concern but recorded here as a cross-cutting V3/transport invariant.

### 4.4 Deferred-field discipline (inline-deferral per phase-11 SPEC §8.1)

Both sub-phases honor the inline-deferral discipline (no omnibus deferral ADR; deferrals grouped by family-coupling, auditable in the ADR-0040 deferral trail). ### 5.10 §18.P10 — Error-classification boundary (RATIFIED)

**Probe:** Live behavioral scrape — `failure_mode_allow:false`, `status_on_error:503`; conditions: auth server down (connect failure), slow auth (timeout exceeded), gRPC transport `INTERNAL`, malformed/garbage response, gRPC `CheckResponse.status.code = UNAUTHENTICATED`, HTTP-mode unrecognized status.

| Condition | gRPC mode | HTTP mode | Classified |
|---|---|---|---|
| Auth server down (connect failure) | `503` | `503` | **error** → `status_on_error` |
| Slow auth (exceeds `timeout`) | `503` (~timeout+ε) | `503` | **error** → `status_on_error` |
| gRPC transport error (RPC fails `INTERNAL`) | `503` | n/a | **error** → `status_on_error` |
| Empty-but-valid `CheckResponse{}` (no oneof, `status.code`=0) | `200` allow | n/a | **allow** (`status.code`=0=OK) |
| HTTP-mode unrecognized status (`555`) | n/a | `503` | **error** → `status_on_error` |
| `CheckResponse.status.code` any non-OK (incl. `UNAUTHENTICATED`, not just `PERMISSION_DENIED`), RPC succeeded | `403` | n/a | **deny** (NOT error) |

With `failure_mode_allow:true` + auth down: the request proceeds → `200`, incrementing **both** `ext_authz.error` AND `ext_authz.failure_mode_allowed`.

**Disposition: RATIFIED.** The error-vs-deny boundary is crisp: transport/timeout/connect failure (and HTTP-mode unrecognized status) ⇒ **error** → `status_on_error`; any well-formed response carrying a non-OK decision ⇒ **deny** (default 403); an empty-but-structurally-valid `CheckResponse{}` ⇒ **allow**. envoy-go's `check.go` dispatcher classifies per this table; `failure_mode_allow` / `status_on_error` act on the **error** class only. §6 amendment 10 documents.

Two PGV wrinkles vs the bare buffer/compressor 5th canonical are recorded: `ExtAuthzPerRoute.disabled` is PGV `const: true` (the value MUST be `true` if the arm is used — envoy-go PARSE-REJECTs `disabled: false`), and the `override` oneof is itself PGV-required (envoy-go PARSE-REJECTs an empty `ExtAuthzPerRoute`). These wrinkles do not constitute a new canonical — buffer's `BufferPerRoute` has the same disabled-bool-in-required-oneof structure. ADR-0163 records the explicit no-ADR-0125-amendment 5th-canonical-REUSE classification. The `CheckSettings` override arm carries `context_extensions` (gRPC-mode-only per its doc-note) + `disable_request_body_buffering` + `with_request_body` — a NARROWER surface than listener-level `ExtAuthz`, exactly the 5th-canonical narrower-override discipline.

**Amendment 4 — `include_peer_certificate` + `include_tls_session` are honored-as-gates (BRAINSTORM §2.4 + §18.P3).** BRAINSTORM §2.4 left open whether Q4-"Full" `AttributeContext` population is unconditional or gated by `include_peer_certificate`/`include_tls_session`. §5.P3 RATIFIES: both are gates. The 18.2 gRPC-mode `AttributeContext` builder populates `Peer.certificate` only when `include_peer_certificate: true` (+ a cert is present) and `tls_session.sni` only when `include_tls_session: true` (+ a TLS connection). `source.principal` (via ADR-0144) + the `socket_address` Peer fields are NOT gated.

**Amendment 5 — gRPC `AttributeContext` population refined: `Timestamp` shape, omitted-when-empty, lowercased-headers (BRAINSTORM §2.4 + §18.P4).** §5.P4's live `CheckRequest` dump REFINES the brainstorm §2.4 population list: `request.time` is a `Timestamp{seconds,nanos}` (not an RFC3339 string); `request.http.query` and `request.http.fragment` are OMITTED when empty (not set to empty-string); the `request.http.headers` map keys are all lowercased and INCLUDE the `:authority`/`:method`/`:path`/`:scheme` pseudo-headers; Envoy injects `x-envoy-auth-partial-body: <bool>` into the header map. The 18.2 `attributes.go` builder mirrors this exactly. `tls_session` population is RATIFIED-PENDING-IMPL-TIME (the scrape used a plaintext listener).

**Amendment 6 — `with_request_body` over-limit → local 413 + `connection: close`, auth skipped (BRAINSTORM §2.3 + §18.P5).** BRAINSTORM §2.3 left the `allow_partial_message=false` over-limit disposition open (413 vs deny vs send-partial). §5.P5 RATIFIES: over-limit + `allow_partial_message:false` → Envoy emits a **local 413 `Payload Too Large` + `connection: close`** and NEVER contacts the auth service. Over-limit + `allow_partial_message:true` → the truncated `max_request_bytes`-byte prefix is sent, `http.size` reflects the true total, and `x-envoy-auth-partial-body:true` is injected. ADR-0162 anchors this; the 18.1 body-buffering path (ADR-0128 reuse) emits the 413 local-reply on the `allow_partial_message:false` over-limit branch BEFORE the outbound check fires.

**Amendment 7 — `disabled` counter is the runtime-gate counter, STRUCTURALLY UNREACHABLE under MVP; `filter_enabled` family defaults are no-ops (BRAINSTORM §5 + §6 + §18.P6 + §18.P12).** BRAINSTORM §6 fixture scenario 7 asserted per-route `disabled: true` → `ext_authz.disabled=1`. §5.P6 REFUTES — the per-route-disabled route was exercised 4× and the `disabled` counter stayed `0`; `disabled` increments ONLY via the filter-level runtime `filter_enabled` gate, which §5.P12 confirms is DEFERRED for MVP (and defaults to no-op when unset). Consequences: (a) the `disabled` counter registers in `filterStats` for scrape-stability but is STRUCTURALLY UNREACHABLE under MVP configs (publishes 0 — mirrors phase-17's `jwt_cache_hit`/`jwt_cache_miss` structurally-unreachable discipline); (b) **the per-route-`disabled` fixture scenario's counter assertion is corrected** to "per-route `disabled` → request 200 backend-echo; NO `ext_authz` counter increments; NOT `disabled=1`" — this is the 18.1 SPEC §7 fixture matrix **scenario 6** (renumbered from BRAINSTORM §6 scenario 7, since the gRPC scenarios were split out to 18.2's fixture); (c) the phase-18 fixture configs need NO explicit `filter_enabled` settings (unlike phase-11/12).

**Amendment 8 — Stat surface is 6 filter counters (71 → 77 names); no `cx_*`; cluster-scoped triple DEFERRED (BRAINSTORM §5 + §18.P6 + §18.P7).** BRAINSTORM §5 hypothesized ~5–8 base counters incl. possible `cx_http_*` connection counters and an `invalid` counter. §5.P6 REFINES: the canonical filter-stat surface is **6 counters** — `ok`, `denied`, `error`, `disabled`, `failure_mode_allowed`, `invalid` (all under `http.<HCM_stat_prefix>.ext_authz.*`; all counters; SN2-reuse per §5.P7). The brainstorm's `cx_http_*` hypothesis is REFUTED (no ext_authz-namespaced connection stats — connection observability lives in the standard cluster stat tree). The 5 extra v1.37.2 names (`filter_state_name_collision`/`ignored_dynamic_metadata`/`omitted_response_headers`/`request_header_limits_reached`/`response_header_limits_reached`) are DEFERRED (couple to deferred families). The cluster-scoped `cluster.<upstream>.ext_authz.{ok,denied,error}` triple is DEFERRED (a NEW stat-namespace pattern; couples to charging-into-the-cluster-stat-tree). Stat-table 71 → **77 names** (6 new). ADR-0163 anchors; the 6-counter table is RATIFIED-PENDING-IMPL-TIME per phase-16 §10 lesson (c).

**Amendment 9 — `allowed_client_headers_on_success` DEFERRED (decode-side-only filter shape) (BRAINSTORM §2.5 + §8 item 10 + §18.P9).** BRAINSTORM §2.5 + §8 item 10 left `allowed_client_headers_on_success` CONDITIONALLY DEFERRED pending the SPEC §18.P9 feasibility resolution. §5.P9 resolves: envoy-go's ext_authz filter is decode-side-only (`Encoder: nil`); honoring the field — copying auth-response headers to the downstream RESPONSE on the ALLOW path — requires an encode-side leg the MVP filter shape does not have. **DEFERRED.** The proto field PARSES (silent-ignore); the runtime never consults it. Documented as a divergence-window. ADR-0161 §Consequences records that the 18.1/18.2 IMPL sessions MAY revisit a stash-for-HCM mechanism if it proves cheap.

**Amendment 10 — Error-classification boundary RATIFIED (BRAINSTORM §2.7 + §18.P10).** BRAINSTORM §2.7 left the error-vs-deny boundary for the SPEC §18.P10 resolution. §5.P10 RATIFIES: transport/timeout/connect failure (+ HTTP-mode unrecognized status) ⇒ **error** → `status_on_error`; any well-formed response with a non-OK decision (gRPC `CheckResponse.status.code` any non-OK value, not just `PERMISSION_DENIED`; HTTP-mode recognized deny status) ⇒ **deny**; empty-but-valid `CheckResponse{}` ⇒ **allow**. `failure_mode_allow` / `status_on_error` act on the **error** class only; `failure_mode_allow:true` + error increments both `error` AND `failure_mode_allowed`. ADR-0157 anchors the error-classification boundary in the `check.go` dispatcher.

**Amendment 11 — Deny-path wire shape RATIFIED (BRAINSTORM §2.9 + §18.P11).** BRAINSTORM §2.9 left the deny-path byte-shape for the SPEC §18.P11 resolution. §5.P11 RATIFIES: body verbatim from the auth response; `content-length` synthesized by the `SendLocalReply` framework primitive (ADR-0085); gRPC `DeniedHttpResponse.headers` applied verbatim incl. `content-type`; HTTP-mode auth-response headers gated by `allowed_client_headers` with a `text/plain` fallback for the local-reply body; no `x-envoy-*` added; `server: envoy` + `date` from the framework standard set; header ordering = decision headers first, framework housekeeping after. ADR-0156 + ADR-0161 anchor.

**Amendment 12 — gRPC dial / TLS-to-auth-cluster plumbing RATIFIED-PENDING-IMPL-TIME (BRAINSTORM §7 + §18.P13).** §5.P13's gRPC scrape used a plaintext h2c auth cluster; the `EnvoyGrpc` cluster-reference → cluster-manager coupling + the TLS-to-auth-cluster path were not behaviorally exercised. RATIFIED-PENDING-IMPL-TIME: the `internal/grpcclient/` primitive's coupling to envoy-go's cluster manager (cluster-name → endpoint + transport-socket resolution) closes at an 18.2 PLAN/IMPL task; this is the most-likely ADR-0044 escape-valve surface for phase 18. The 18.1 sub-phase is unaffected.
