## 1. Mission and scope confirmation (18 only)

ROADMAP row `18 | http-filter-ext-authz | 17 | planned | | …` (added by this brainstorm, see §10 + the ROADMAP edit) is the row this brainstorm registers as `planned`. Phase 18 is the ELEVENTH concrete phase to enter the BOOTSTRAP_PROMPT.md §9 HTTP filters family heading (the family heading at `ROADMAP.md` line 66 — `### HTTP filters family` — is a conceptual umbrella, not a row, per ADR-0106). The phase 17 squash-merge commit `3cee1d3` (with SHA-fill at `d56d51a`) is this row's `depends-on` anchor.

The HTTP filters family lists candidate filters at `ROADMAP.md` line 66: header manipulation, cors, compression, fault, local + global rate limit, jwt_authn, rbac, ext_authz, ext_proc, oauth2, csrf, buffer, lua, wasm, adaptive concurrency, admission control, bandwidth limit. `cors` shipped in phase 07.1 (`internal/filter/http/cors/` per ADR-0074); `fault` shipped in phase 09 (`internal/filter/http/fault/` per ADR-0100); `header_mutation` shipped in phase 10 (`internal/filter/http/header_mutation/` per ADR-0108); `local_ratelimit` shipped in phase 11 (`internal/filter/http/localratelimit/` per ADR-0114); `csrf` shipped in phase 12 (`internal/filter/http/csrf/` per ADR-0120); `buffer` shipped in phase 13 (`internal/filter/http/buffer/` per ADR-0125); `compressor` shipped in phase 14 (`internal/filter/http/compressor/` per ADR-0129–ADR-0134); `bandwidth_limit` shipped in phase 15 (`internal/filter/http/bandwidthlimit/` per ADR-0135–ADR-0139); `rbac` shipped in phase 16 (`internal/filter/http/rbac/` + `internal/matcher/` per ADR-0140–ADR-0147); `jwt_authn` shipped in phase 17 (`internal/filter/http/jwtauthn/` + `internal/jwks/` + `internal/jwt/` per ADR-0148–ADR-0155). Phase 18 ships **external authorization delegation as a decode-side authentication/authorization gate** as the ELEVENTH real filter — the canonical Envoy-style "extract request attributes; ask an external auth service; allow / deny / mutate-headers" filter. The chosen branch + directory + Go-package identifier are aligned per phase-11 ADR-0114's underscore-stripping convention: branch `phase-18-http-filter-ext-authz-brainstorm` (preserves underscore for human readability of the source filter type-URL), directory `internal/filter/http/extauthz/` (underscore-stripped per ADR-0114; matches `localratelimit/` + `jwtauthn/` precedent), Go package identifier `extauthz` (same as directory).

Phase 18 is also: (i) the FIRST §9 family-row whose configuration **delegates the authorization decision itself to an external service** — distinct from all prior §9 rows including jwt_authn (jwt_authn fetches a remote JWKS key set but makes the allow/deny decision locally with `internal/jwt/`; ext_authz ships the request attributes to a separate process/service and the *decision* arrives over the wire). This introduces a new failure-mode class — the auth service can be unreachable, slow, or return malformed responses — handled by the `failure_mode_allow` / `status_on_error` posture (§2.7). (ii) the FIRST §9 family-row to introduce **gRPC infrastructure** in envoy-go — the repo currently has zero `google.golang.org/grpc` usage of any kind (no dial, no stubs, no compiled service bindings); the `grpc_service` mode requires a brand-new gRPC-client framework primitive (§3.1). Phase 17 introduced the FIRST outbound-HTTP-from-filter primitive (`internal/jwks/`); phase 18 introduces the FIRST outbound-gRPC-from-filter primitive — the strategic foundation for the entire RPC-delegating filter family (`ext_proc`, `global_ratelimit` all consume gRPC-outbound resources). (iii) the FIRST §9 family-row to **REUSE a canonical per-route pattern rather than add one** — `ExtAuthzPerRoute{oneof{disabled(bool) | check_settings(CheckSettings)}}` maps cleanly onto ADR-0125's existing 5th canonical (disabled-OR-override sum-type with SHARED-stats), the pattern phase-13 buffer + phase-14 compressor already use; phase 18 lands NO ADR-0125 amendment paragraph, breaking the phase-13-through-17 per-phase-roster-growth streak (§4). (iv) the FIRST §9 family-row whose **MVP envelope spans two structurally distinct service-call transports** (gRPC + HTTP) selected by a proto `oneof` — both consumed proto-faithful per Q2, which is the dominant ADR-0045 split-readiness driver (§1.4). (v) the FIRST §9 family-row to interact with the framework's decode-side body-buffering machinery (phase-13 ADR-0128) as a *consumer* rather than its introducer — `with_request_body` reuses ADR-0128 to materialize the request body for inclusion in the auth check (§2.3 + §3.3).

4. **Dual-mode check dispatcher (Decision #1 → ADR-0157 + ADR-0158 + ADR-0159).** The `services` oneof selects the transport at config-load time → produces a `checkFn` closure on the `compiledConfig`. The gRPC arm dials the configured `grpc_service` cluster and invokes `envoy.service.auth.v3.Authorization/Check` with a populated `CheckRequest`; the HTTP arm POSTs to the configured `http_service.uri` (+ `path_prefix`) with the filtered request headers (+ optional body). Both arms converge on a common `checkDisposition` value — `{allow, deny, error}` plus the header-mutation set + (on deny) the response status/body/headers. The dispatcher is async: the outbound call parks the decode-side dispatch goroutine on the per-stream resume channel (mirroring the phase-09 fault async-resume primitive — `StopIteration` + a goroutine performing the call + `cb.ContinueDecoding()` on completion) so the HCM dispatch goroutine is not blocked on network I/O. `OnDestroy` cancels the in-flight call's `context.Context` (the FIRST §9 row with a per-request cancellable outbound call — mirrors no prior precedent exactly; jwt_authn's JWKS fetch was background, not per-request).

5. **Filter-callback shape: `StreamDecoderFilter` ONLY on the `*filter` instance.** Phase 18 is decode-side only — `ext_authz` is a request-gate filter, evaluated at `DecodeHeaders` time (with an async-resume leg for the outbound call + the body-buffering wait when `with_request_body` is set), with the disposition (allow / deny) computed BEFORE the request body is forwarded upstream. The filter does NOT implement `StreamEncoderFilter`. Static blank-identifier compile-time check for `StreamDecoderFilter` only. The decode-side surface: `DecodeHeaders(headers, endStream)` resolves per-route → caches `*compiledPerRoute` on filter state → if `with_request_body` is set, returns `HeaderStopIteration` and waits for the body via the ADR-0128 decode-side body-buffering primitive; otherwise (or once the body is buffered) builds the `AttributeContext` / HTTP `AuthorizationRequest`, fires the async outbound check, and on resume applies the disposition — on allow, applies the allow-path header mutations + (if `clear_route_cache`) invokes `cb.ClearRouteCache()` + returns `HeaderContinue`; on deny, invokes `cb.SendLocalReply(<status>, <body>, <headers>)` and returns `HeaderStopIteration`; on error, applies the `failure_mode_allow` / `status_on_error` posture. `DecodeData` participates in the ADR-0128 body-buffering interaction when `with_request_body` is set (otherwise pass-through). `DecodeTrailers` pass-through.

6. **AttributeContext + AuthorizationRequest builder (Decision #3 → ADR-0160).** Per Q4 Full-peer-request-TLS: the gRPC-mode builder populates `CheckRequest.attributes` (`AttributeContext`) with `source` + `destination` Peers (`address` as `core.Address` socket-address; `principal` via the phase-16 ADR-0144 `DecoderFilterCallbacks.DownstreamPrincipal()` accessor; `certificate` when available), `request.time` + `request.http` (`id`, `method`, `path`, `host`, `scheme`, `query`, `fragment`, `size`, `protocol`, `headers`, and `body` / `raw_body` when `with_request_body` is set + `pack_as_bytes` governs `body`-vs-`raw_body`), `tls_session.sni`, and `context_extensions` (merged from per-route `CheckSettings.context_extensions`). The HTTP-mode builder constructs the outbound POST: filters client headers through `AuthorizationRequest.allowed_headers` (a `ListStringMatcher` — SPEC §10 pin §18.P8 confirms the matcher subset), adds `AuthorizationRequest.headers_to_add`, prepends `path_prefix`, and includes the body when `with_request_body` is set. ADR-0160 anchors the builder discipline + the per-field population rules + the `DownstreamPrincipal()` reuse.

7. **Header-mutation discipline (Decision #4 → ADR-0161).** Per Q5 Full-header-side: on **allow**, the response from the auth service carries headers to inject into the *upstream* request — gRPC `OkHttpResponse.{headers (append/overwrite per HeaderValueOption), headers_to_remove, response_headers_to_add}`, HTTP `authorization_response.{allowed_upstream_headers, allowed_upstream_headers_to_append}` filtering the auth service's response headers. On **deny**, the auth service's response carries headers + body + status to emit *downstream* — gRPC `DeniedHttpResponse.{status, body, headers}`, HTTP `authorization_response.allowed_client_headers` filtering. On **allow with `allowed_client_headers_on_success`**, a subset of the auth response headers is ALSO copied to the eventual downstream response (a deferred-to-encode-side concern — SPEC §10 pin §18.P9 confirms whether envoy-go's decode-side-only filter shape can honor this or whether it defers). The `validate_mutations` flag gates whether header-name/value safety validation rejects the mutation (mirrors the phase-10 header_mutation protected-header discipline). Deferred: `query_parameters_to_set/remove` (path-query subsystem per ADR-0112); `dynamic_metadata_from_headers` (dynamic-metadata family). ADR-0161 anchors the bidirectional header-mutation emit-order + the per-direction filtering rules.

### 2.2 Service-mode envelope: Both proto-faithful *(Decision #1 → ADR-0157 + ADR-0158 + ADR-0159)*

Per Q2 = "Both RemoteJwks-... — Both gRPC + HTTP proto-faithful", the proto's `ExtAuthz.services` oneof has two arms; phase 18 consumes BOTH. **gRPC mode** (`grpc_service` → a `core.GrpcService` pointing at a cluster) requires the new gRPC-client framework primitive (§3.1) — dial the cluster, invoke `envoy.service.auth.v3.Authorization/Check`, marshal a `CheckRequest`, unmarshal the `CheckResponse`. **HTTP mode** (`http_service` → a `uri` + `timeout` + `path_prefix` + request/response-side header rules) requires the HTTP-outbound auth-check (§3.2) — POST the filtered request to the URI, parse the HTTP response status/body/headers into a disposition. The hybrid surface enables real-world deployment parity (most production ext_authz deployments use gRPC; HTTP mode serves simpler/legacy auth services). Tradeoff: the MVP envelope spans two structurally distinct transports — the dominant ADR-0045 split-readiness driver (§1.4). ADR-0157 anchors the dual-mode `compiledConfig` envelope + the `services`-oneof dispatch; ADR-0158 anchors the gRPC-client framework primitive; ADR-0159 anchors the HTTP-outbound auth-check.

### 2.3 Request body inclusion: Include proto-faithful *(Decision #2 → ADR-0162)*

Per Q3 = "Include, proto-faithful", phase 18 consumes `with_request_body` (`BufferSettings{max_request_bytes, allow_partial_message, pack_as_bytes}`). When set, the filter buffers the request body up to `max_request_bytes` (reusing the phase-13 ADR-0128 decode-side body-buffering primitive — a load-bearing reusability demonstration mirroring phase-15 bandwidth_limit's reuse of ADR-0128/ADR-0131) and includes it in the auth check — for gRPC mode in `AttributeContext.request.http.body` (string) or `.raw_body` (bytes) governed by `pack_as_bytes`; for HTTP mode as the POST body. `allow_partial_message` governs the over-`max_request_bytes` behavior: when true, the buffered prefix is sent and the request proceeds; when false, an over-limit body is rejected (SPEC §10 pin §18.P5 confirms the exact reference-Envoy disposition — 413 local-reply vs send-partial vs deny). The body-buffering interaction makes `DecodeHeaders` return `HeaderStopIteration` when `with_request_body` is set, with the outbound check deferred until the body is materialized via `DecodeData`. ADR-0162 anchors the body-inclusion discipline + the ADR-0128 reuse + the `allow_partial_message` edge case + the `pack_as_bytes` shape.

### 2.4 gRPC AttributeContext population: Full peer + request + TLS *(Decision #3 → ADR-0160)*

Per Q4 = "Full peer + request + TLS", phase 18's gRPC-mode `CheckRequest.attributes` (`AttributeContext`) population covers: `source` Peer (`address` socket-address; `principal` via the phase-16 ADR-0144 `DownstreamPrincipal()` accessor; `certificate` when the downstream presented one), `destination` Peer (`address`), `request.time` + `request.http` (`id`, `method`, `path`, `host`, `scheme`, `query`, `fragment`, `size`, `protocol`, `headers` map, and `body`/`raw_body` when `with_request_body` is set per §2.3), `tls_session.sni`, and `context_extensions` (merged from per-route `CheckSettings.context_extensions`). This is the richest auth surface — the external auth service can decide on client identity (mTLS principal + cert), connection attributes (source/destination address, SNI), and the full request shape. The `metadata_context` / `route_metadata_context` AttributeContext fields are DEFERRED (couple to the dynamic-metadata family — §8). SPEC §10 pin §18.P3 confirms whether `include_peer_certificate` + `include_tls_session` are honored-as-gates (i.e. the cert/SNI population is conditional on those bools) or whether the Q4 Full pick populates unconditionally. ADR-0160 anchors the AttributeContext builder + the `DownstreamPrincipal()` reuse + the per-field population rules.

### 2.5 Header-mutation faithfulness: Full header-side proto-faithful *(Decision #4 → ADR-0161)*

Per Q5 = "Full header-side proto-faithful", phase 18 honors the bidirectional header-mutation surface:

- **Request-side (into the auth request):** HTTP mode — `AuthorizationRequest.allowed_headers` (a `ListStringMatcher` filtering which client headers are forwarded to the auth service) + `AuthorizationRequest.headers_to_add` (static headers added to the auth request). gRPC mode — the full client header map is conveyed in `AttributeContext.request.http.headers` (no separate allow-list at the proto level for gRPC).
- **Allow-path (into the upstream request):** gRPC mode — `OkHttpResponse.headers` (`HeaderValueOption` set; append/overwrite per the option's `append_action`), `OkHttpResponse.headers_to_remove`, `OkHttpResponse.response_headers_to_add`. HTTP mode — `authorization_response.allowed_upstream_headers` + `allowed_upstream_headers_to_append` filtering the auth service's HTTP response headers into the upstream request.
- **Deny-path (into the downstream response):** gRPC mode — `DeniedHttpResponse.{status, body, headers}` emitted verbatim via `SendLocalReply`. HTTP mode — the auth service's HTTP response status/body + `authorization_response.allowed_client_headers` filtering its response headers into the downstream response.
- **Allow-with-client-headers:** `allowed_client_headers_on_success` copies a subset of the auth response headers to the eventual downstream response on the allow path — SPEC §10 pin §18.P9 confirms whether envoy-go's decode-side-only filter shape can honor this (it may require deferring to an encode-side leg the MVP filter shape doesn't have; if so it defers per §8).

`validate_mutations` gates header-name/value safety validation (mirrors the phase-10 header_mutation protected-header discipline — protected pseudo-headers rejected). Deferred: `query_parameters_to_set/remove` (path-query subsystem per ADR-0112); `dynamic_metadata_from_headers` (dynamic-metadata family). ADR-0161 anchors the bidirectional emit-order + per-direction filtering rules.

### 2.6 Per-route discipline: 5th canonical REUSE + SHARED stats *(Decision #5 → ADR-0163, NO ADR-0125 amendment)*

Per Q6 = "5th canonical reuse + SHARED stats", phase 18's `ExtAuthzPerRoute` proto — `oneof{disabled(bool) | check_settings(CheckSettings)}` — maps cleanly onto ADR-0125's **existing 5th canonical** (disabled-OR-override sum-type with SHARED-stats; the pattern phase-13 buffer + phase-14 compressor already use). The `disabled` arm wholly deactivates the filter on the route (no auth check, no counter increments, request forwards as-is). The `check_settings` arm carries a `CheckSettings` message — a NARROWER per-route override surface (`context_extensions` merged into the AttributeContext; `disable_request_body_buffering`; possibly `with_request_body` per-route) — exactly analogous to compressor's per-route `ResponseDirectionOverrides` being narrower than its listener-level config. **Phase 18 is the FIRST §9 family-row to REUSE an ADR-0125 canonical rather than add one** — it lands NO ADR-0125 amendment paragraph, breaking the phase-13-§(ix) / phase-14-§(x) / phase-15-§(xi) / phase-16-§(xii) / phase-17-§(xiii) per-phase-roster-growth streak. Per-route stats SHARED with listener-level (per-route adjusts `context_extensions`/buffering but still calls the same auth service — no new stateful policy-evaluation surface, unlike phase-11/15/16's INDEPENDENT-stats stateful filters; mirrors phase-12/13/14/17 SHARED-stats). ADR-0163 anchors the per-route parsing + the explicit 5th-canonical-reuse classification + the SHARED-stats discipline + the stat surface (§5).

### 2.7 Error-handling posture *(self-answered → ADR-0157)*

NOT requiring live input — core ext_authz semantics, consumed proto-faithful. `failure_mode_allow` (bool; default false): when the auth service is unreachable / times out / returns a malformed response, `false` → the request is denied (with `status_on_error`'s status, default 403) and `true` → the request is allowed through. `failure_mode_allow_header_add` (bool): when `failure_mode_allow` allowed an erroring request through, adds an `x-envoy-auth-failure-mode-allowed: true` header to the upstream request so the backend can observe the bypass. `status_on_error` (`*HttpStatus`): the HTTP status used for the deny-on-error path (default 403). `validate_mutations` (bool): gates response-mutation safety validation (§2.5). These four fields are consumed proto-faithful; the SPEC §10 empirical-pin block confirms the exact reference-Envoy defaults + the error-classification boundary (what counts as an "error" — connect failure, timeout, non-200 HTTP, gRPC non-OK status, malformed response — per pin §18.P10). ADR-0157 (the dual-mode `compiledConfig` ADR) anchors the error-posture fields alongside the service-oneof dispatch.

Per §5 below + SPEC §10 pins §18.P6/P7. ### 2.9 Deny-path wire shape *(self-answered → ADR-0156 + ADR-0161)*

On a deny disposition, the filter emits `SendLocalReply(<status>, <body>, <headers>)` where the status/body/headers come from the auth service's response: gRPC mode — `DeniedHttpResponse.{status, body, headers}`; HTTP mode — the auth service's HTTP response status + body + the `allowed_client_headers`-filtered headers. On an error disposition with `failure_mode_allow=false` — `SendLocalReply(status_on_error, ...)` with the default 403 if `status_on_error` is unset. The exact byte-shape of the deny response (whether envoy-go reproduces the auth service's body verbatim, whether a `Content-Length` / `Content-Type` is synthesized, the header-set ordering) is a SPEC §10 empirical-pin §18.P11 against reference Envoy v1.37.2 — mirroring the phase-09/11/12/16/17 `SendLocalReply` wire-shape empirical-pin discipline. ext_authz is the FIRST §9 row whose deny-path status code is **not fixed by the filter** — it is whatever the auth service returns (or `status_on_error`), unlike fault's `[200,600)`-constrained abort, csrf/rbac's fixed 403, local_ratelimit's 429, jwt_authn's 401-or-403. ADR-0156 anchors the filterStats + the deny-path mechanism; ADR-0161 anchors the deny-path header-set construction.

## 3. Framework-survey result — TWO new primitives + TWO reuses

Phase 18 introduces TWO new framework primitives, both designed cross-phase-reusable at introduction time per the phase-16 (ADR-0142 + ADR-0144) + phase-17 (ADR-0150 + ADR-0151) framework-primitive-introduction discipline. The framework survey evaluated reuse of phase-09-through-17 primitives BEFORE proposing new — per phase-16 §10 lesson (a) + lesson (d) + phase-17 §3 discipline. Findings:

- **Phase-09 `time.AfterFunc` + `cb.ContinueDecoding/Encoding` async-resume primitives**: **REUSED** — the outbound check (gRPC or HTTP) is async; the filter parks the decode dispatch goroutine and resumes on call completion. This is the SAME async-resume primitive fault introduced; ext_authz is its load-bearing re-consumer for a per-request *outbound* call (fault used it for an internal timer).
- **Phase-11 token-bucket primitive**: NOT reused (no rate-limiting at ext_authz).
- **Phase-13 ADR-0128 decode-side body-buffering primitives**: **REUSED** — `with_request_body` materializes the request body via ADR-0128 (§2.3). Load-bearing reusability demonstration.
- **Phase-14 ADR-0131 `EncoderFilterCallbacks.OverwriteBody`**: NOT reused (ext_authz is decode-side only; the deny-path response goes through `SendLocalReply`, not encode-side body overwrite).
- **Phase-16 ADR-0142 matcher-engine at `internal/matcher/`**: NOT reused at phase-18 MVP (ext_authz has no `xds.type.matcher.v3.Matcher`-typed config field; per-route is the simple 5th-canonical oneof; `filter_enabled_metadata` is a `MetadataMatcher` but it is DEFERRED per §8).
- **Phase-16 ADR-0144 TLS-principal accessor `DownstreamPrincipal()`**: **REUSED** — the gRPC `AttributeContext.source.principal` field is exactly the TLS-principal accessor's output (§2.4). Load-bearing reuse.
- **Phase-17 ADR-0150 `internal/jwks/Fetcher` outbound-HTTP structure**: **COMPOSED-AGAINST** — the HTTP-mode auth-check (§3.2) reuses the `http.Client` + timeout + retry structure the JWKS fetcher established; the SPEC author decides whether to generalize that structure into a shared `internal/httpclient/` package.
- **Phase-17 ADR-0151 `internal/jwt/` verifier**: NOT reused at phase-18 MVP (ext_authz delegates the decision; it does not verify JWTs locally — though a future ext_authz extension or a downstream filter could).
- **ADR-0125 8 canonical per-route patterns**: NO NEW canonical needed — the 5th canonical is REUSED (§2.6 + §4).

**Zero-delta is NOT feasible** for phase 18 — the `grpc_service` proto-faithful Q2 pick requires the gRPC-client primitive (envoy-go has zero gRPC infrastructure), and the `http_service` arm requires the HTTP-outbound auth-check. Both primitives are clean cross-phase-reusable lifts.

### 3.1 gRPC-client outbound primitive — `internal/grpcclient/` package *(ADR-0158)*

A new top-level Go package `internal/grpcclient/` (location TBD at SPEC time — the SPEC author confirms whether the package is ext_authz-generic or `Authorization`-service-specific; the strategic intent is generic). envoy-go currently has **zero** `google.golang.org/grpc` usage of any kind — no dial, no client stubs, no compiled service bindings (`go-control-plane` ships the `envoy.service.auth.v3` bindings but they are not imported anywhere, so they are not codegen'd in). The package establishes:

- A dial + connection-management layer over `google.golang.org/grpc` — dial a `core.GrpcService`-described cluster (the `GrpcService.EnvoyGrpc` arm references an envoy-go cluster by name; the `GrpcService.GoogleGrpc` arm is likely DEFERRED — SPEC §10 pin §18.P7 confirms), with the configured timeout + connection reuse.
- The `envoy.service.auth.v3.Authorization/Check` client stub — the FIRST compiled gRPC service stub in envoy-go.
- An error-classification layer — gRPC status codes + transport failures → the `{allow, deny, error}` disposition classes that `failure_mode_allow` / `status_on_error` act on.

Cross-phase reuse intent (codified at ADR-0158 §Decision): future filters consuming outbound-gRPC-from-filter primitives reuse the dial + connection-management + error-classification layer and extend with their own service stubs. The strategic reuse targets are: future `ext_proc` (bidirectional `Process` streaming over gRPC — reuses the dial layer, extends with stream management); future `global_ratelimit` (the `RateLimitService/ShouldRateLimit` unary call — reuses dial + error-classification, swaps the service stub). The package lives OUTSIDE `internal/filter/` (mirroring phase-16's `internal/matcher/` + phase-17's `internal/jwks/` + `internal/jwt/`) explicitly to anchor cross-phase reusability. The BEHAVIOR_CONTRACT NEW top-level `## gRPC client framework primitive` umbrella anchors operator-facing semantics; future filters extend the umbrella additively.

### 3.2 HTTP-outbound auth-check — composes against `internal/jwks/Fetcher` *(ADR-0159)*

The HTTP-mode auth-check POSTs the filtered request (headers via `allowed_headers` + `headers_to_add`, plus the body when `with_request_body` is set, plus the `path_prefix`-prepended path) to the configured `http_service.uri` and parses the HTTP response status/body/headers into a disposition. This composes against the phase-17 `internal/jwks/Fetcher`'s established outbound-HTTP structure — the `http.Client`, the configurable timeout, the retry discipline. The SPEC author decides at SPEC time whether to:
