## 1. Purpose / Mission

Deliver envoy-go's THIRD stats-export sink and the THIRD consumer of the bootstrap `stats_sinks[]` `DogStatsdSink` TypeURL: when the bootstrap carries a `dog_statsd` `stats_sinks[]` entry with a UDP `address`, envoy-go dials that UDP address once (`net.DialUDP` — a SECOND, independent `*net.UDPConn`, phase-48-shaped) and every `stats_flush_interval` (default 5s) snapshots the frozen process-global `stats.Registry` (via the SAME `snapshot()` the metrics_service/statsd sinks use — `mapping.go:22`) and writes one DogStatsd line per metric as a UDP datagram to the configured address: `<prefix>.<residual-name>:<value>|c[|#tag1:val1,...]` for each COUNTER family (the value is the **per-flush delta** — D-DSD-DELTA, CONFIRMED independently of phase 48's plain-statsd answer, matching it), `<prefix>.<residual-name>:<value>|g[|#tags]` for each GAUGE family (the value is the **absolute** current value), `<residual-name>` = `stats.ExtractTags`'s residual dotted name (tag-value segments removed, dots preserved — the SAME extraction the 47.2b `labelMapper` uses, D-DSD-NAME CONFIRMED byte-identical), the extracted tags formatted `envoy.<key>:<value>` pairs comma-joined in NATURAL (unsorted) extraction order (D-DSD-TAGS — CONFIRMED to be delimiter `,`/`:`, tag-key format IDENTICAL to the 47.2b `labelMapper` convention `"envoy."+strings.TrimPrefix(l.Key,"envoy_")`, and — the LOAD-BEARING correction vs the BRAINSTORM — the reference does NOT alphabetically sort; §1.1 AMEND-DSD-TAGS-ORDER), `<prefix>` = `DogStatsdSink.prefix` joined `prefix + "." + residual-name` (default `envoy`, CONFIRMED). This composes ENTIRELY on the phase-47/48 substrate (the `Flusher` registry-snapshot loop, the `Sink` interface, the `snapshot()` cumulative-absolute mapping, the `deltaState` per-flush-delta transform, the `stats.ExtractTags` tag-extraction core, the `stats_sinks[]`/`stats_flush_interval` parse, the `main.go` post-Freeze flusher build) — it adds NO new framework piece: ONE new `Sink` impl (`internal/statssink/dogstatsd.go`), ONE new bootstrap parse arm, ONE new config struct, a SECOND UDP datagram seam (phase-48-shaped, independent). The `MetricsServiceSink`, `StatsdSink`, and `DogStatsdSink` coexist in the same `statsSinks []Sink` slice; the `Flusher` stays sink-agnostic and fans the same absolute batch to all three. ZERO new Go packages, ZERO new go.mod modules (the DogStatsd line protocol is hand-rolled `strconv`/`net` + the ALREADY-shared `stats.ExtractTags` — no client lib; the `DogStatsdSink` proto resolves at the ALREADY-imported `config/metrics/v3` package). ### 1.1 Empirical-finding-driven scope (amendment block per ADR-0044)

The §11 live probe (2026-07-02, contrib-v1.37.2 — an H1 downstream :10000 `stat_prefix=ingress_http` → an `hashicorp/http-echo` backend, K=7 requests, with a bootstrap `dog_statsd` `stats_sinks[]` entry [UDP `address` → a driver-owned Go UDP receiver at a static bridge IP `172.31.98.10:8125`, `prefix: probepfx`] + `stats_flush_interval=1s`, all on a shared Docker bridge per `reference_docker_probe_bridge_network`; four probe runs: the base topology, a no-`address` variant, an explicit `max_bytes_per_datagram: 512` variant, a no-`prefix` variant, and a `protocol: TCP` variant) CONFIRMED the brainstorm's core hypotheses (residual-name projection, prefix join, tag-key format, +0 self-stats) and RESOLVED the two LOAD-BEARING D-DSD-DELTA/D-DSD-TAGS questions. The findings that RESHAPE the design vs the brainstorm's "self-answered"/proposed defaults:

- **AMEND-DSD-DELTA-CONFIRMED (the FIRST LOAD-BEARING finding — counter `|c` is a per-flush DELTA-since-last-flush, INDEPENDENTLY confirmed to match phase 48's plain-statsd answer, NOT assumed).** Live finding (D-DSD-DELTA): `probepfx.cluster.upstream_rq_total` (tagged `envoy.cluster_name:backend`) emitted `6|c` then `1|c` then `0|c` then `0|c` across four flushes in the base run (SUM==7==K) and `7|c` then `0|c` then `0|c` in the no-prefix run (SUM==7==K); `probepfx.http.downstream_rq_total` (tagged `envoy.http_conn_manager_prefix:ingress_http`) emitted `6,1,0,0` (SUM==7==K). This is the canonical DogStatsd increment semantics, matching plain statsd. **Consequence:** the `DogStatsdSink` UNCONDITIONALLY owns its OWN sink-private `deltaState` — a SECOND, INDEPENDENT instance from `StatsdSink`'s (never shared; each sink builds its own delta batch off the same absolute snapshot, per the `delta.go` contract that forbids mutating the shared slice) — and `0093` asserts the delta-SUM with a post-convergence stability barrier (`reference_delta_sink_differential_stability_barrier`), NOT an absolute `value==K` last-seen. GAUGES (`|g`) are absolute (e.g. `cluster.membership_total:1|g` tagged `envoy.cluster_name:backend`), no sign prefix.
- **AMEND-DSD-TAGS-ORDER (the SECOND LOAD-BEARING finding — the reference does NOT alphabetically sort multi-tag suffixes; it emits tags in NATURAL EXTRACTION order, which happens to be IDENTICAL to `stats.ExtractTags`'s own return order for every shape envoy-go can produce ⇒ the `DogStatsdSink` tag formatter must NOT sort, reversing the BRAINSTORM §2.3 "tags SORTED" default).** Live finding (D-DSD-TAGS): a two-tag line reads `probepfx.cluster.external.upstream_rq_xx:0|c|#envoy.response_code_class:2,envoy.cluster_name:backend` — `response_code_class` BEFORE `cluster_name`, which is the REVERSE of alphabetical order (`cluster_name` < `response_code_class`). This is not an accident of this one stat: `stats.ExtractTags` (`internal/stats/name.go:47`) implements Rule SN4 (the `_Nxx` status-class collapse) by *prepending* the `envoy_response_code_class` label to the FRONT of the label slice returned by the earlier SN1/SN2/SN3 base-rule match (`name.go:354-357`, `labels = append([]Label{...}, labels...)`) — so `ExtractTags`'s own natural (unsorted) return order for any envoy-go stat with BOTH an `_Nxx` suffix and a base tag is ALWAYS `[response_code_class, <base-tag>]`, which is exactly the reference's observed order. Sorting alphabetically (the BRAINSTORM's proposed determinism default) would put `cluster_name` FIRST, diverging from the reference for every `_2xx`/`_4xx`/etc.-suffixed counter (the majority of envoy-go's tag-bearing stats). **Consequence:** the `DogStatsdSink` tag formatter iterates the `[]Label` slice `stats.ExtractTags` returns AS-IS (no `sort.Slice` — CONTRAST the 47.2b `labelMapper`, which sorts because `LabelPair` order is immaterial to a structured Prometheus label set, whereas a DogStatsd tag suffix is a literal wire string where order is part of the byte-format). This is SIMPLER (no sort call) AND reference-parity for every shape envoy-go can produce (envoy-go's tag sets are at most 2 elements: an optional `response_code_class` SN4 label prepended in front of at most one SN1/SN2/SN3/SN9/mongo/redis/thrift base tag — never more, since `ExtractTags` dispatches on exactly one top-level prefix rule per name). The `0093` differential asserts the tag SET (order-independent set-equality on the parsed `|#` suffix), not a literal-string tag-order match — so this finding governs the PRODUCTION formatter's behavior, while the differential's own assertion stays robust to either choice; the finding is recorded because reference-parity is the cheaper AND more correct implementation, not because the differential requires it.
- **AMEND-DSD-NAME-CONFIRMED (the residual-name projection is BYTE-IDENTICAL to `stats.ExtractTags`'s own residual; the prefix join is `prefix + "." + residual-name`; the default prefix is `envoy`).** Live finding (D-DSD-NAME): `cluster.backend.upstream_rq_total` → residual `cluster.upstream_rq_total` tagged `envoy.cluster_name:backend`; `http.ingress_http.downstream_rq_total` → residual `http.downstream_rq_total` tagged `envoy.http_conn_manager_prefix:ingress_http` — EXACTLY the SN1/SN2 residual + label split `stats.ExtractTags` already implements (the SAME function the 47.2b `labelMapper` calls, now confirmed to ALSO match the dog_statsd wire projection, not just the metrics_service one). Untagged names (`server.*`, `runtime.*`, `listener_manager.*`, etc.) emit with NO `|#` suffix at all (CONFIRMED — e.g. `probepfx.runtime.num_keys:0|g`, no trailing pipe). The no-prefix probe variant emitted `envoy.cluster.upstream_rq_total:...` — **default prefix CONFIRMED `envoy`** (identical to statsd).
- **AMEND-DSD-LINE-CONFIRMED (one DogStatsd line per UDP datagram BY DEFAULT — `max_bytes_per_datagram` unset; integer values; no `@rate` sampling suffix; no signed values; `|ms` timers present but unreachable for envoy-go).** Live finding (D-DSD-LINE): the base/no-prefix/protocol-TCP probe runs emitted exclusively single-line datagrams (max ~155 bytes observed), framed `<prefix>.<residual-name>:<int>|<type>[|#tags]`. - **AMEND-DSD-REJECT (`max_bytes_per_datagram`, when EXPLICITLY set, is HONORED by the reference — it produces multi-metric NEWLINE-BATCHED datagrams up to the byte cap — so envoy-go-STRICT-REJECTING it this row is a REQUIRED anti-silent-divergence guard, not a defensive-only posture; a missing `dog_statsd_specifier`/address is a REFERENCE-PARITY reject; `socket_address.protocol` is accepted-and-IGNORED, identical to statsd).** Live finding (D-DSD-REJECT, 3 config variants beyond the base): a `DogStatsdSink` with NO `address` → the reference REJECTS at config-load (`Proto constraint validation failed (field: "dog_statsd_specifier", reason: is required)`, exit 1 — a PGV oneof-required constraint, IDENTICAL wording-shape to the phase-48 `statsd_specifier` finding); an EXPLICIT `max_bytes_per_datagram: 512` → the reference BOOTS and DEMONSTRABLY BATCHES — datagrams grow to the 512-byte cap and contain MULTIPLE newline-separated `name:value|type[|#tags]` lines per datagram (up to 6 metrics observed in one 512-byte datagram; confirmed by inspecting the raw multi-line payload, not just the byte count); a `socket_address` with `protocol: TCP` → BOOTS and STILL delivers UDP datagrams to the receiver (the reference IGNORES `protocol` for the dog_statsd sink too — always UDP, matching phase-48's `StatsdSink` finding on the identical shared `core.v3.Address` field). ⇒ envoy-go REFERENCE-PARITY on the missing-`dog_statsd_specifier` reject; envoy-go-STRICT (ADR-0080 anti-silent-divergence) on an EXPLICIT `max_bytes_per_datagram` (honoring the field's ABSENCE as one-per-datagram is reference-parity for the common/default case, but SILENTLY IGNORING an explicit non-default value would silently under-batch relative to what the operator configured — this is a MEANINGFUL divergence, unlike `protocol`, which the reference itself ignores); the `protocol` field is accepted-and-ignored (envoy-go dials UDP regardless).

### 3.3 The `DogStatsdSink` (`internal/statssink/dogstatsd.go`) — a `Sink` over a `*net.UDPConn` + the DogStatsd-line-with-tags mapping

ONE new file in the EXISTING `internal/statssink` package (a sibling to `sink.go`'s `MetricsServiceSink` and `statsd.go`'s `StatsdSink`, phase-48-shaped). It satisfies the EXISTING `Sink` interface (`sink.go:18` — `Submit(batch []*dto.MetricFamily)` / `Close() error`):

- **Construction:** `NewDogStatsdSink(udpAddr string, prefix string) (*DogStatsdSink, error)` — `net.ResolveUDPAddr("udp", udpAddr)` + `net.DialUDP("udp", nil, raddr)`; stores the `*net.UDPConn`, the `prefix`, and a sink-private `deltaState` (`newDeltaState()` — AMEND-DSD-DELTA-CONFIRMED, ALWAYS, no knob, a SEPARATE instance from any `StatsdSink`'s). A dial error is returned (→ `main.go` `log.Fatalf`, the `StatsdSink`-error precedent).
- **`Submit(batch []*dto.MetricFamily)`:** apply the sink-private `deltaState.apply(batch)` (counters → per-flush delta, gauges → absolute, NO shared-slice mutation — the landed `delta.go` contract); then for each family, call `stats.ExtractTags(fam.GetName())` to get the residual name + extracted `[]Label` (the SAME extraction the 47.2b `labelMapper` calls — `internal/stats/name.go:47` — consumed DIRECTLY here, NOT via `labelMapper`/`dto.LabelPair`, since the target shape is an inline wire-string suffix, not a structured metric field); on an `ExtractTags` error (a name matching no top-level rule — a defensive "can't happen" branch, since every name the registry actually holds matches one of the SN1–SN9 rules), fall back to the FULL untransformed name with NO tags (the `labelMapper` precedent — `label.go:39-41`); format ONE DogStatsd line and write ONE UDP datagram per family:
  - COUNTER family `f` → `<prefix>.<residual>:<int delta>|c[|#tags]` (the value is the delta from `apply`).
  - GAUGE family `f` → `<prefix>.<residual>:<int abs>|g[|#tags]` (absolute; gauges may be negative — `int64`; no sign-prefix, AMEND-DSD-LINE-CONFIRMED).

### 8.2 New BackendKind: NONE (the UDP receiver EXTENDS the driver-owned `test/helpers/statsdrecv`)

The dog_statsd line grammar (`<name>:<value>|<type>[|#tag1:val1,...]`) is a STRICT SUPERSET of the plain statsd grammar (`<name>:<value>|<type>`) confirmed at §11 — so `test/helpers/statsdrecv` (the `0092` receiver) is EXTENDED in-place (the SAME package/type, NOT a sibling package per `reference_differential_grpc_receiver_driver_owned`; BackendKind STAYS **38**). This requires revising `ingest`'s CURRENT name/value split, not just appending a further split: today `colon := strings.LastIndexByte(line, ':')` locates the LAST colon in the WHOLE line, which is correct only because a tagless statsd line has exactly one colon; a tagged line's `|#` suffix itself contains `key:value` pairs, so the LAST colon falls INSIDE the tag suffix, not at the name/value boundary. The revised parser must instead locate the FIRST `|` in the line (`pipe1`; neither the name nor the value contains `|`), split `name:value` from `line[:pipe1]` (a colon-split that is now unambiguous — no tag colons precede `pipe1`), then split `line[pipe1+1:]` on a SECOND `|` (if present) into the `c`/`g`/`ms` type token and an optional `#tag1:val1,tag2:val2` tag-suffix token (stripping the leading `#` and splitting on `,` then `:`). The parsed tag SET (`map[string]string`) is stored alongside the existing `DeltaSum`/`Gauge`/`SeenCount` accumulators, exposed via a NEW `Tags(name string) (map[string]string, bool)` accessor. This is BACKWARD-COMPATIBLE with `0092`'s existing usage: a plain-statsd line (no second `|`, no `|#` suffix — `StatsdSink` never emits tags, the proto "does not support tagged metrics") parses identically to today (the FIRST-`|`-then-colon split degenerates to the same name/value/type result as the current LAST-colon split when there is only one colon in the line), with an empty/absent tag set.
