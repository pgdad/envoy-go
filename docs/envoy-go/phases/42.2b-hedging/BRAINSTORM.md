This document captures the design decisions reached during the brainstorm session for phase **42.2b** (`hedging`), the SECOND and FINAL sub-leg of the hedging leg (the SECOND leg of the FOURTH Upstream-robustness-family row, row 42). It CONFIRMS + REFRESHES the parent hedging charter (`docs/envoy-go/phases/42.2-hedging/BRAINSTORM.md`, commit `3979881f`) against the AS-BUILT 42.2a substrate (the per-attempt deadline IMPL squash `55fb279e`, ADR-0250), settles the one residual fork the parent left open (the fan-out budget/concurrency model — reference-silent, so an envoy-go design choice), and CHARTERS the §10 D-H-RACE-family empirical pins for the 42.2b SPEC to execute.

Phase 42.2b layers **CONCURRENCY** + a deliberate **fan-out** on top of the live 42.2a per-attempt deadline: a separate concurrent `hedgeExecutorH1`/`hedgeExecutorH2` (dispatched via the `H{1,2}ClusterAction` closure switch, alongside the byte-stable 42.1 retry branch) that reuses the 42.2a per-attempt unit but launches attempts CONCURRENTLY and collects the first acceptable response. It realizes `RouteAction.hedge_policy` (`route.v3.HedgePolicy`, field 27; `VirtualHost.hedge_policy` field 17 the route-absent fallback): `hedge_on_per_try_timeout` (the only reference-wired field — per-try-timeout-TRIGGERED concurrency) AND the `initial_requests`/`additional_request_chance` fan-out the reference leaves `#not-implemented-hide:` (a deliberate richer-than-reference scope, subject-side verified).

Where phase 42.2a BOUNDS each sequential 42.1 attempt by a deadline and ABANDONS-then-retries on expiry (strictly one attempt in flight), phase 42.2b leaves the slow attempt IN FLIGHT and races a concurrent hedge, returning whichever completes acceptably first. It is the first envoy-go feature with MORE THAN ONE upstream attempt in flight per request.

The load-bearing facts that shape this brainstorm (CONFIRMED against the as-built substrate):

- **The 42.2a substrate landed exactly as the parent charter + the 42.2a SPEC anticipated — and its per-attempt unit is RICHER than the parent assumed.** The as-built `retryExecutorH1`/`retryExecutorH2` (`internal/filter/http/router/retry.go`) wrap each `do{H1,H2}ClusterAction` call in a child `context.WithTimeout(ctx, rp.perTryTimeout)` (when `>0`) and discriminate a per-try-timeout via a **RACE-ROBUST** three-signal test: `perTryTimeout>0 && ctx.Err()==nil && <failure-guard> && (errors.Is(attemptCtx.Err(), DeadlineExceeded) || !time.Now().Before(attemptDeadline))`, where `<failure-guard>` is `resp.localOrigin` (H1) / `resp.localOrigin || resp.Status==0` (H2). The wall-clock fallback is immune to context's timer-goroutine lag; it is READ BEFORE the explicit `cancel()`. On a per-try-timeout: a synthesized **504** (overriding the H1 driver's 502 / the H2 `Status:0` CANCEL sentinel), `IncUpstreamRqPerTryTimeout()`, retried via `perTryTimeoutRetriable()` (`matches(504,false) || retryReset`). The `reset`/`connect-failure` SPLIT landed (`retryReset` the 5th `retryOnBits` value; the `matches` localOrigin arm `(retryConnectFail|retryReset)`). The hedge executor REUSES this exact per-attempt unit concurrently — so the race-robust discriminator + the loser-cancellation interaction is a NEW first-class D-H-RACE charter item (§2.6, §10) the parent (written before 42.2a) could not foresee. ## 2. Design decisions

### 2.1 Subject confirmation: hedging — the `HedgePolicy` proto surface; the #not-implemented-hide finding *(Q-subject → the pre-authorized 42.2b sub-leg)*

`RouteAction.hedge_policy` (field 27; `VirtualHost.hedge_policy` field 17 fallback) is a single `route.v3.HedgePolicy` message in the EXISTING go-control-plane dep (ZERO new module — the 42.2a SPEC D-H-PROTO confirmed `go mod tidy -diff` EMPTY). Its three fields: `initial_requests` (field 1, `*wrapperspb.UInt32Value`, default 1, PGV `gte:1`, **`#not-implemented-hide:`**), `additional_request_chance` (field 2, `*type.v3.FractionalPercent`, default 0%, **`#not-implemented-hide:`**), `hedge_on_per_try_timeout` (field 3, default false — the ONLY reference-wired field). The full field roster + the default/PGV pins are RE-CONFIRMED from the 42.2a SPEC D-H-PROTO probe (§5/§10). The #not-implemented-hide finding is load-bearing: the reference's hedging is per-try-timeout-triggered concurrency (`hedge_on_per_try_timeout`), NOT the fan-out the field names suggest — so the cross-side-faithful core is `hedge_on_per_try_timeout`; the user adds the fan-out as a subject-side-verified departure (§2.5).

### 2.2 The 42.2b sub-leg: hedging over the as-built 42.2a deadline *(Q-split2 → already SUB-SPLIT; 42.2b is the FINAL leg)*

42.2a (`per_try_timeout`) landed the clean prerequisite: a per-attempt deadline the sequential 42.1 loop consumes (bound each attempt; on expiry, a synthesized-504 retriable timeout → the existing re-attempt), cross-side-faithful, no concurrency (ADR-0250, `55fb279e`). 42.2b layers the concurrent `hedgeExecutor` + `hedge_on_per_try_timeout` (which CHANGES the per-try-timeout behavior from abandon-and-retry to leave-in-flight-and-hedge) + the fan-out on top. Splitting isolated the concurrency risk (goroutines, the first-acceptable-wins collector, the cancel/drain lifecycle, the `-race` guarantees) into its own leg, landed `per_try_timeout` as a usable standalone, and kept each leg well under the ADR-0045 gate. 42.2b is the FINAL sub-leg; row 42 flips `done` at its IMPL (§1.3).

### 2.3 The hedge reuses the as-built 42.2a per-attempt unit (incl. the race-robust discriminator) *(self-answered — the as-built substrate)*

The 42.2a per-attempt unit is the natural reuse seam: body replay + `attemptCtx, cancel := context.WithTimeout(ctx, perTryTimeout)` + the race-robust `timedOut` discriminator (the wall-clock fallback + the `localOrigin`/`Status==0` failure-guard, read before `cancel()`) + `do{H1,H2}ClusterAction` + the synthesized-504-on-timeout + the `matches`/`perTryTimeoutRetriable` classify + the CB-admission/outcome seams. The hedge executor runs this unit per goroutine.

CRITICAL as-built wrinkle (§2.6, D-H-RACE — an OPEN risk, NOT a solved one): under the collector's loser-cancellation, a loser goroutine is cancelled by the collector (NOT by its own per-try deadline) — the discriminator must NOT misread that collector-cancel as a per-try-timeout (which would falsely `IncUpstreamRqPerTryTimeout()` + synthesize a 504 for a loser whose result is about to be discarded, CORRUPTING the cross-side `upstream_rq_per_try_timeout` assertion). The as-built discriminator (`perTryTimeout>0 && ctx.Err()==nil && <failure-guard> && (errors.Is(attemptCtx.Err(), DeadlineExceeded) || !time.Now().Before(attemptDeadline))`) does NOT automatically defend against this, and the doc does NOT claim it does: the `<failure-guard>` (`localOrigin`/`Status==0`) is TRUE for a cancelled in-flight attempt (a cancel manifests exactly as the synthesized 502 / `Status:0` sentinel), and the wall-clock fallback `!time.Now().Before(attemptDeadline)` — the very arm the 42.2a IMPL added for race-robustness — fires on deadline-ELAPSE regardless of the cancel cause. So a SLOW loser the collector reaps AFTER that loser has already passed its own `attemptDeadline` would FALSELY fire the per-try-timeout. The `ctx.Err()==nil` parent-alive guard is the only structural defense, and it ONLY suppresses when the collector cancels losers via a context that is an ANCESTOR of the `ctx` each goroutine sees (making `ctx.Err() != nil` for losers) — NOT via the per-attempt child `attemptCtx`. The 42.2b SPEC MUST therefore PIN one of three mitigations (D-H-RACE, §10) — it is NOT assumed solved: **(a)** cancel losers via a hedge-scoped parent context so `ctx.Err() != nil` short-circuits the discriminator; **(b)** add an explicit collector-cancel signal (a sentinel/flag) the discriminator checks BEFORE the wall-clock fallback; or **(c)** suppress the per-try-timeout accounting entirely for any attempt the collector has already abandoned. This is the single highest-risk decision in 42.2b.

### 2.4 hedgeExecutor architecture: a separate concurrent racer *(Q-concurrency → Fork: SEPARATE-EXECUTOR → ADR-0251; CONFIRMED against the as-built seam)*

**Fork (chosen, CONFIRMED): a SEPARATE concurrent `hedgeExecutorH1`/`hedgeExecutorH2`.** The 42.1 `retryExecutorH1`/`retryExecutorH2` (+ the 42.2a deadline) stay byte-identical for the no-hedge path. The `H{1,2}ClusterAction` closure switch (as-built `router.go:578`: `if a.rp != nil { return retryExecutorH1(...) }`) gains a `hedgePolicy` branch BEFORE the retry branch: `if a.hp != nil && a.hp.triggersConcurrency() { return hedgeExecutorH1(ctx, a, req) }`. The `hedgeExecutor` reuses the per-attempt unit but launches attempts as goroutines feeding a result channel, collecting the first acceptable result. Chosen over **the unified concurrent executor** (rejected: it would refactor the byte-stable 42.1/42.2a loop and route the common no-feature path through concurrency machinery — a byte-stability + perf risk; the 42.1 reviewer explicitly sanctioned keeping executors SEPARATE rather than forcing a premature shared abstraction) and **goroutine-per-attempt threaded into the shared loop** (rejected for the same reason). Separation isolates all goroutines/channels/cancellation to the hedge path; the sequential path never spawns a goroutine.

**The per-attempt-unit reuse SHAPE (a PLAN/SPEC call, with a refreshed lean):** the parent left "extract a shared helper vs duplicate ~30 LoC" as a SPEC/PLAN call leaning toward the 42.1 H1/H2-separate duplication precedent. The as-built substrate REFRESHES the calculus: the per-attempt unit now carries the ~15-LoC RACE-ROBUST discriminator, and the hedge executor would bring the copy count to FOUR (H1/H2 × retry/hedge). With four prospective copies of a non-trivial, correctness-load-bearing block, the balance tips toward EXTRACTING a shared per-attempt helper (`runAttempt`-style: takes the ctx + `rp` + the driver closure, returns `(resp, ep, err, timedOut)`) that both the sequential and the concurrent executors call. This is a PLAN decision (not settled here) — but the lean is now EXTRACT, reversing the parent's duplicate-lean, BECAUSE the discriminator's correctness sensitivity (the 42.2a IMPL race-fix) makes a single source of truth materially safer than four hand-maintained copies.

### 2.5 The fan-out scope + the split verification posture *(Q-scope → Fork: IMPLEMENT-FAN-OUT; Q-fanout-verify → Fork: SPLIT-BY-FIELD; CONFIRMED)*

42.2b implements the FULL `HedgePolicy`: `hedge_on_per_try_timeout` (cross-side-faithful) AND the `initial_requests`/`additional_request_chance` parallel fan-out (which the reference leaves `#not-implemented-hide:`). The finer YAGNI option (defer only the probabilistic `additional_request_chance`) was surfaced this session and DECLINED — the full fan-out lands (it is testable at the 0%/100% boundaries; the user's IMPLEMENT-FAN-OUT scope holds). VERIFICATION SPLITS BY FIELD:
- **Cross-side** (the reference implements it): `hedge_on_per_try_timeout` — asserted against `contrib-v1.37.2` (final downstream status + the hedge-as-retry `upstream_rq_retry` + `upstream_rq_per_try_timeout`, offset-invariant per `reference_round_robin_offset_randomized`).
- **Subject-side** (the reference no-ops them — a recorded DEPARTURE): the `initial_requests`/`additional_request_chance` fan-out — router-package unit tests (deterministic, no Docker) + a subject-side differential arm asserting N parallel upstream attempts + first-success-wins. The reference fires exactly 1 initial request, so the upstream-attempt COUNTS diverge cross-side; the offset-invariant DOWNSTREAM-2xx outcome (both sides return 200) STAYS cross-checkable. The subject-side-ONLY fan-out arm is a NEW verification posture for 42.2b (the reference no-ops the fields), NOT a `0075`/`0076` inheritance. The departure is recorded in the BEHAVIOR_CONTRACT + ADR-0251 §Consequences.

### 2.5b The fan-out budget/concurrency model — BUDGET-COUNTED *(Q-fanout-budget → Fork: BUDGET-COUNTED → ADR-0251)*

Because the reference no-ops `initial_requests`/`additional_request_chance`, their concurrency/budget semantics are a PURE envoy-go design choice (no live probe can settle them — a subject-side decision). **Fork (chosen): BUDGET-COUNTED (Envoy-faithful).** The FIRST of the N initial requests is the PRIMARY (NOT a retry — it does not draw `TryAcquireRetry`, does not bump `upstream_rq_retry`). Each ADDITIONAL fan-out attempt beyond the first is a budget-counted retry: it draws `TryAcquireRetry` (denied ⇒ that hedge does not fire; the overflow counter bumps), bumps `upstream_rq_retry`, and counts toward `num_retries`. `additional_request_chance` (a `FractionalPercent`) probabilistically adds ONE more budget-counted attempt — fired iff the draw succeeds AND `TryAcquireRetry` grants (at 100% with an already-exhausted budget/`num_retries`, the additional attempt is budget-DENIED — the testable boundary is "100% ⇒ one more attempt IF budget headroom remains", §2.5). CONSEQUENCES:
- **The budget CAPS the goroutine fan-out** (a safety property) — BUT ONLY if the `TryAcquireRetry` grant GATES the spawn (acquire-then-spawn), NOT spawn-then-acquire. This is an explicit PLAN/SPEC constraint (D-H-RACE-adjacent), NOT an automatic consequence: if N goroutines are spawned first and EACH then calls `TryAcquireRetry`, the budget caps in-flight UPSTREAM attempts but N goroutines were already spawned. With acquire-gates-spawn, a degenerate `initial_requests:1000` cannot spawn 1000 goroutines — it is bounded by `min(N, 1 + num_retries, 1 + retry_budget_headroom)`. NO separate goroutine cap needed; the existing 42.1 budget machinery is the cap, PROVIDED the acquire gates the spawn.
- **Reuses the 42.1 accounting verbatim** — no new counter for the fan-out; the (N−1) additional attempts increment the EXISTING `upstream_rq_retry`/`upstream_rq_retry_overflow` exactly as a sequential retry does. Consistent with the proto's "a retry will be issued" + the shared-budget ethos (ADR-0248/0249).

Chosen over **budget-exempt fan-out** (rejected: all N fire unconditionally ⇒ unbounded goroutines on a large `initial_requests` + diverges from Envoy's hedged-request-counts-as-retry budget accounting). The `additional_request_chance` random draw needs a deterministic test seam (a `FractionalPercent`-to-bool helper unit-tested at 0%/100% boundaries) — a PLAN detail (D-H-RACE-adjacent).

### 2.6 first-acceptable-wins collector semantics + the goroutine lifecycle *(self-answered; the highest-risk pin — D-H-RACE)*

The concurrent collector: each in-flight attempt runs as a goroutine (body replay + the per-attempt deadline ctx + the race-robust discriminator + `do{H1,H2}ClusterAction` + the synthesized-504-on-timeout + `matches` classify + CB-admission + `RecordUpstreamResult`) and sends its `(ActionResponse, endpoint, err)` to a result channel. The collector `select`s the FIRST ACCEPTABLE (non-retriable per `matches`) response → returns it, cancels the in-flight losers via their child `context`, and drains their channel sends (no goroutine leak; the loser's late `RecordUpstreamResult` still fires so outlier detection counts it). Open collector rules (the D-H-RACE charter, §10) — the highest-risk area of 42.2b, to be live-pinned + unit-tested + `-race`-gated:
- **The retry-vs-hedge replacement rule** — if a concurrent attempt returns a RETRIABLE outcome (a real 503, NOT a per-try-timeout) and budget/`num_retries` remain, does the executor launch a REPLACEMENT attempt (keep the in-flight count up), or only launch hedges on a per-try-timeout (`hedge_on_per_try_timeout`)? Live-observed against the reference's `hedge_on_per_try_timeout` behavior.
- **The budget accounting under concurrency** — do concurrent hedges EACH `TryAcquireRetry` (the §2.5b budget-counted model says yes for fan-out attempts; the `hedge_on_per_try_timeout` hedge likewise)? The total in-flight + sequential attempts are capped cluster-wide by `num_retries` + `retry_budget`.
- **The cancel/drain ordering + the loser's `RecordUpstreamResult`** — counted vs double-counted; the loser-cancellation must NOT trip the race-robust discriminator into a false `IncUpstreamRqPerTryTimeout()` (§2.3 — a discarded loser's miscounted timeout corrupts the cross-side counter assertion).
- **The exhaustion terminal** — if ALL attempts settle retriable without an acceptable response, the LAST retriable response is returned (the 42.1 exhaustion semantics).
- **The goroutine-leak / `-race` guarantees** — every spawned goroutine terminates (via completion or context-cancel + drain); `-race`-clean under `-count=1` (`reference_differential_break_protocol_count1`).

### 2.7 Response-flags posture: RX/URX + any hedge flag are a RECORDED DEPARTURE *(self-answered — the 42.1/42.2a/41 precedent)*

Envoy emits `RX`/`URX` (retry) response flags + may annotate hedged requests on the access-log line. envoy-go has NO response-flags plumbing (`RESPONSE_FLAGS` hardcoded `-`; the 42.1 AMEND-RT7 + the 42.2a + the phase-41 CB4 precedent). So any hedge/retry response flag is a RECORDED DEPARTURE; the differential asserts STATS (`upstream_rq_retry`, `upstream_rq_per_try_timeout`) + the final status code, NEVER the access-log line. §5.2.
