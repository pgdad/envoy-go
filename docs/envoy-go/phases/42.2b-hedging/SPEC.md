## 1. Purpose / Mission

Land **concurrent request recovery** at the route boundary: a route whose `retry_policy` carries `per_try_timeout` AND whose `hedge_policy` sets `hedge_on_per_try_timeout:true` no longer ABANDONS a timed-out attempt (the 42.2a behavior) — instead it LEAVES the slow attempt in flight and launches a concurrent HEDGE (a retry against an LB-re-picked host), returning whichever attempt completes acceptably first. Where 42.2a (sequential) bounds each attempt and abandons-then-retries on the deadline (one attempt in flight, a final 504 on exhaustion), 42.2b RACES: the slow original can still WIN (a 200) even after the hedges fire — hedging RECOVERS what sequential ABANDONS (§1.1 AMEND-H2, the headline live finding). It is the project's FIRST feature with more than one upstream attempt in flight per request.

42.2b is the SECOND/FINAL sub-leg of the 42.2a/42.2b sub-split (the BRAINSTORM §1.3 / §2.2): the concurrent `hedgeExecutorH1`/`hedgeExecutorH2` + the first-acceptable-wins collector + the goroutine/cancel/drain lifecycle + `hedge_on_per_try_timeout` + the `initial_requests`/`additional_request_chance` fan-out. **Row 42 flips `done` only at the 42.2b IMPL** (ALL THREE legs 42.1 + 42.2a + 42.2b landed — ADR-0106 + `reference_roadmap_split_phase_row_done`). Byte-identical when no `hedge_policy` (the nil/non-triggering-guard — the 42.1 sequential `retryExecutor` + the 42.2a per-attempt deadline are untouched).

### 1.1 Empirical-finding-driven scope (amendment block per ADR-0044)

The §11 live pins drove these amendments/refinements to the BRAINSTORM design. SEVERAL are SURPRISES that reshape the architecture — the BRAINSTORM (authored before any live hedge probe) made assumptions the reference refutes.

- **AMEND-H1 (THE load-bearing surprise — a hedged per-try-timeout increments `upstream_rq_retry`, NOT `upstream_rq_per_try_timeout`; the latter STAYS 0 under hedge mode).** Live finding (D-H-STATS): with `hedge_on_per_try_timeout:true`, `cluster.<n>.upstream_rq_per_try_timeout` STAYS **0** on EVERY probe — both the slow-but-recovers case (`/delay/2` + `per_try_timeout:0.5s` + `num_retries:3` ⇒ `upstream_rq_per_try_timeout=0`, `upstream_rq_retry=3`, `upstream_rq_total=4`, final 200) AND the very-slow case (`/delay/10` same policy ⇒ `upstream_rq_per_try_timeout=0`, `upstream_rq_retry=3`, `upstream_rq_retry_limit_exceeded=1`, final 200 @ 10s). So `upstream_rq_per_try_timeout` is EXCLUSIVELY the 42.2a SEQUENTIAL-abandon-path counter; under `hedge_on_per_try_timeout` the per-try-timeout becomes a HEDGE (a retry, `upstream_rq_retry`++ + `upstream_rq_retry_backoff_exponential`++), and the original is left in flight — never counted as a per-try-timeout. CONSEQUENCE for envoy-go: the `hedgeExecutor` must NOT call `IncUpstreamRqPerTryTimeout()`; it detects the per-attempt deadline (to LAUNCH a hedge) and counts it as a retry. This REFRAMES the BRAINSTORM (the `next-prompt.txt` + BRAINSTORM §1.6(c)/§5.1 said "a per-try-timeout that triggers a hedge increments `upstream_rq_per_try_timeout`" — REFUTED). §7.
- **AMEND-H2 (hedging RECOVERS what sequential ABANDONS — the headline + the differential basis).** Live finding (D-H-HEDGE-BEHAVIOR): the SAME route (`/delay/2` + `per_try_timeout:0.5s` + `num_retries:3`) returns **200 @ 2.0s** WITH `hedge_on_per_try_timeout` (the slow original is left in flight and completes; `upstream_rq_retry=3`, `upstream_rq_per_try_timeout=0`, `upstream_rq_retry_limit_exceeded=0`) but **504 @ 2.0s** WITHOUT it (the 42.2a sequential abandon-and-retry; `upstream_rq_per_try_timeout=4`, `upstream_rq_retry=3`, `upstream_rq_retry_limit_exceeded=1`). And `/delay/10` + hedge returns **200 @ 10s** WITH `upstream_rq_retry_limit_exceeded=1` (the `num_retries` cap was hit at ~1.5s, but the request WAITED for the in-flight original). So under hedging, `upstream_rq_retry_limit_exceeded` means "no MORE hedges can launch" — NOT "final failure"; the request returns the first ACCEPTABLE result among ALL in-flight attempts (the slow original wins). The terminal is first-acceptable-wins, not a 504-on-exhaustion.
- **AMEND-H3 (the reference CANCELS losers; cancelled losers are UNCOUNTED — the D-H-RACE hazard is DISSOLVED at the source).** Live finding (D-H-RACE/D-H-STATS): when the winner completes, the in-flight losers are cancelled (`upstream_rq_total=4` but `upstream_rq_200=1` — only the winner's 200 counts; the 3 in-flight losers' upstreams are reset, counted as neither 200 nor per-try-timeout). Combined with AMEND-H1 (the hedge path NEVER calls `IncUpstreamRqPerTryTimeout`), the BRAINSTORM's headline D-H-RACE hazard ("the collector's loser-cancellation trips the race-robust per-try-timeout discriminator into a false synthesized-504") is DISSOLVED: the `hedgeExecutor` does NOT reuse the 42.2a abandon-and-count discriminator at all — the per-try-timeout in hedge mode is a HEDGE-TRIGGER (timer fires → launch a hedge, leave the original running), NOT an attempt-cancelling deadline (CONTRAST 42.2a's `context.WithTimeout` that cancels + counts). So the executor never increments `upstream_rq_per_try_timeout`, and a cancelled loser cannot corrupt it. The remaining D-H-RACE obligation REDUCES to goroutine hygiene (cancel + drain + no-leak + `-race`-clean) + first-acceptable-collector correctness. §3.2.
- **AMEND-H4 (the fan-out fields are NO-OPS in the reference — confirmed behaviorally).** Live finding (D-H-PROTO/HEDGE-BEHAVIOR): `hedge_policy{initial_requests:3}` on a fast backend fires EXACTLY **1** upstream request (Δ`upstream_rq_total`=1) — the reference no-ops `initial_requests` (the `#not-implemented-hide:` annotation, confirmed behaviorally). PGV: `initial_requests:0` ⇒ a config reject (`HedgePolicyValidationError.InitialRequests: value must be greater than or equal to 1` — the `gte:1`); `initial_requests:3` (a no-op field set) ⇒ config ACCEPTED (`configuration OK`). So the cross-side-faithful core is `hedge_on_per_try_timeout` ONLY; the `initial_requests`/`additional_request_chance` fan-out is implemented richer-than-reference (the BRAINSTORM Q-scope IMPLEMENT-FAN-OUT), verified SUBJECT-SIDE (SPLIT-BY-FIELD), with the BUDGET-COUNTED accounting (§3.3). §5.
- **AMEND-H5 (NO new stat — surface STAYS 1181).** Live finding (D-H-STATS): NO hedge-specific counter exists in a hedging cluster's `/stats` roster (no `*hedge*` name; `retry_or_shadow_abandoned` STAYED 0 — the cancelled losers are NOT counted as "abandoned retries"; the global `upstream_rq_timeout` STAYED 0 — `RouteAction.timeout` deferred; `upstream_rq_per_try_idle_timeout` STAYED 0 — `per_try_idle_timeout` deferred). A hedge REUSES the EXISTING `upstream_rq_retry` (+ `upstream_rq_retry_backoff_exponential`); per AMEND-H1 it does NOT touch `upstream_rq_per_try_timeout`. So 42.2b registers NOTHING NEW — stat surface STAYS **1181** (the BRAINSTORM's "+0 net" CONFIRMED, and even firmer: NO new name AND the per_try_timeout counter is untouched). §7.
- **AMEND-H6 (the differential — single-held-host + release-barrier gives a DETERMINISTIC cross-side 200 with exact counts).** Live finding (D-H-DIFFERENTIAL): a SINGLE held `BlockingHoldResponder` host makes the original + N hedges all launch onto the held host (the per-try-timeouts at T, 2T, …, NT all become hedges) — poll until `upstream_rq_retry==N` + `upstream_rq_retry_limit_exceeded==1` (the hedges all launched, the cap hit), THEN `/__release` ⇒ the first held attempt completes 200 ⇒ downstream **200**, losers cancelled. Cross-side EXACT (SINGLE host, offset-irrelevant — no `reference_round_robin_offset_randomized` exposure): `upstream_rq_retry==N`, `upstream_rq_per_try_timeout==**0**` (AMEND-H1), `upstream_rq_retry_limit_exceeded==1`, `upstream_rq_total==N+1`, `upstream_rq_200==1`, final downstream **200**. `0077-hedge-on-per-try-timeout`; NO new BackendKind (REUSE `BlockingHoldResponder` 36). §8.

The `H{1,2}ClusterAction` closure switch (as-built `router.go:578`: `if a.rp != nil { return retryExecutorH1(...) }`) gains a `hedgePolicy` branch BEFORE the retry branch:

```
if a.hp != nil && a.hp.triggersConcurrency() { return hedgeExecutorH1(ctx, a, req) }
if a.rp != nil { return retryExecutorH1(ctx, a, req) }
return doH1ClusterAction(ctx, a, req)
```

`triggersConcurrency()` = `initialRequests > 1 || additionalRequestChance > 0 || hedgeOnPerTryTimeout` (a nil or non-triggering `hedgePolicy` ⇒ the exact 42.1/42.2a path ⇒ byte-identical — the full 78-dir gate holds). The `hedgePolicy` is carried on `clusterRouteAction` (`hcm/actions.go`, alongside `retryPolicy`) + threaded through the widened `H{1,2}ClusterAction` constructor signatures onto the `routerAction`/`routerActionH2`.

The `hedgeExecutor` REUSES the per-attempt unit (body replay + `do{H1,H2}ClusterAction` + the `matches` classify + the per-attempt `TryAcquireRequest` CB-admission + the `RecordUpstreamResult` outcome seam + the activated `retry_budget`) but orchestrates it CONCURRENTLY: it launches an attempt as a goroutine feeding a result channel + a per-attempt HEDGE-TRIGGER timer, and collects the first ACCEPTABLE result.

### 3.2 The per-attempt HEDGE-TRIGGER timer (NOT the 42.2a cancelling deadline) — AMEND-H1/H3

This is the LOAD-BEARING architectural distinction the live findings forced. In 42.2a (sequential), the per-attempt deadline is a `context.WithTimeout` that CANCELS the attempt + abandons it + synthesizes a 504 + `IncUpstreamRqPerTryTimeout()`. In 42.2b (hedge), the per-attempt timeout is a HEDGE-TRIGGER: a timer (per in-flight attempt) that, on firing, LAUNCHES a hedge (a new concurrent attempt) WITHOUT cancelling or counting the original — the original goroutine runs the driver to natural completion (or until the collector cancels it as a loser, or the request ctx is cancelled). So:
- The attempt goroutine runs `do{H1,H2}ClusterAction` with a context derived from a HEDGE-SCOPED parent (`hedgeCtx`, a child of the request `ctx`), NOT a per-attempt `WithTimeout` (the original must NOT self-cancel at the per-try-timeout — live-confirmed: probe E's original ran to 10s).
- A separate per-attempt timer fires at `per_try_timeout`; on firing (and if `num_retries`/budget remain), it launches ONE hedge (`IncUpstreamRqRetry()` + `IncUpstreamRqRetryBackoffExponential()` + `TryAcquireRetry`; NO `IncUpstreamRqPerTryTimeout` — AMEND-H1) and re-arms a timer for the new attempt.
- The collector `select`s the FIRST ACCEPTABLE (`!matches(status, localOrigin)`) result from the channel → returns it, cancels ALL in-flight losers via `hedgeCtx`-derived cancels, drains their channel sends (the loser's `RecordUpstreamResult` still fires inside the driver so outlier detection counts every attempt; the cancelled loser is NOT counted as 200 / per-try-timeout — AMEND-H3, reference parity).
- On `num_retries` exhaustion (no more hedges can launch): `IncUpstreamRqRetryLimitExceeded()` ONCE, but the request CONTINUES — it awaits the first acceptable among the in-flight attempts (AMEND-H2). If ALL in-flight settle retriable (no acceptable), the LAST retriable result is returned (the 42.1 exhaustion semantics).
- `upstream_rq_retry_success` accounting under hedging is UNVERIFIED by the probes (in PROBE A/E the ORIGINAL — not a hedge — won, so `retry_success` would be 0 there) — whether a hedge-recovered win increments it is a PLAN/IMPL D-question (D-S422B-9), NOT asserted by `0077` (a held-host winner is ambiguous between the original and a hedge); the 42.1 `attempt>0` precedent is the candidate rule.

Because the `hedgeExecutor` NEVER calls `IncUpstreamRqPerTryTimeout` and uses a hedge-trigger timer (not a cancelling deadline + the 42.2a discriminator), the BRAINSTORM's D-H-RACE "loser-cancel trips the discriminator" hazard cannot occur (AMEND-H3). The collector's correctness (first-acceptable selection, loser cancel/drain, no goroutine leak) + `-race`-cleanliness is the remaining D-H-RACE obligation (D-S422B-2, unit-tested + `-race`-gated).

### 3.3 The BUDGET-COUNTED fan-out (`initial_requests`/`additional_request_chance`) — subject-side; AMEND-H4 + the BRAINSTORM Q-fanout-budget

`initial_requests:N` fires up to N concurrent attempts up front: 1 PRIMARY (not a retry) + (N−1) budget-counted hedges (each `TryAcquireRetry` + `upstream_rq_retry`++ + `upstream_rq_retry_backoff_exponential`++, capped by `num_retries` + the `retry_budget`). `additional_request_chance` (a `FractionalPercent`) probabilistically adds ONE more budget-counted attempt (fired iff the draw succeeds AND `TryAcquireRetry` grants). All feed the same first-acceptable collector. CONSEQUENCE (the BRAINSTORM safety property): the `retry_budget` + `num_retries` CAP the goroutine fan-out — PROVIDED the `TryAcquireRetry` grant GATES the spawn (acquire-then-spawn, NOT spawn-then-acquire — an explicit PLAN/IMPL constraint, D-S422B-3). The fan-out is SUBJECT-SIDE verified (the reference no-ops it — AMEND-H4); the offset-invariant downstream-2xx outcome stays cross-checkable. A recorded departure (BEHAVIOR_CONTRACT + ADR-0251 §Consequences).

## 8. Differential fixture taxonomy (+1: `0077` cross-side hedge-on-per-try-timeout — held-host first-acceptable-wins; + a possible subject-side fan-out dir)

### 8.1 `0077-hedge-on-per-try-timeout` (cross-side; NO new BackendKind)
