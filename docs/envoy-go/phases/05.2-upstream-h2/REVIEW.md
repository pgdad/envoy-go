## Strengths

- **Doctrine D-3.2 compliance is rigorously verifiable, end-to-end across the boundary.** Production grep of the forbidden runtime types returns zero call sites; the only textual mentions are inside `doc.go`'s prohibition statement. The ADR-0046 boundary holds at 5 allowed files; the count discrepancy from 05.1 (which named 4 files) is now correct because `client.go` is the new fifth file. Driver-side use in `test/helpers/h2.go`, `test/fixtures/0004-h2-routing/driver/driver.go`, and `test/conformance/h2spec/` is correctly contained.
- **`writeData` chunking implementation is small, defensive, and correct.** Both `ServerConn.writeData` (`conn.go:686-760`) and `ClientConn.writeData` (`client.go:550-602`) follow the same template: per-stream window reserved FIRST (smaller bound first → reduces head-of-line blocking on conn-level), conn-level reserved second for the streamTaken amount, conn-level under-reservation triggers per-stream replenishment so window state stays consistent. The ctx-cancel error path replenishes only the per-stream over-reservation (NOT the conn-level reserve which is already complete) — subtly correct. The empty-body + endStream zero-DATA-frame emission discipline is preserved (the chunking loop is skipped when `len(b) == 0`).
- **`reserveBlocking` collapse delivers M-3's atomicity fix.** The PLAN-anticipated atomicity hazard (`waitFor` releases the lock; a second goroutine drains the window before the first calls `reserve`) is closed. The new `flow.window.reserveBlocking(ctx, max)` is a single mutex-guarded operation; the dead `if taken <= 0` recovery branch is deleted; the regression test in `flow_test.go` and the race-detector pass on the multi-stream surface validate the fix.
- **Inbound flow-control is now load-bearing.** The receive-side debit + half-window WINDOW_UPDATE emission policy at the threshold of 32768 is implemented symmetrically on both `ServerConn.onData` and `ClientConn.dispatchFrame`'s DATA case. Per-conn and per-stream debit accumulators are mutated only from the readLoop goroutine, so no separate mutex is required (the comments at `client.go:80-84` make this happens-before discipline explicit). The half-window threshold matches `golang.org/x/net/http2` and Envoy's defaults; ADR-0055's Consequences section justifies the choice + the future-tunability note.
- **Overflow bounds-check via `safeAddInt32` is uniformly applied.** Both stream-level (`stream.go`'s `recvWindowUpdate`) and conn-level (`conn.go`'s `onWindowUpdate` + `client.go`'s WINDOW_UPDATE dispatch) sites use the same helper; on overflow the conn-level path emits GOAWAY(FLOW_CONTROL_ERROR) and the stream-level path finishes the stream with `streamError(ErrFlowControlError)` so RoundTrip returns. The discipline matches RFC 9113 §6.9.1.
- **`Cluster.DialH2`'s defensive `HandshakeContext(ctx)` is cheap and correct insurance.** The handshake is normally complete by the time `Cluster.Dial` returns (the `crypto/tls.Conn` lazily handshakes on first read/write, and `Cluster.Dial`'s phase-03 implementation reads/writes during connect); the explicit call here is a no-op on already-handshaken conns and ensures `NegotiatedProtocol` is authoritative even under a future `Cluster.Dial` refactor. SPEC §11.3 mitigation is small + grep-verifiable.
- **`extractH2Mode`'s eight-branch decision matrix is exhaustive and well-documented.** Each branch has an explicit comment naming the SPEC clause it implements: ExplicitHttpConfig with Http2 → useH2=true; ExplicitHttpConfig with Http1 → silent-ignore (correct phase-04 baseline-preserving behaviour); AutoConfig → silent-ignore (the documented narrowing of master SPEC §5.8); UpstreamProtocolOptions=nil/default → silent-ignore (defensive). The three build-error diagnostics carry the cluster name and the actual offending value (got %q, got %v) for operator usability. The validation-when-useH2-true block enforces transport_socket presence, type, and ALPN-h2-presence at build time, surfacing config errors before runtime.
- **`routerActionH2.doH2`'s ctx-cancel discriminator is correct + non-trivial.** The decision check `ctx.Err() != nil && (errors.Is(ctx.Err(), context.Canceled) || errors.Is(ctx.Err(), context.DeadlineExceeded))` (`actions.go:195`) discriminates caller-side cancellation (→ RST_STREAM(CANCEL)) from upstream-conn-broken errors that wrap `cc.ctx.Err()` (→ 502). A naive `errors.Is(err, context.Canceled)` would match both and mis-categorize. The comment at `actions.go:189-194` explicitly documents this trap.

The advisory-response note at PLAN line 209 explicitly preserves phase-04 byte-equivalence (the H1 path's empty-body 502 is NOT changed in 05.2).

**I-2. `routerActionH2.do` (the H1-path defensive stub) writes a 500 status line with NO body and is unreachable in well-formed bootstraps — but the unreachability claim is not enforced.** *(`internal/filter/hcm/actions.go:240-246` + the compile-time conformance assertion at `:252`)*

The `*routerActionH2` type satisfies the `routeAction` interface so it can be stored in `routeEntry.action` and reachable via the shared route-table machinery. The `do` method's docstring claims this branch is "unreachable in well-formed bootstraps: variant selection at filter-build time guarantees H2-clusters get *routerActionH2 and the HCM-level codec dispatch picks the H2 driver for those listeners." But:

1. There is no defensive runtime check that catches this unreachability claim. If a future bootstrap shape gets a malformed `routerActionH2` onto an H1 listener (via an HCM `codec_type: AUTO` listener with `alpn_protocols: ["h2", "http/1.1"]` that negotiates `http/1.1` to a route pointing at an H2 cluster — a configuration shape SPEC §5.5 does not explicitly forbid), the stub silently produces a 500 with no body. There is no log line, no metric increment, no panic.
2. The fall-through is also not unit-tested. A test that constructs a bootstrap with this shape and asserts the diagnostic would catch a future regression where the route-table builder no longer enforces the variant-selection invariant.

**Why it matters:** D-3.4 (context isolation) — a stranger reading the `do` method's docstring would expect either the defensive stub to be observable (log / metric) or the unreachability invariant to be enforced (a `panic` on first call would surface the misconfiguration loudly). As written, a misconfiguration produces a silent 500 that is difficult to debug. SPEC §5.5's "the configuration is rejected at build time" language is honoured for the explicit cases (no transport_socket, wrong type, ALPN-lacks-h2) but not for the implicit codec_type=AUTO + ALPN=http/1.1 + H2-cluster shape this stub guards.

**Fix (minimum):** add a one-line `log.Printf("hcm: routerActionH2.do reached on H1 path — bootstrap misconfiguration; route variant selection should have produced *routerAction, not *routerActionH2")` before the 500 emission, plus a unit test that synthesises the misconfiguration shape and asserts the log line is emitted (or asserts a counter increment if 05.2 had a stats surface; it doesn't, so log is the right level for now).

**Fix (preferred):** at filter-build time, add a defensive route-table validation pass that walks all routes and rejects any `*routerActionH2` whose listener's `codec_type` is not `HTTP2` (and whose listener's `alpn_protocols` doesn't include `h2`); fail-build with a diagnostic. This makes the unreachability claim a build-time invariant rather than a runtime stub.

**Disposition:** state-3 follow-up acceptable but the project may prefer to defer to phase 07's filter-chain framework where the broader codec-mismatch detection lives. **Recommend deferral to phase 07** with a `phase-07-must-consider` tag in PROGRESS, OR a small log-line addition in a state-3 follow-up commit (5-line change). Either is acceptable; the gap is dormant in 05.2 (fixture 0004 doesn't exercise the misconfiguration shape).

**M-8. `ClientConn.Close`'s `closeOnce` discipline is correct but the `closeErr = cc.conn.Close()` capture races with the GoAway-emit-best-effort branch.** *(`client.go:607-621`)*

`Close` is documented as "Idempotent — safe to call from multiple goroutines." The `closeOnce.Do` ensures only one goroutine performs the body; the body sets `closeErr = cc.conn.Close()`. After the first call returns `closeErr`, subsequent `Close()` calls return... `closeErr` from the closure variable, which is captured by reference in the `closeOnce.Do` lambda. Wait — Go 1.21+ defines `Do` to "call the function f if and only if Do is being called for the first time for this instance of Once. ... return only after any call to f has completed". So subsequent calls return from `Do` with `closeErr` already set; the variable is captured in the function literal, not in `Do` itself.

Re-reading: the variable is declared at line 608 (`var closeErr error`), the `Do` body sets it at line 618 (`closeErr = cc.conn.Close()`), and line 621 returns it. Subsequent `Close` calls re-enter the function, see `var closeErr error` declared as a fresh zero-value, call `Do` (which is a no-op since the once already fired), and return the freshly-zero-valued `closeErr`. **This means the SECOND and subsequent calls to `Close` return `nil` even if the first call failed with an error from `cc.conn.Close()`.**

**Fix:** lift `closeErr` into a `*ClientConn` field so the value persists across re-entries; OR rely on the documented contract that `Close` may return error only on the first call and subsequent calls return nil (which is the stdlib's `io.Closer` discipline already, so this is acceptable). **Disposition:** accept the current shape; this is the stdlib `io.Closer` discipline. Cosmetic at most. The first-caller's error is the authoritative one; subsequent callers don't expect to learn about it.
